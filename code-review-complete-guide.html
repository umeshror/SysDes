1. Philosophy: Why Code Review Exists

Before tactics, you need to understand the purpose. Most developers think code review is about catching bugs. That's too narrow. The resources on the Awesome Code Review list converge on a richer picture:

The Four Real Purposes

  1. Codebase health over time — The primary goal isn't perfection in any single PR. It's that the codebase improves on a trajectory. A CL that makes things 10% better should be approved, even if it isn't perfect.
  2. Knowledge sharing — Reviews spread understanding of the codebase across the whole team. Microsoft's research shows that developers cite knowledge transfer as the #1 value of code review — ahead of bug detection.
  3. Mentorship — Reviews are an opportunity to pass along best practices, architectural instincts, and domain knowledge to newer developers.
  4. Social bonding — A well-run code review builds trust between teammates. It signals "I care about your success and the quality of what we ship together."
"Code reviews are as much a social exercise as a technical one. They're an opportunity for teammates to share knowledge and bond through collaboration."
⚠️ The Anti-Pattern: Gatekeeping

If your reviews feel like a toll booth — where developers grudgingly pay their way through — you've lost. Reviews should feel like collaboration, not inspection. The difference shows up in language, speed, and tone. All of that is in your control as a reviewer.

2. What to Actually Look For

Google's engineering practices document gives the most complete checklist. Here it is, with examples added for each item:

🧭 Design

Does the change fit the architecture? Are pieces interacting well?

❌ Bad Design Signal

A developer adds a feature by storing user preferences in the HTTP session object. Works now — but now preferences are lost on logout, can't be shared across devices, and can't be queried from admin tools. The design is wrong even if the code is clean.

✅ Right Comment

"Storing prefs in the session means they can't survive a logout or be accessed server-side. Would you be open to persisting this to the UserProfile table instead? Happy to discuss the migration path."

⚙️ Functionality

Does the code do what the author intended? Does it do what users need?

  • Think about edge cases: empty lists, null values, concurrent modification, very large inputs
  • Think about the user's mental model: will they see the right error message when this fails?
  • Think about race conditions in async/parallel code
// What would a reviewer catch here? function calculateAverage(numbers) { return numbers.reduce((sum, n) => sum + n, 0) / numbers.length; // BUG: if numbers = [], returns NaN (0 / 0) } // After the review: function calculateAverage(numbers) { if (numbers.length === 0) return 0; return numbers.reduce((sum, n) => sum + n, 0) / numbers.length; }

🧠 Complexity

Could this be simpler? Will a future developer be able to understand and modify this safely?

"Reviewers should be especially vigilant about over-engineering. Encourage developers to solve the problem they know needs to be solved now, not the problem that the developer speculates might need to be solved in the future."
🚫 YAGNI — You Aren't Gonna Need It

This is one of the most linked principles in the list. A developer building a NotificationService might add plugin hooks, strategy patterns, and event buses "for future extensibility." But if the current feature just needs to send one email — all of that is waste. Future requirements will change the interface anyway. Build what you know you need, today.

🧪 Tests

Tests are code too. They need to be reviewed with the same rigor as production code. Ask:

  • Will this test actually fail if the code breaks?
  • Does it test behavior, or is it just a ceremony that always passes?
  • Are edge cases covered?
  • Is the test brittle — will minor refactoring break it even if the behavior is still correct?
// Weak test — tests nothing meaningful: it('should return a user', () => { const result = getUser(1); expect(result).toBeDefined(); // Always true if no exception thrown }); // Strong test — tests actual behavior: it('should return the correct user name and email', () => { const result = getUser(1); expect(result.name).toBe('Alice'); expect(result.email).toBe('alice@example.com'); }); it('should throw NotFoundError for a non-existent ID', () => { expect(() => getUser(999)).toThrow(NotFoundError); });

📛 Naming

Names are the primary documentation of code. Bad names force every future reader to reverse-engineer intent.

❌ Confusing const d = new Date();
let x = users.filter(u => u.a);
function proc(inp) { ... }
✅ Clear const createdAt = new Date();
let activeUsers = users.filter(u => u.isActive);
function processPayment(order) { ... }

💬 Comments in Code

Code comments should explain why, not what. If the "what" isn't obvious from the code, fix the code — don't add a comment to explain confusing code.

❌ Useless // Increment i by 1
i++;
✅ Valuable // Skip the first element — it's always a header row
// that the CSV library doesn't strip automatically
for (let i = 1; i < rows.length; i++) {

📐 Style

Style debates with no canonical reference are a waste of time. The style guide is law. If there is no style guide, accept the author's style — and then create a style guide after.

3. How to Navigate a PR / CL

A PR with 30 changed files is overwhelming if you start at the top and work down. Google's engineering practices give a structured way to navigate:

  1. Read the description first. Does this change make sense? Is it solving the right problem? If the description is missing or vague, ask for one before reviewing. A good description explains what the change does and why.
  2. Find the "main" file. Usually one file has the largest number of logical changes. Start there. This gives you context that makes the rest of the PR fall into place.
  3. Read the tests. Tests tell you what the author intended to do. They're the executable specification. Read them before the implementation.
  4. Check for major design problems immediately. If there are architectural issues, flag them right away — even if you haven't finished reviewing. If you find a fatal design flaw on file 2 of 30, there's no point reviewing files 3–30. The developer needs to know now, before they build more code on top of this base.
  5. Review the rest in logical order. After major files, go through remaining files systematically. Most review tools have a sensible default order.
💡 When to Reject Before Starting

Sometimes a PR shouldn't exist at all — the team is deprecating the system being modified, or the approach fundamentally conflicts with the roadmap. Reject early and politely. Example: "Looks like you put some good work into this! However, we're moving away from the FooWidget system you're modifying. Would you be open to discussing an alternative approach before we proceed?"

4. Speed: The Most Underrated Factor

Most complaints developers have about code review are actually complaints about speed. Slow reviews cause cascading damage:

  • Team velocity drops — other developers are blocked waiting for their dependencies to land
  • Context is lost — the author has moved on mentally; revisiting old code is now expensive
  • Quality pressure builds — developers start accepting subpar code just to get things moving
  • Cleanups stop happening — nobody refactors if they know it'll sit in review for a week
"One business day is the maximum time it should take to respond to a code review request. Following this guideline means a typical CL should get multiple rounds of review within a single day."
— Google Engineering Practices

The Right Tradeoff: Personal vs. Team Velocity

There's one exception: don't interrupt deep work. Research shows that interrupting focused coding is more expensive for the team than making a developer wait an hour or two. The key word is "respond" — you don't need to drop everything immediately. Wait for a natural break (after lunch, end of a task, returning from a meeting), then review promptly.

When to Give LGTM With Outstanding Comments

You can approve a PR while still leaving comments if:

  • You're confident the developer will address the remaining notes appropriately
  • The remaining comments are minor and don't affect correctness

This avoids an unnecessary round-trip for low-stakes nits. It's a sign of trust and respect for the author's judgment.

Timezone Handling

When working across timezones, try to return reviews while the author still has time to respond the same day. A review dropped at 5pm in their timezone effectively adds a full day to the cycle. If you can't complete a full review, send a partial response with a note on when you'll finish. The developer can unblock on the initial comments.

5. Writing Great Review Comments

The Core Rule: Code, Not Person

Every comment should be about a line of code, a function, a design decision — never about the developer as a person. This single rule, if followed religiously, eliminates most toxic review behavior.

❌ Personal "You wrote this in the worst possible way."

"Did you even test this?"

"I can't believe you didn't handle the null case."
✅ About the Code "This function will throw if the array is empty. What would you think about adding a guard clause?"

"There doesn't appear to be a test for the null input case — would a test here help document this behavior?"

The "Never Say You" Technique (mtlynch)

Michael Lynch suggests never using the word "you" in a review comment. It sounds extreme but works: it forces you to phrase feedback about the code, not the person who wrote it.

❌ With "you" "You need to handle the error here."

"Why did you use a loop instead of a map?"

"You should add a test for this."
✅ Without "you" "This error case isn't handled — would it make sense to return an empty array here?"

"Curious about the loop vs. map choice here — is there a performance reason?"

"A test covering this edge case would help document the expected behavior."

Back Opinions with Evidence

Never present a personal preference as a fact. If you want something changed, cite:

  • The style guide: "The style guide (section 3.4) prefers early returns over nested if blocks."
  • A performance measurement: "I benchmarked this — the Map lookup is 10x faster than iterating for large inputs."
  • A documented best practice: "MDN recommends against this approach because X."
  • A concrete concern: "This regex can catastrophically backtrack on inputs like 'aaaaaab' — here's a safer alternative."

Ask Questions, Don't Issue Commands

❌ Commands "Rename this variable."

"Move this to a separate function."

"Don't use a for loop here."
✅ Questions & Suggestions "What would you think about a name like activeUsers to make the intent clearer?"

"This is getting complex — would extracting the validation logic into its own function help readability?"

".map() might communicate the intent more clearly here — curious if you considered it?"

Show Code Examples (Sparingly)

When a suggestion is clear and uncontroversial, a concrete code example communicates faster than words. But limit yourself to 2–3 per review round. If you're writing the entire PR for someone, you're signaling you don't trust them.

// Your comment: // "This 8-line loop can be a one-liner — would this work?" // Current code: const result = []; for (let i = 0; i < users.length; i++) { if (users[i].isActive) { result.push(users[i].name); } } return result; // Suggested replacement: return users.filter(u => u.isActive).map(u => u.name);

Praise Good Work

This is not optional politeness. Positive reinforcement motivates developers, creates psychological safety, and builds the kind of trust where they want their code reviewed rather than dread it.

✅ Examples of Good Praise

"This error handling is really clean — I'll remember this pattern."

"Great test coverage on the edge cases. Exactly what this function needed."

"I didn't know about this API — this is a much better approach than what we've been doing."

Signal Why Something Matters

Don't just flag a problem. Explain why fixing it matters. This is how you teach, not just enforce.

💡 Example with Context

"This query runs inside the loop, so for 1,000 users we're making 1,000 DB calls. Moving it outside and batching the results will make this page load 50× faster under real traffic. Happy to show an example."

6. Conventional Comments

Conventional Comments is a standard format for writing review comments that immediately communicates the reviewer's intent. It works by prefixing every comment with a typed label.

The Format

<label> [(decorations)]: subject Optional discussion — explain the "why", provide context, suggest a path to resolution, or cite relevant documentation.

The Labels

blocker issue suggestion question nitpick praise thought todo
LabelMeaningAction Required?
blocker This must be fixed before merge. A real defect, security issue, or correctness failure. Yes — cannot merge
issue A problem that needs to be addressed. Often paired with a suggestion for how to fix it. Yes — should fix
suggestion A proposed improvement. May or may not be blocking depending on severity. Pair with a (blocking) or (non-blocking) decoration. Depends on decoration
question A genuine question. Seeking understanding, not implying a problem. May resolve to no action if the author explains the rationale. Answer, not necessarily change
nitpick A trivial preference — variable name, whitespace, a minor stylistic thing. Almost always non-blocking. Usually no
praise Genuine positive recognition. No action needed, but powerful for culture and motivation. No
thought An idea that might spark a discussion or future improvement. Not an actionable request right now. No — food for thought
todo A small, clear action item. Usually blocking. Yes — before merge

Decorations

Decorations add precision to a label. The most important ones:

  • (blocking) — must be resolved before merge
  • (non-blocking) — author may address at their discretion
  • (if-minor) — blocking only if the fix is easy
  • (security) — security-sensitive suggestion

Real Examples

blocker: This endpoint has no authentication check. Any unauthenticated user can access all customer data. Please add the @RequireAuth decorator before merging. issue: This function doesn't handle empty arrays. If passed [], it returns NaN. Consider returning 0 or throwing a more descriptive error. suggestion (non-blocking): The .filter().map() chain could be a single .reduce() call, which avoids a full second pass. Only worth changing if performance is a concern here. question: Why is the timeout set to 30 seconds here rather than the standard 5? Is this an intentional exception? nitpick (non-blocking): "isUserAuthenticated" could just be "isAuthenticated" since the context already implies a user. Up to you! praise: This retry logic with exponential backoff is elegant. I'll borrow this pattern for the jobs queue. thought: Long-term it might be nice to extract the validation logic into a shared utility — not for this PR, but worth noting for future refactoring discussions.
🏆 Why This System is Powerful

In async code review (the default for most teams), tone is invisible. A comment that reads as casual curiosity to the author might feel like an accusation to the reader. Labels remove the guesswork. The author knows exactly what they're dealing with: is this a crisis or a nitpick? Can they merge after answering a question, or do they need to redesign something?

7. Netlify's Feedback Ladder

Netlify published one of the most practical ideas in the list: the feedback ladder. The core insight is that review comments exist on a spectrum, and teams that communicate this spectrum explicitly have far smoother reviews.

The ladder (from most to least critical):

RungLabelMeaning
🔴 6BlockerCannot merge. Correctness, security, or a fundamental design failure.
🟠 5Should FixStrong recommendation. Would significantly improve code health.
🟡 4ConsiderA suggestion worth thinking about. Won't block the PR.
🟢 3NitA trivial stylistic preference. Take it or leave it.
🔵 2PraiseCalling out something good. No action needed.
⚪ 1FYISharing information. No action requested.

The Roundtrip Problem

"Roundtrips — from teammate to reviewer back to teammate — are expensive, costing up to two working days of a sprint each time."

Every unnecessary back-and-forth round is a tax on both the author and the reviewer. The feedback ladder reduces roundtrips in two ways:

  1. Authors can immediately see which comments block them and which don't — no more waiting to clarify whether a comment means "fix this now" or "think about this someday."
  2. Reviewers are forced to decide whether something truly blocks a merge before writing the comment. This naturally filters out low-signal noise.

Self-Review as a Pre-emptive Tool

Netlify also recommends that authors review their own code before submitting and annotate it with comments meant for the reviewer. For example:

// Author's note for reviewer: // I chose the retry-3-times approach here instead of circuit breakers // because this endpoint is called infrequently and the infra team // doesn't have circuit breaker support yet. Open to other approaches // if there's a strong preference.

This proactively answers questions the reviewer was about to ask, saving an entire roundtrip.

8. Toxic Behaviors to Unlearn

Sandya Sankarram's talk "Unlearning Toxic Behaviors in a Code Review Culture" is one of the most human-centered pieces on the list. The behaviors she identifies:

🧨 Toxic Behavior #1: Opinion Passed Off as Fact

❌ Toxic "This is wrong. Use a hashmap."
✅ Backed by Evidence "For this size of input (>1000 items), a Map lookup is O(1) vs O(n) for the array search. If performance matters here, the Map would be worth the added complexity."

Personal preference is not a sufficient reason to request a change. Developers need to know why. If you can't explain the why, reconsider whether you're asking for a real improvement.

🧨 Toxic Behavior #2: The Comment Avalanche

Dumping 50 comments in a first review pass is overwhelming and demoralizing, especially for junior developers. Even if every individual comment is valid, the cumulative effect reads as "this entire PR is garbage and so are you."

💡 The Letter Grade Approach (mtlynch)

Privately rate the PR from A to F. If it's a D, help the author get to a C or B−, not an A+. A D → A+ journey takes 8 rounds of review. By the end, the author never wants to send you code again. The goal is incremental improvement over time, not perfection in one pass.

🧨 Toxic Behavior #3: Scope Creep Used as Power

Blocking a PR because of pre-existing problems the author didn't cause is a form of hostage-taking. The rule: if it was broken before this PR, it should be tracked in a separate ticket — not used to block an unrelated change.

🧨 Toxic Behavior #4: Sarcasm and Condescension

❌ Corrosive "Another O(n²) loop. Classic."

"I can't believe this passed linting."

"This is... interesting design."
✅ Constructive "This nested loop is O(n²) — for large data sets that's a concern. A Map-based approach would bring it to O(n)."

"Looks like the linting rule for X isn't catching this. Shall I flag it in our config?"

🧨 Toxic Behavior #5: Judgmental "Why" Questions

❌ Accusatory "Why didn't you just use the existing utility function?"

"Why is this so complicated?"
✅ Curious "There's an existing utility function formatDate() that does something similar — would that work here, or is there a reason this needs a custom implementation?"

"I'm having trouble following this logic — could we break it into smaller functions or add some comments to help future readers?"
🚨 Why This Matters Beyond Feelings

Toxic behaviors in code reviews can be more harmful than no code review at all, because they actively stifle the qualities developers need most: creativity, confidence to try new approaches, and the willingness to ask questions. A review culture that engineers dread produces worse code than one with no reviews at all.

9. Code Reviews Like a Human (mtlynch.io)

Michael Lynch's two-part series is the most cited article in the list. Its central argument: most review guides treat code review as a purely technical process. In reality, the social dynamics determine whether a review is useful or destructive.

High-Level Before Low-Level

Don't review style nits in round one if there are architectural problems to discuss. Your low-level notes may become completely moot once the author addresses the high-level design feedback. Sequence your rounds:

  1. Round 1: Architecture, design, approach. Is this the right solution?
  2. Round 2: Logic, correctness, edge cases. Does it work correctly?
  3. Round 3: Style, naming, readability. Is it easy to maintain?

The Worst Code Review of My Life

Lynch describes receiving a first PR from a new teammate and leaving 59 comments. She never sent him code again. The lesson: even technically correct feedback, delivered all at once without empathy for context, is toxic. She was new to Python, working on a legacy codebase, and 59 notes was not a teaching moment — it was a wall.

Frame Feedback as Collaboration

The best reviewers don't position themselves as gatekeepers approving or rejecting work. They position themselves as a collaborator helping polish shared code. Language choices matter enormously here:

❌ Gatekeeper Frame "I'm not approving this until X is fixed."

"This needs to be completely rewritten."

"Missing test coverage."
✅ Collaborator Frame "This is close — just need to sort out X before we land it."

"The approach here is making this complex. What if we tried Y instead? Here's a quick sketch."

"Test coverage for the error path would make this much safer to iterate on. Want me to add an example test?"

When to Meet Synchronously

If a thread has gone 4+ messages and no consensus is emerging, stop the async discussion and schedule a 10-minute call. Text communication strips out tone, context, and body language. A short conversation resolves in minutes what text threads drag on for days. After the meeting, post a comment summarizing the decision made, so the PR record is complete.

10. Being a Great PR Author

Lynch's companion piece, "How to Make Your Code Reviewer Fall in Love with You," covers the author's side of the equation. Reviews are dramatically better when the author makes them easy.

Write a Great Description

A good PR description has three parts:

  • What — what does this change do at a high level?
  • Why — what problem does it solve? Why is this the right solution?
  • How to test — how can the reviewer verify this works? Any special setup?
❌ Bad PR Description

Title: "fix stuff"
Body: (empty)

✅ Good PR Description

Title: "Fix order total calculation when discount codes are stacked"

Body:
Fixes a bug where stacking two discount codes resulted in a negative total if both were percentage-based and the combined discount exceeded 100%.

Root cause: The discounts were applied sequentially to the original price rather than cumulatively on the remaining balance.

Fix: Caps the combined discount percentage at 100% before applying.

Testing: Added unit tests for single discount, stacked discounts, and the edge case of >100% combined. Can manually test by adding codes SAVE20 + SAVE90 to any order.

Review Your Own Code First

Before requesting review, open the diff as if you were the reviewer. You'll catch embarrassing issues that would otherwise waste your reviewer's time — and the act of explaining your own code often reveals design problems you didn't notice while writing it.

Respond to Feedback Gracefully

When a reviewer catches a bug, your first instinct may be to make excuses. Don't. Thank them. When someone spots a subtle logic error in well-written code, it means your PR is in good shape — the reviewer had enough clarity to find deep issues rather than surface noise.

When a reviewer is wrong, push back politely with evidence. You're both trying to write the best code possible — it's a dialogue, not a judgment.

Acknowledge Every Comment

For every comment, either make the change and mark it resolved, or reply with your reasoning. Never silently ignore a comment — the reviewer doesn't know whether you missed it, disagree, or are planning to address it later.

11. Ship Small Diffs

This is one of the most universally agreed-upon practices in all of software engineering, yet it's routinely ignored. The evidence is overwhelming:

📊 The Data

Teams that keep PRs under 200 lines ship approximately 40% more code than teams doing 200+ line PRs. The cognitive overhead of a large PR isn't just inconvenient — it measurably reduces throughput.

What Happens With Large PRs

Two failure modes, both bad:

  • Review delay — the PR is so large the reviewer keeps postponing it until they "have time." That time never comes. The PR sits for days or weeks.
  • Rubber stamp — the reviewer gets through it superficially, approves to stop the bleeding, and misses genuine bugs. The review is theater, not safety.
"Ask a programmer to review 10 lines of code, he'll find 10 issues. Ask him to review 500 lines, he'll say it looks good."

How to Split Large Work

  • Separate refactoring from feature work. Rename a function in one PR; add the new behavior in the next.
  • Use feature flags. Merge incomplete code to main behind a flag that's off in production. This unlocks continuous integration without waiting for a full feature.
  • Plan your PRs before you code. List the steps the feature requires. Most of those steps can be separate PRs.
  • Database migrations first. Add columns in one PR; write the code that uses them in the next.

What "Small" Actually Means

Small doesn't just mean few lines — it means one logical change. A PR that touches 50 files across three different concerns is hard to review even if it's only 200 lines. A PR that touches 100 lines but does one coherent thing is easy to review.

12. Stacked Pull Requests

Stacked PRs are the advanced technique for keeping diffs small when you're building a large feature that has natural sequential dependencies.

The Problem They Solve

Suppose you're building a new payments feature. It requires: a DB schema change → a data model layer → a service layer → an API endpoint → a UI component. These steps can't be parallelized, but building them all in one PR creates a massive, tangled diff that's nearly impossible to review well.

The Stacked PR Workflow

  1. Create branch fb-schema from main. Add the DB migration. Open PR #1 targeting main.
  2. While PR #1 is in review, create branch fb-model from fb-schema. Add the model layer. Open PR #2 targeting fb-schema. The diff for PR #2 only shows the model changes, not the schema.
  3. Continue stacking: fb-service from fb-model, fb-api from fb-service, etc.
  4. Merge in order: PR #1 first, retarget PR #2 to main, merge, and so on.
⚠️ The Trade-Off

Stacked PRs create rebasing complexity. If PR #1 is changed based on review feedback, all downstream branches need to be rebased. Tools like ghstack automate this. If doing it manually, agree with your team that the author owns rebasing the stack after any change to an early PR.

Benefits

  • Each PR is focused and reviewable in isolation
  • Reviewers can specialize — a DB expert reviews the schema PR; a backend engineer reviews the service PR
  • You don't block on reviews to start the next piece of work
  • A merge on any PR doesn't block deployment of that piece

13. Handling Pushback & Disagreements

Even in the best teams, reviewer and author sometimes disagree. How you handle this determines the long-term health of the review culture.

When the Author Pushes Back

First: actually consider that they might be right. They're closer to the code. If their argument makes sense from a code health perspective, drop the issue and acknowledge they were right. Reviewers who can't do this lose credibility fast.

If you still believe the change is the right one after hearing their argument, explain more clearly — not just restate your position, but address their specific concern:

💡 Good Disagreement Example

Reviewer: "This should use our standard RetryPolicy class rather than manual retry logic."

Author: "The RetryPolicy class doesn't support this timeout behavior I need."

Reviewer: "That's a fair point — I didn't realize RetryPolicy didn't support custom timeouts. Two options: (1) we could extend RetryPolicy with a timeout parameter, which benefits everyone, or (2) if the timeline is tight, we could use the custom logic now and file a ticket to generalize it. Which do you prefer?"

The "Clean It Up Later" Promise

Developers often say "I'll fix this in a follow-up PR" to unblock review. Sometimes they genuinely will. Often they won't — the next task takes priority, context is lost, and the cleanup never happens. The rule: if the cleanup is important enough to ask for, it's important enough to require before merging. If it's not important enough to block merge, accept the code as-is.

Escalation Path

If a genuine technical disagreement can't be resolved between two people:

  1. Switch to a synchronous conversation (video/voice) — text is terrible for conflict resolution
  2. Bring in a third technical opinion: a tech lead, architect, or domain expert
  3. Reference the team's documented standards — having a written style guide or architecture decision records (ADRs) is the single best way to remove personality from technical disputes

14. Building an Inclusive Review Culture

Code review culture can unintentionally exclude people — junior developers, new hires, developers from underrepresented groups, or people for whom English is not a first language. An inclusive review culture requires deliberate design.

The Confidence Gap

Experienced developers often have confidence to push back on comments they disagree with. Newer developers don't. They'll make changes they don't agree with and don't understand, learning nothing from the interaction except that reviews are unpleasant. Label your feedback clearly (Conventional Comments helps here) and explain your reasoning more, not less, for developers who are still learning.

Don't Pile On

When multiple reviewers are assigned, avoid a pile-on where everyone leaves the same feedback. Coordinate — pick a primary reviewer and have others only add what the primary missed. 15 people commenting "this needs a null check" is demoralizing even if they're all right.

Psychological Safety

If people are afraid to submit code for review — because they fear judgment, mockery, or public humiliation — they'll avoid reviews, batch their changes into massive PRs to minimize touchpoints, or leave the team. The ultimate measure of your review culture is: do people want to send you their code?

Onboarding New Members

For new developers especially, the first few reviews set expectations that last. Make them positive. Be generous with context (they don't know your conventions yet), explicit about what's blocking vs. optional, and sparing with feedback volume. One key point per round is often enough to start.

15. What Research Says

The Awesome Code Review list includes several academic papers and industry research studies. Here are the key findings:

Microsoft's Study (Bosu, Greiler, Bird — 2015)

A large-scale study at Microsoft on which code review comments developers actually find useful. Key findings:

  • Comments were most valued when they pointed to relevant expertise the author lacked
  • Vague, subjective comments ("this could be cleaner") were consistently rated as unhelpful
  • Knowledge transfer was cited as the #1 value of code review — ahead of defect detection
  • Early, frequent reviews were significantly more useful than large, infrequent ones

The Smartbear/Cisco Study

An analysis of code review data from Cisco found that:

  • Reviewers catch significantly fewer defects after 60–90 minutes of review time
  • Reviews of more than 200–400 lines of code produce significantly fewer bug findings per line
  • The sweet spot is reviewing less than 400 lines over no more than 60 minutes

Multi-Stage vs. Single-Pass Review

An early paper (Porter, Siy, Toman & Votta, 1997) tested multi-stage reviews (multiple passes with different focuses) vs. single offline pass with two reviewers. The finding: you can get most of the benefit of elaborate multi-stage review in a single pass with two reviewers. More elaborate processes don't yield proportionally more value.

What Good Comments Look Like (in Data)

Comments that were consistently rated useful had these characteristics:

  • Specific — pointed to a concrete problem, not a vague pattern
  • Actionable — suggested a clear path to resolution
  • Educational — explained the "why" not just the "what"
  • Delivered quickly — value drops dramatically with time

16. Automation: Let Computers Do Their Job

One of the most widely agreed-upon ideas across the entire list: automation should handle everything a computer can check, so humans can focus on things only humans can judge.

What to Automate

  • Formatting — Prettier, gofmt, rustfmt. No human should ever leave a comment about indentation.
  • Linting — ESLint, Pylint, Rubocop. Catch undefined variables, unused imports, deprecated APIs.
  • Type checking — TypeScript, mypy, Sorbet. Catch type errors before humans read the code.
  • Test execution — CI runs tests automatically. No PR should be reviewable if tests are failing.
  • Test coverage — Block merge if coverage drops below a threshold.
  • Security scanning — Tools like Snyk, Dependabot, and Semgrep catch common vulnerability patterns.
  • Code complexity metrics — Cyclomatic complexity, function length. Flag functions that are getting too long or complex.
✅ The Right Division of Labor

Automation handles: style, formatting, linting, test execution, type checking, coverage, known security patterns
Humans handle: design, logic correctness, edge cases, readability, mentorship, architectural fitness

The Cultural Shift

Setting up these tools requires an upfront investment and some initial friction (people don't like being told their formatting is wrong by a bot). But within a few weeks, style debates disappear entirely from human reviews. This is a feature, not a bug — it returns hundreds of hours per year to the team for work that actually requires human judgment.

17. The 10 Principles to Live By

01
Automate the mechanical stuff
Linters, formatters, CI. Free reviewers to think about design and logic.
02
Approve when it improves things
Don't hold out for perfection. A CL that makes the codebase better deserves to land.
03
Keep PRs small — always
One logical change per PR. If it's large, break it up. This is a skill; practice it.
04
Label your feedback clearly
Use Conventional Comments or a feedback ladder. Eliminate ambiguity about what's blocking.
05
Back opinions with evidence
Style guide, docs, benchmarks, or concrete reasoning. "I prefer" is never enough.
06
Comment on code, not the person
"This function" not "you wrote". Every single time. No exceptions.
07
Ask questions, don't issue commands
"What would you think about..." opens collaboration. "Do this." closes it.
08
Praise good work genuinely
It motivates, builds psychological safety, and models the behaviors you want to see.
09
When stuck, talk
Async threads spiral. A 10-minute call resolves what 30 comment replies couldn't.
10
Respond within one business day
Most complaints about code review are really complaints about speed. Be fast.
