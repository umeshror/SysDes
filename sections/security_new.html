Encryption: In Transit vs. At Rest vs. In Use

Type What It Protects How Tools
In Transit Data moving over network TLS 1.2/1.3 (mandatory), mTLS for service-to-service Let's Encrypt, AWS ACM, Istio mTLS
At Rest Data stored on disk, in DB, in S3 AES-256 server-side encryption (SSE), full-disk encryption AWS KMS, S3-SSE, db-level TDE (Transparent Data Encryption)
In Use Data while being computed (cutting edge) Homomorphic encryption, trusted execution environments (Intel SGX) AWS Nitro Enclaves, Azure Confidential Computing
End-to-End (E2E) Data from sender to recipient — not even servers can read Client-side encryption with user-controlled keys Signal Protocol, WhatsApp, iMessage
TLS 1.3 vs TLS 1.2
TLS 1.3 (2018) eliminates the round-trip in the handshake: 1-RTT instead of 2-RTT for new connections, and 0-RTT session resumption (at slight security cost). It also removes weak ciphers (RC4, SHA-1, RSA key exchange). Google found TLS 1.3 reduced connection setup latency by ~20ms on average. All new systems should require TLS 1.3 minimum.
Key Management: The Hard Part
Encrypting data is easy. Managing keys securely at scale is hard. Gold standard: use a Hardware Security Module (HSM) — a tamper-resistant chip that stores root keys and never exposes them. AWS CloudHSM and AWS KMS (backed by HSMs) handle this. Keys should be rotated regularly. Never store encryption keys in the same system as the encrypted data.

Password Hashing: bcrypt vs. Argon2
Never store plain-text passwords. Never use MD5 or SHA-256 alone (too fast — GPU can crack billions/sec). Use bcrypt (work factor 12–14), scrypt, or Argon2id (winner of Password Hashing Competition 2015). Argon2id is memory-hard — costs GB of RAM to compute, making GPU/ASIC attacks impractical. bcrypt at work_factor=12 takes ~250ms per hash on a server — slow enough to prevent dictionary attacks, fast enough for legitimate logins.
JWT (JSON Web Tokens) Trade-offs
JWTs are stateless — the server doesn't need a DB lookup to validate a request. The downside: you can't invalidate a JWT before expiry without a blocklist (which adds a DB lookup back). Mitigation: use short expiry (15 minutes) for access tokens + long-lived refresh tokens (stored in DB, revocable). This is the standard OAuth 2.0 pattern.
mTLS for Service-to-Service Auth
In microservices, services must authenticate each other, not just users. mTLS (mutual TLS) requires both client and server to present certificates. A service mesh (Istio) does this automatically via short-lived SPIFFE certificates (rotated every 24 hours). No API keys in config files. This is how Google's BeyondCorp zero-trust network works internally.

Authorization: RBAC vs. ABAC vs. ReBAC

Model Logic Pros Cons Used By
RBAC (Role-Based) User has Role → Role has Permissions Simple, auditable Role explosion at scale (1000s of roles) AWS IAM roles, most enterprise apps
ABAC (Attribute-Based) Access decided by user/resource/env attributes Fine-grained, context-aware Complex policies, hard to audit AWS IAM policies, XACML systems
ReBAC (Relationship-Based) Access based on graph of relationships Natural for social/sharing models Complex graph queries Google Zanzibar, GitHub, Notion
Google Zanzibar: The Authorization System Powering Gmail, Drive, Docs
Google's Zanzibar (published 2019) handles 10 million authorization checks per second globally, with <10ms p95 latency. It stores relationships as tuples: (object, relation, user) — e.g., (doc:42, viewer, user:alice). Arbitrary graph traversal lets you answer: "Can Alice view Doc 42?" by following relationship chains. Open-source implementations: OpenFGA, SpiceDB, Permify, Cerbos.

Zero Trust Architecture

Traditional security: "Trust everything inside the network perimeter." Zero Trust: "Never trust; always verify." The network perimeter is dead — endpoints are mobile, services run in shared clouds, insiders can be attackers.

Google BeyondCorp
Google implemented zero trust internally after the Aurora attacks (2010). All employee access is granted based on device certificate (is this a managed Google laptop?) + user identity (is this the right person?) + policy (does this person's role allow this resource?). No VPN required — engineers access internal tools directly from any network. The model is now the basis for Google Cloud's BeyondCorp Enterprise product.
OWASP Top 10 and System Design
When asked about security in a system design interview, cover: (1) Injection: parameterized queries, not string concatenation; (2) Broken Auth: short-lived tokens, MFA, rate limit login attempts; (3) Sensitive Data Exposure: encrypt at rest and in transit, no PII in logs; (4) SSRF: validate and whitelist outbound URLs in services that fetch URLs; (5) Rate limiting + DDoS: CDN-level (Cloudflare) + application-level (token bucket per IP/user).
