Forward Proxy vs. Reverse Proxy

flowchart LR subgraph Forward Proxy C1[Client] --> FP[Forward Proxy\ne.g. Squid, VPN] FP --> I[Internet / Server] style FP fill:#4a4a8a,color:#fff end subgraph Reverse Proxy C2[Client] --> RP[Reverse Proxy\ne.g. Nginx, Cloudflare] RP --> S1[Server A] RP --> S2[Server B] style RP fill:#2d6a4f,color:#fff end

Forward Proxy

  • Client-side intermediary — client is aware of it
  • Hides the client's identity from the destination server
  • Enforces outbound access policies (egress filtering)
  • Caches outbound responses for bandwidth savings
  • Used in: corporate networks, schools, VPNs, Tor

Real-world: Squid Proxy, Charles Proxy (debug mobile traffic), Privoxy

Reverse Proxy

  • Server-side intermediary — client doesn't know backend topology
  • Hides server identity — clients see one IP/domain
  • SSL/TLS termination (offload crypto from app servers)
  • Load balancing, health checks, failover
  • Static asset caching, compression, DDoS mitigation

Real-world: Nginx, Cloudflare, AWS ALB, Traefik, HAProxy, Varnish

Nginx as a Reverse Proxy: What It Actually Does

SSL/TLS Termination
Nginx handles the expensive HTTPS handshake and decryption. Requests flow internally as plain HTTP. This keeps TLS certificates centralized and removes crypto load from app servers. A single Nginx instance can handle ~10,000 TLS connections/sec on commodity hardware.
Connection Pooling (Keepalive)
Nginx maintains a pool of persistent connections to upstream app servers (upstream keepalive). Without this, each proxied request requires a new TCP handshake to the backend — 3-way handshake adds ~0.5–2ms per request. With keepalive, the connection is reused: ~0.05ms overhead.
Request Buffering
Nginx fully buffers slow client uploads before forwarding to the app server. This prevents "slow client" attacks from tying up app server threads. The app server sees a fast, complete request — not a slow trickle.
Static File Serving
Nginx serves static files at ~50–100K RPS from disk with sendfile() syscall (zero-copy, kernel-level). App servers (Node.js, Python) max out at ~5K RPS for static files. Always offload statics to Nginx or CDN.

Service Mesh: The Sidecar Proxy Pattern

In a microservices architecture, a service mesh deploys a lightweight reverse proxy (sidecar) beside every service instance. The sidecar handles all network traffic — the app doesn't need to implement retries, mTLS, circuit breaking, or observability itself.

flowchart LR subgraph Pod A A[Service A] <--> SA[Sidecar\nEnvoy] end subgraph Pod B B[Service B] <--> SB[Sidecar\nEnvoy] end SA <-->|mTLS\nretry\ntracing| SB CP[Control Plane\nIstion / Linkerd] -.->|config| SA CP -.->|config| SB
What the sidecar (Envoy) provides:
  • mTLS — automatic mutual TLS between services (zero trust)
  • Circuit breaking — stop sending to failing upstreams
  • Retries with jitter — configurable retry policies
  • Distributed tracing — propagates trace headers automatically
  • Traffic splitting — canary/blue-green at the network layer
Performance cost of a sidecar:
Envoy adds ~0.2–0.5ms per hop and ~10–15MB RAM per instance. At Lyft scale (Envoy's origin), this overhead is worth the security and observability gains. At small scale (<20 services), a service mesh may be overkill.
Real-world: Lyft, Airbnb, Google
Lyft created Envoy in 2015 because their service-to-service communication had no visibility. Airbnb runs SmartStack (their own service mesh). Google invented gRPC and builds products with their own internal mesh (Traffic Director). Netflix uses Zuul as an edge proxy and Eureka for service discovery — a form of mesh without a dedicated sidecar.

Proxy Use Cases in FAANG System Design Interviews

When to mention proxy in your design
  • Any public-facing API: mention reverse proxy for TLS termination, rate limiting, and DDoS protection at the edge (Cloudflare/CDN)
  • Microservices: mention service mesh (Istio/Envoy) for mTLS, circuit breaking, and distributed tracing without app code changes
  • Database connections: mention a connection proxy (PgBouncer for PostgreSQL, ProxySQL for MySQL) to pool thousands of app connections into tens of DB connections
  • Multi-cloud / egress: forward proxy for controlling which external APIs services can call
PgBouncer — The Database Connection Proxy
PostgreSQL creates a new OS process per connection (~5–10MB RAM each). A Node.js app with 100 instances × 10 connection pool = 1,000 connections = 10GB RAM just for idle connections. PgBouncer sits in front of Postgres and multiplexes thousands of app connections onto ~20–50 actual DB connections. Transactions are serialized through the real connections. Shopify runs PgBouncer in front of all their PostgreSQL clusters. Result: DB can scale to 10K+ app instances without adding more DB connections.
