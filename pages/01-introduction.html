Introduction to System Design

Module 1  |  5 topics

What is System Design?

System design is the process of defining the architecture, components, modules, interfaces, and data flow of a system to satisfy specified requirements. It bridges the gap between a product specification and its implementation.

At its core, system design asks: given that millions of users need to do X, how do we build software that is fast, reliable, cost-effective, and maintainable?

Why System Design Matters

  • Scale: A design that works for 100 users usually fails at 100 million users. Choices made early — how you store data, how you split components — become load-bearing walls.
  • Cost: Poor design wastes compute, storage, and engineering time. A well-designed cache can cut database costs by 90%.
  • Resilience: Real systems fail. Good design contains failures rather than letting them cascade.
  • Maintainability: Code is read and modified far more than it is written. Design shapes how easy that is.

The System Design Process

  1. Requirements clarification — functional requirements (what it does) vs non-functional (how well it does it: latency, availability, consistency).
  2. Capacity estimation — estimate traffic, storage, and bandwidth needs.
  3. High-level design — sketch major components and their relationships.
  4. Detailed design — deep-dive critical subsystems.
  5. Identify bottlenecks — single points of failure, hotspots, scaling walls.
  6. Tradeoff discussion — no design is perfect; articulate what was sacrificed.

What is a System Design Interview?

A System Design Interview (SDI) is a technical conversation about how to build a large-scale system. Unlike coding interviews, there is no single "correct" answer. The interviewer is assessing your ability to handle ambiguity, make informed trade-offs, and design for scalability and reliability.

Focus Areas
  • Scalability: Can the system handle 10x or 100x more traffic?
  • Architecture: How are components organized and how do they interact?
  • Trade-offs: Why choose X over Y? (e.g., SQL vs NoSQL)
  • Problem Solving: How do you handle edge cases and failures?

Functional vs. Non-functional Requirements

Before designing anything, you must define the scope. This is split into two categories:

Functional Requirements

What the system must do. Features and behaviors.

  • "Users can upload photos."
  • "Users can follow each other."
  • "The system generates a news feed."

Non-functional Requirements

How the system performs. Constraints and qualities.

  • Scalability: Handle 10M daily active users.
  • Availability: 99.9% uptime (Highly available).
  • Latency: Feed generation under 200ms.
  • Consistency: Eventual vs strong consistency.

What are Back-of-the-Envelope Estimations?

These are quick, approximate calculations used to assess if a design is feasible within given constraints. They help determine the scale of the system (e.g., "Do we need 1 server or 1000?").

Common Units to Know
  • 1 Trillion requests/day ≈ 12 Million requests/sec
  • 1 GB = 109 bytes
  • Latency: Memory (100ns) vs SSD (100µs) vs Disk (10ms) vs Network (150ms).

Things to Avoid During System Design Interview

  • Skipping Requirements: Never start designing without clarifying the goal.
  • Ignoring Trade-offs: Don't just pick a technology because it's popular; explain why.
  • Poor Communication: Don't go silent. Think out loud and engage the interviewer.
  • Rigid Thinking: If the interviewer suggests a flaw, be open to adjusting your design.
  • Diving Too Deep Early: Don't design the database schema before the high-level architecture.
