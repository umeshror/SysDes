Load Balancing

Module 5  |  Distributing Traffic, Health Checks, and Layer 4 vs Layer 7

L4 vs. L7 Load Balancing

Layer 4 (Network/Transport)

  • Routes based on IP + TCP/UDP port only
  • No inspection of HTTP headers, URL, cookies
  • Extremely fast: <0.1ms overhead, millions of conn/sec
  • Stateful TCP connections — single server per connection

Use: Raw throughput needs, non-HTTP protocols (gRPC, databases, gaming)

Examples: AWS NLB, HAProxy TCP mode, hardware F5 BIG-IP

Layer 7 (Application)

  • Reads HTTP headers, URL paths, cookies, request body
  • Route /api/* to one server group, /static/* to another
  • Sticky sessions via cookie (SERVERID)
  • Header rewriting, request/response transformation
  • WebSocket and HTTP/2 multiplexing aware

Use: Web apps, microservices, content-based routing, canary deployments

Examples: AWS ALB, Nginx, Envoy, Traefik, HAProxy HTTP mode

Load Balancing Algorithms

flowchart LR subgraph Round Robin C1[Request 1] --> S1[Server A] C2[Request 2] --> S2[Server B] C3[Request 3] --> S3[Server C] C4[Request 4] --> S1 end subgraph Least Connections C5[New request] --> L{Who has\nfewest active\nconnections?} L -->|"A:10, B:2, C:7"| S2b[Server B\n2 conns] end subgraph Weighted Round Robin C6[4 requests] -->|2 go here| SA[Server A\nweight=2] C6 -->|1 goes here| SB[Server B\nweight=1] C6 -->|1 goes here| SC[Server C\nweight=1] end
Algorithm Best For Limitation
Round Robin Uniform request cost, stateless services Bad if some requests take 100× longer than others
Weighted Round Robin Heterogeneous hardware (some servers have more CPU) Weights need manual tuning as load changes
Least Connections Highly variable request duration (file uploads, slow queries) Doesn't account for server CPU/RAM, only connection count
Least Response Time When response time is the key metric Requires active health probing — small overhead per server
IP Hash (Sticky) Stateful apps where session state lives on server Hash may be skewed (all users behind one corporate IP)
Random with Two Choices (P2C) Large distributed clusters, proven theoretically optimal Slightly more complex implementation
Power of Two Choices (P2C) — The Modern Standard

Pick 2 random servers, route to the one with fewer connections. Theoretically proven to reduce max load from O(log N / log log N) (round robin) to O(log log N) — a dramatic improvement at scale. Used by Nginx Plus, HAProxy (with random selection), and most modern service meshes. Netflix uses a variant they call "Hysteresis" which also weighs recent response latency.

Health Checks: Active vs. Passive

Active Health Checks

  • LB periodically probes each backend (HTTP GET /health every 5s)
  • Detects failure BEFORE a real user request fails
  • Costs some bandwidth and server resources
  • Checks should test real dependencies: DB connection, cache reachability

Passive Health Checks

  • Monitor actual traffic responses for failures (5xx, timeouts)
  • Zero overhead when healthy
  • At least one real user sees the error before the server is marked down
  • Good complement to active checks
Health check endpoint best practices
A good /health endpoint: (1) returns 200 only if all critical dependencies are reachable; (2) returns the check results as JSON for debugging; (3) completes in <500ms; (4) never logs at INFO level (it's called every 5 seconds — logs would drown real application logs). Kubernetes distinguishes liveness (is the app running?) from readiness (is the app ready to serve traffic?). Never combine these — a slow DB shouldn't kill a pod.
AWS ALB at FAANG scale
AWS ALB (Application Load Balancer) handles Layer 7 routing for millions of AWS customers. It auto-scales to handle sudden traffic spikes without any pre-warming (unlike the legacy Classic LB, which needed pre-warming requests). Internally, ALB nodes themselves are behind a Network Load Balancer for multi-AZ distribution. ALB supports: weighted target groups (canary), Lambda as a target (serverless backends), gRPC, and WebSocket protocol upgrades.

Global Load Balancing: DNS-Based vs. Anycast

flowchart LR U[Global Users] --> DNS[DNS-based GSLB\ne.g. Route53 Geolocation] DNS --> R1[us-east-1\nALB] DNS --> R2[eu-west-1\nALB] DNS --> R3[ap-southeast-1\nALB] U --> ANY[Anycast IP\ne.g. Cloudflare] ANY --> E1[NYC edge] ANY --> E2[London edge] ANY --> E3[Singapore edge]
DNS-based GSLB (e.g., AWS Route 53)
Route 53 returns different IPs based on the user's geographic origin. Users in Europe get the EU ALB's IP. Limitation: DNS TTL means failover takes 60–300 seconds (users may have cached the old IP). Use Route 53 Health Checks + low TTL (60s) to speed up failover.
Anycast (Cloudflare, Akamai)
All edge PoPs advertise the same IP address. BGP routing directs each user to the nearest PoP automatically. Failover is near-instantaneous — BGP re-converges in seconds when a PoP goes down. DDoS attacks are automatically spread across all PoPs (absorptive capacity).

Caching Architecture

Module 5  |  Cache Hierarchies, Eviction Policies, and Cache Stampede Mitigation

The Cache Hierarchy at Scale

flowchart LR C([Client]) --> B[Browser Cache\n0ms] B --> CDN[CDN Edge\n10–30ms] CDN --> LMem[In-process Cache\n<0.1ms] LMem --> Redis[Redis / Memcached\n0.5–2ms] Redis --> RR[Read Replica\n2–10ms] RR --> W[(Primary DB)]
The 80/20 Rule of Caching

In most read workloads, 80% of reads hit 20% of the data (Pareto principle). Caching that 20% (the "hot set") eliminates 80% of your DB load. Identify your hot set with a read-frequency histogram. Start with a small cache (even 1% of your data may be enough to capture 80% of reads).

Cache Eviction Policies

Policy Evicts Implementation Best For
LRU (Least Recently Used) Item not accessed most recently Doubly-linked list + hash map; O(1) get/put Most workloads — temporal locality common
LFU (Least Frequently Used) Item accessed fewest times Min-heap or frequency buckets Stable popular content (videos, docs)
TTL (Time-To-Live) Item after a fixed time window Heap ordered by expiry; passive or active sweep Any time-sensitive data (sessions, API responses)
SLRU (Segmented LRU) LRU from probation segment only Two LRU queues: protected + probation Scan-resistant (batch operations shouldn't flush popular items)
W-TinyLFU (Window Tiny LFU) Low-frequency items, sketch-based Frequency sketch (Count-Min) + LRU window Production highest hit-rate; used by Caffeine (Java)
Random Random item O(1) trivial Uniform access patterns (rare); used by CPU TLBs
Why Redis uses LRU (with approximation)
True LRU on every access requires updating a linked list — expensive at Redis's million ops/sec throughput. Redis uses approximated LRU: sample N random keys (default: 5) and evict the one with the oldest last-access time. This gives ~95% of the hit rate of true LRU at a fraction of the CPU cost. Redis 4.0+ introduced LFU policy as an alternative — better for access-pattern-stable datasets.

Cache Problems and Solutions

Cache Stampede (Dog-Piling)

A cached item expires. Simultaneously, 10,000 requests arrive and all miss the cache. All 10,000 go to the DB simultaneously. The DB is overwhelmed.

Solutions:

  • Probabilistic early recomputation: Re-cache slightly before expiry with probability proportional to time-to-expiry. One request rebuilds while others still serve the old value.
  • Mutex/lock: First miss acquires a distributed lock, recomputes, populates cache. Others wait then hit the warm cache.
  • Stale-while-revalidate: Serve stale data; one background thread recomputes. No stampede possible.

Cache Penetration

Requests for keys that never exist in DB or cache bypass the cache on every request, hammering the DB. Classic DDoS vector: query non-existent user IDs.

Solutions:

  • Cache null results: Cache user:99999 → NULL with a short TTL. Future misses are cache hits.
  • Bloom Filter: In-memory probabilistic set membership. If Bloom Filter says "definitely not in DB," skip DB entirely. Instagram uses Bloom Filters for non-existent user lookups.

Cache Avalanche

All cached items expire at the same time (e.g., everything was set with TTL=3600 at 9am → all expire at 10am). Massive cache miss simultaneously.

Solutions:

  • Jitter TTL: TTL = base_ttl + random(0, base_ttl * 0.2). Spreads expiry across time.
  • Layered TTL: Different cache tiers with different TTLs prevent all-at-once expiry.

Cache Coherence

Multiple caching nodes holding different versions of the same data.

Solutions:

  • Write-through: Update cache and DB atomically on every write.
  • Event-driven invalidation: Write → Kafka event → cache invalidation subscriber.
  • TTL-based convergence: Accept brief inconsistency; short TTL bounds staleness.

Redis Deep Dive

Redis is single-threaded but fast
Redis processes commands in a single thread (+ I/O threads in Redis 6+). No locking contention. All operations are O(1) or O(N) on data structure size — predictable latency. ~100K–1M ops/sec per node (benchmark: redis-benchmark -n 1000000). Max RAM: limited to server memory. Typical: 16–128GB instances in production. At Twitter: 8,000+ Redis instances managing session data, rate limits, and real-time counters.
Redis Cluster for horizontal scaling
Redis Cluster shards keyspace into 16,384 slots across N primary nodes. Each primary has 1+ replicas. Clients use cluster-aware libraries (redis-py, Jedis cluster mode) that route to the correct shard. Resharding is online — no downtime. Redis Cluster handles ~1 million ops/sec across a 6-node cluster (3 primary + 3 replica).
Redis Persistence: RDB vs. AOF
RDB (snapshot): Point-in-time snapshot every N minutes. Fast recovery, smaller files. Data loss: up to N minutes of writes. Good for: cache (some data loss acceptable).
AOF (Append-Only File): Every write command logged. Recovery by replaying log. Can sync every write (fsync=always: zero data loss, low throughput) or every second (fsync=everysec: max 1s loss, high throughput). Good for: session store, pub/sub, durable cache.
Hybrid: AOF + RDB — fast load from RDB, then replay AOF tail. Default in Redis 7+.

Object Storage: S3 Architecture & Design Decisions

Amazon S3 is one of the most studied distributed systems. Understanding how it works reveals fundamental distributed storage patterns.

Key-Value Namespace
S3 objects are stored by a flat key (e.g., photos/user42/profile.jpg). There are no real directories — the "/" is just part of the key name. S3 partitions the keyspace by prefix hash, so keys with the same prefix go to the same partition. Implication: If you name all keys with a date prefix (2024-01-15-image.jpg), all January keys hit the same partition → hot partition. Add a random prefix hash to distribute: a7f3/2024-01-15-image.jpg.
Durability: 11 Nines (99.999999999%)
S3 achieves this by storing data in multiple AZs using erasure coding. An object is split into chunks and encoded with parity such that it can be reconstructed even if multiple chunks are lost. This is far cheaper than 3× full replication while providing stronger durability.
Eventual Consistency (Historically) → Strong Now
Until 2020, S3 offered only eventual consistency for LIST operations — a PUT followed immediately by GET/LIST might not return the new object. AWS moved S3 to strong read-after-write consistency in December 2020, at no performance cost. A key lesson: eventual consistency can sometimes be eliminated without sacrificing performance if the architecture allows it.
S3 Pricing Levers
S3 Standard ($0.023/GB) → S3-IA ($0.0125/GB) → S3 Glacier ($0.004/GB) → S3 Glacier Deep Archive ($0.00099/GB). Lifecycle policies auto-tier objects. Netflix saves ~$20M/year by tiering old content to Glacier.

Block Storage Internals (EBS)

flowchart LR EC2[EC2 Instance] -->|NVMe over\ntransport| EBS[EBS Volume\nSSD-backed] EBS --> R1[Replica 1\nSame AZ] EBS --> R2[Replica 2\nSame AZ] EBS -.->|Snapshot| S3[(S3 Object Store\nCross-AZ durability)]
EBS vs. Instance Store
EBS: Network-attached, persistent. Volume survives instance termination. Max: 64TB, 256K IOPS (io2 Block Express). Costs money.
Instance Store (ephemeral): Physically attached NVMe — millions of IOPS with <100μs latency. Wiped on instance stop/terminate. Used for: Kafka broker local logs, database temp files, cache warmer. Free (included in instance price).
IOPS vs. Throughput on EBS
IOPS (I/O operations/second) matters for random I/O (OLTP databases — many small reads/writes). Throughput (MB/s) matters for sequential I/O (Kafka, video encoding, log tailing). A gp3 EBS allows you to independently configure both: up to 16,000 IOPS and 1,000 MB/s on the same volume.

Choosing the Right Storage

flowchart TD Q1{What type of data?} --> D[Database rows\nindexes] Q1 --> B[Binary blobs\nimages video files] Q1 --> C[Structured logs\napp state] D --> DB[Block Storage\nEBS / local SSD\nMount as DB data dir] B --> OBJ[Object Storage\nS3 / GCS\nHTTP GET by key] C --> MIX{Access pattern?} MIX -->|Sequential read| OBJ2[Object Storage\nor append log] MIX -->|Random access| DB2[Block Storage\nor KV store]
FAANG Design Principle: Separate Compute and Storage

Modern cloud-native systems separate compute (stateless, ephemeral) from storage (persistent, separate tier). This enables independent scaling — add more compute without adding more storage, and vice versa. Databricks, Snowflake, and BigQuery all run compute in one layer and store data in S3/GCS — this is the "lakehouse" architecture and is how FAANG handles exabyte-scale analytics without buying dedicated storage hardware.
