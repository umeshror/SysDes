API Design

Module 6  |  What is an API · Idempotency · Data Formats · REST · GraphQL · gRPC

What is an API?

An API (Application Programming Interface) is a defined contract that specifies how software components should communicate. In the context of system design, APIs define how clients (web browsers, mobile apps, other services) interact with servers. A well-designed API is consistent, predictable, secure, and versioned.

API Design Principles

  • Consistency: Naming conventions, error formats, and response structures should be uniform across all endpoints.
  • Backward compatibility: Existing clients must not break when the API evolves. Add fields, do not remove them. Version breaking changes.
  • Least surprise: Behavior should match what the name and documentation imply.
  • Proper error responses: Return informative error codes and messages, not generic 500 errors.
  • Security by default: Authenticate and authorize all sensitive endpoints. Validate all input.

Idempotency

An operation is idempotent if performing it multiple times produces the same result as performing it once. This is critical for reliability: in distributed systems, network failures can cause clients to retry requests without knowing if the original succeeded.

HTTP Method Idempotency

Method Idempotent Safe (read-only) Notes
GET Yes Yes Read only, no side effects
HEAD Yes Yes Like GET, returns only headers
OPTIONS Yes Yes Describes allowed methods
PUT Yes No Replace resource; same payload → same result
DELETE Yes No Delete twice → still deleted (may return 404 on second)
POST No No Creates new resource each time
PATCH Not always No Depends on implementation

Idempotency Keys

For non-idempotent operations (like POST to create a payment), clients can include an idempotency key — a unique identifier for the request. The server stores the key and the result of the first execution. If the same key is received again, the server returns the stored result without re-executing.

POST /api/payments HTTP/1.1
Idempotency-Key: a8098c1a-f86e-11da-bd1a-00112444be1e
Content-Type: application/json

{ "amount": 99.99, "currency": "USD", "card": "tok_visa" }

Server implementation:

def create_payment(idempotency_key, payload):
    # Check if this request was already processed
    cached = redis.get(f"idem:{idempotency_key}")
    if cached:
        return json.loads(cached)   # Return stored result

    # Process for the first time
    result = payment_processor.charge(payload)

    # Store result keyed by idempotency key (TTL = 24 hours)
    redis.setex(f"idem:{idempotency_key}", 86400, json.dumps(result))
    return result

API Architectural Styles

Different API paradigms make different tradeoffs between flexibility, performance, simplicity, and tooling.

REST API Design

REST (Representational State Transfer) is an architectural style that uses HTTP methods and URLs to create a uniform interface for accessing and manipulating resources. REST is stateless — each request contains all information needed to process it.

REST Constraints

  • Stateless: Server holds no session state. All state is in the request.
  • Uniform interface: Resources identified by URIs; resources manipulated through representations; self-descriptive messages; HATEOAS.
  • Layered system: Client cannot tell whether it's communicating with an origin server or a middleman (cache, load balancer).
  • Cacheable: Responses must indicate if they are cacheable.

Resource-Based URL Design

# Resources are nouns, not verbs
GET    /users              — List users
GET    /users/123          — Get user 123
POST   /users              — Create user
PUT    /users/123          — Replace user 123
PATCH  /users/123          — Partially update user 123
DELETE /users/123          — Delete user 123

# Nested resources for relationships
GET    /users/123/orders   — Orders belonging to user 123
POST   /users/123/orders   — Create order for user 123
GET    /users/123/orders/456 — Specific order for specific user

# Avoid verbs in URLs:
POST /users/123/activate   — Acceptable for actions with no resource representation
GET  /search?q=term        — Query parameters for filtering/searching

REST API Best Practices

  • Use plural nouns for collections (/users, not /user)
  • Return appropriate HTTP status codes (201 for created, 204 for no content)
  • Provide pagination for list endpoints (?page=2&limit=20 or cursor-based)
  • Version your API (/api/v1/ or Accept: application/vnd.api+json;version=1)
  • Return consistent error format with machine-readable error codes
  • Use HTTPS always

GraphQL Deep Dive

GraphQL is a query language for APIs and a runtime for executing those queries. Rather than exposing a collection of fixed endpoints that return predetermined data shapes, GraphQL exposes a single endpoint where clients specify exactly what data they need using a typed query language.

Core Problems GraphQL Solves

  • Over-fetching: REST endpoints return a fixed data shape. Fetching GET /users/123 returns all user fields even if you only need name and email.
  • Under-fetching (N+1 requests): Getting a list of posts with each author's name requires one request for posts, then one per post for author details.
  • Client-specific data requirements: Mobile and web clients may need different subsets of data but REST uses the same endpoint for both.
# Single GraphQL query — client specifies exactly what it needs
query {
  user(id: "123") {
    name
    email
    recentOrders(limit: 5) {
      id
      total
      status
      items {
        productName
        quantity
      }
    }
  }
}

# Server returns exactly this structure — no more, no less

GraphQL Schema

GraphQL APIs are strongly typed. The schema defines all types, queries, mutations, and subscriptions, and serves as a contract between client and server. Introspection allows clients to query the schema itself, enabling powerful tooling (auto-generated documentation, type-safe client code).

type User {
  id: ID!
  name: String!
  email: String!
  orders(limit: Int = 10): [Order!]!
}

type Order {
  id: ID!
  total: Float!
  status: OrderStatus!
  items: [OrderItem!]!
}

enum OrderStatus { PENDING PROCESSING SHIPPED DELIVERED }

type Query {
  user(id: ID!): User
  users(page: Int, limit: Int): [User!]!
}

type Mutation {
  createUser(name: String!, email: String!): User!
  updateOrder(id: ID!, status: OrderStatus!): Order!
}

type Subscription {
  orderStatusChanged(orderId: ID!): Order!
}

Tradeoffs

Advantages

  • Client fetches exactly what it needs — no over/under-fetching
  • Single endpoint simplifies API versioning
  • Strong typing catches client/server mismatches at build time
  • Introspection enables self-documenting APIs
  • Subscriptions provide real-time capability

Challenges

  • HTTP-level caching is harder (single endpoint, complex queries)
  • N+1 query problem if not handled with DataLoader batching
  • Complex queries can be expensive — need query cost analysis and rate limits
  • Steeper learning curve than REST
  • Not ideal for simple CRUD APIs where REST is simpler

gRPC Deep Dive

gRPC is a high-performance, open-source remote procedure call framework developed by Google. It uses Protocol Buffers as its interface definition language and data serialization format, and HTTP/2 as its transport protocol.

Protocol Buffers

Protocol Buffers (protobuf) define the service contract and message types in a .proto file. Code generators produce client and server stubs in many languages. The binary encoding is typically 3–10x smaller than equivalent JSON and serialization/deserialization is significantly faster.

syntax = "proto3";

service UserService {
  rpc GetUser (GetUserRequest) returns (User);
  rpc ListUsers (ListUsersRequest) returns (stream User);
  rpc CreateUser (CreateUserRequest) returns (User);
  rpc StreamUserActivity (ActivityRequest) returns (stream Activity);
}

message User {
  string id = 1;
  string name = 2;
  string email = 3;
  google.protobuf.Timestamp created_at = 4;
}

message GetUserRequest {
  string id = 1;
}

Resilience Patterns: The Circuit Breaker

Named after the electrical circuit breaker: when a downstream service is failing, stop sending requests to it (open the circuit) to prevent cascading failures and allow it time to recover.

stateDiagram-v2 [*] --> Closed Closed --> Open: Failure threshold\nexceeded (e.g. 50% in 10s) Open --> HalfOpen: After reset timeout\n(e.g. 30 seconds) HalfOpen --> Closed: Test request succeeds HalfOpen --> Open: Test request fails note right of Closed: Normal operation\nAll requests pass note right of Open: STOP sending requests\nFail fast, return fallback note right of HalfOpen: Allow one trial request\nto test recovery
Why Circuit Breakers Matter: Amazon's 2012 Outage
In 2012, an Amazon service experienced cascading failures because one upstream dependency slowed, causing callers to queue requests, exhausting thread pools, causing more timeouts, causing more requests to queue — a cascade. Circuit breakers prevent this: when the upstream is slow, fail fast immediately rather than queuing indefinitely. Fail fast = bounded latency.
Netflix Hystrix → Resilience4j
Netflix invented Hystrix for circuit breaking in their Java services. It became the industry standard. Hystrix is now in maintenance mode; Resilience4j is the successor. Polly is the .NET equivalent. At Netflix, wrapping each external call in a circuit breaker reduced cascading failures from seconds of outage to milliseconds of fallback responses. Netflix's degraded experience (low-res video, no personalization, cached recommendations) is graceful degradation via circuit breakers.
Parameters to tune
Failure rate threshold: 50% of last N calls failed → open. Slow call threshold: 50% of calls >2s → also open. Reset timeout: Try again after 30s in OPEN state. These must be tuned per service — too sensitive and you'll open on transient blips; too loose and the cascade happens before the breaker opens.

Retry Strategies: When and How to Retry

Naive Retry (DO NOT do this)

  • Retry immediately on failure, N times
  • If 100 clients all retry simultaneously → thundering herd
  • Can amplify load on an already-failing service by 100×
  • Makes cascading failures worse, not better

Exponential Backoff + Jitter (correct approach)

  • Retry delay doubles each attempt: 100ms, 200ms, 400ms, 800ms…
  • Add jitter: random ±25% to each delay to desynchronize clients
  • Cap at max delay (e.g., 30 seconds)
  • Use idempotent requests only — never retry non-idempotent (POST payments)
AWS SDKs Use Exponential Backoff + Jitter by Default

AWS's "Retry Architecture" paper (2015) showed that adding jitter reduced retry-storm magnitude by 50× compared to fixed backoff. All AWS SDKs implement this. When writing your own retry logic, use: sleep(pow(2, attempt) * 100ms + random(0, 100ms)).

Bulkhead Pattern: Isolating Failures

Named after compartments in a ship's hull — if one compartment floods, the others stay dry. In software: isolate resources (thread pools, connection pools) per downstream dependency.

Thread Pool Bulkhead
Give each downstream service its own thread pool. Service A: 20 threads. Service B: 20 threads. If Service B starts hanging, only Service B's 20 threads fill up — not all 200 shared threads. Service A continues operating normally. Without bulkheads, slow Service B fills all shared threads, making the entire application unresponsive to all requests.
Semaphore Bulkhead
Limit concurrent requests to a service with a counting semaphore (N permits). Faster than thread pool isolation, but doesn't protect against slow calls blocking the calling thread. Used for non-blocking async calls where thread pool isolation is overkill.

Timeout Hierarchy

Tier Connect Timeout Read Timeout Total Timeout Notes
Client → CDN 1–2s 10–30s — CDN has generous timeouts for slow mobile
CDN → API Gateway 100–500ms 5–15s — Behind CDN, latency is lower
API Gateway → Service 50–200ms 1–5s 600ms–5s Service must complete before this
Service → DB 50–200ms 200ms–2s 500ms–3s Short! DB calls should be <100ms
Service → Cache 10–50ms 50–200ms 100ms Very short — fall through to DB on timeout
Always Set Timeouts

A service with no timeout is a thread leak waiting to happen. Without timeouts, every slow downstream call leaves a thread hanging indefinitely. With 50 API threads and a downstream taking 60s (no timeout), you'll be fully "stuck" in 50 requests. Always: connect timeout (quick failure) + read timeout (bounded wait). Also set overall request deadlines (context cancellation in Go, CompletableFuture timeout in Java) that propagate through the entire call chain.

Authentication and Authorization

Module 6  |  Authentication vs Authorization · Session vs Token · JWT · OAuth2 · SSO

Authentication vs Authorization

Authentication (AuthN)
Verifying who the entity is. Answering: "Are you really Alice?" Methods: password + username, cryptographic certificates, biometrics, hardware tokens.
Authorization (AuthZ)
Determining what the authenticated entity is allowed to do. Answering: "Alice, can you delete this resource?" Methods: RBAC, ABAC, ACLs.
Sequence

Authentication always happens before authorization. You cannot determine what someone is allowed to do until you know who they are.

Session-Based Authentication (Stateful)

The server creates and stores a session object after successful login. A session ID is sent to the client (usually as an HTTP-only cookie). On subsequent requests, the client sends the session ID; the server looks it up in the session store to retrieve user context.

Flow

  1. Client sends credentials (username + password).
  2. Server authenticates credentials against database (compare bcrypt hash).
  3. Server creates session: stores session data in Redis keyed by session ID.
  4. Server sends session ID in Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax
  5. Client sends Cookie: session_id=abc123 on every request.
  6. Server looks up session in Redis to retrieve user identity and permissions.

Token-Based Authentication (Stateless)

After successful authentication, the server issues a signed token (typically a JWT) containing claims about the user. The client stores the token and includes it in subsequent requests. The server verifies the token's signature — no server-side storage needed.

JWT — JSON Web Tokens

A JWT is a compact, URL-safe token format consisting of three Base64URL-encoded parts separated by dots: header, payload, signature.

# Structure
header.payload.signature

# Header (algorithm + type)
{ "alg": "HS256", "typ": "JWT" }

# Payload (claims)
{
  "sub": "user_123",        # Subject (user ID)
  "name": "Alice Smith",
  "role": "admin",
  "iat": 1704067200,        # Issued at (Unix timestamp)
  "exp": 1704070800         # Expiration (Unix timestamp)
}

# Signature = HMAC-SHA256(
#     base64url(header) + "." + base64url(payload),
#     secret_key
# )

JWT Verification

The server verifies the token by recomputing the signature using the secret key and comparing it to the signature in the token. If they match, the token is authentic and unmodified. The server can then extract the claims from the payload without any database lookup.

Access Token + Refresh Token Pattern

  • Access token: Short-lived (15 minutes). Used for API requests. If compromised, exposure window is small.
  • Refresh token: Long-lived (7–30 days). Stored securely (HttpOnly cookie or secure storage). Used only to obtain new access tokens. Can be revoked by deleting from database.

OAuth 2.0 / OAuth2

OAuth 2.0 is an authorization framework that enables a third-party application (client) to obtain limited access to a user's account on a service (resource server), without the user sharing their credentials with the third party.

Authorization Code Flow (Most Secure — for Web Apps with Backend)

  1. User clicks "Login with Google" on your app.
  2. Your app redirects user to Google's authorization endpoint with client_id, redirect_uri, scope, and a state parameter (CSRF protection).
  3. User logs into Google and grants permission to your app.
  4. Google redirects back to your redirect_uri with a short-lived authorization code.
  5. Your backend exchanges the authorization code for an access token and optionally a refresh token, using the client secret (server-side only — never exposed to browser).
  6. Your app uses the access token to call Google APIs on the user's behalf.

OAuth 2.0 Grant Types

Grant Type Used By Flow
Authorization Code Web apps with backend server Redirect flow with code exchange
Authorization Code + PKCE Mobile apps, SPAs Same as above with Proof Key for Code Exchange, no client secret
Client Credentials Machine-to-machine (no user) Service exchanges client_id + secret for token directly
Implicit (deprecated) Legacy SPAs Token returned in URL fragment — insecure, avoid
Device Code TV apps, CLI tools Device shows code; user authenticates on another device

Single Sign-On (SSO)

SSO allows a user to authenticate once with an Identity Provider (IdP) and then access multiple applications (Service Providers) without re-authenticating. The IdP asserts the user's identity to each application via a protocol-specific token or assertion.

SAML 2.0

Security Assertion Markup Language — XML-based enterprise SSO standard. Widely used in corporate environments (Okta, Azure AD, Ping Identity). The IdP generates a digitally signed XML assertion. The service provider validates the assertion's signature and extracts user attributes.

OpenID Connect (OIDC)

An identity layer built on top of OAuth 2.0. OAuth 2.0 was designed for authorization (access to resources); OIDC adds authentication (verifying identity) by introducing the ID Token — a JWT containing identity claims about the authenticated user.

SAML

  • XML-based assertions
  • Designed for enterprise/corporate SSO
  • Complex specification
  • Excellent legacy system support
  • Typical use: employee accessing Salesforce, Workday, Jira via corporate IdP

OIDC

  • JSON/JWT-based
  • Simpler than SAML
  • Built for web and mobile apps
  • Provider examples: Google, Apple, Auth0, Okta
  • Typical use: "Login with Google" on consumer apps

WebSockets Deep Dive

A full-duplex connection over a single TCP socket. Starts with an HTTP 101 Switching Protocols handshake.

Scaling WebSockets

Since WS is Stateful, a client is tied to a specific server. To scale, you need a Pub/Sub backplane (like Redis). When Server A wants to send a message to Client B (on Server B), it publishes to Redis, and Server B picks it up.

Server-Sent Events (SSE)

SSE is a standard HTTP mechanism for servers to push a stream of events to a client over a single long-lived HTTP connection. It is one-directional: server to client only. SSE uses the standard HTTP protocol and is therefore compatible with HTTP/2 multiplexing and most proxies.

// Server (Node.js)
app.get('/events', (req, res) => {
    res.setHeader('Content-Type', 'text/event-stream');
    res.setHeader('Cache-Control', 'no-cache');
    res.setHeader('Connection', 'keep-alive');

    const sendEvent = (data, eventType = 'message') => {
        res.write(`event: ${eventType}\n`);
        res.write(`data: ${JSON.stringify(data)}\n\n`);
    };

    const interval = setInterval(() => {
        sendEvent({ price: getStockPrice(), ts: Date.now() }, 'price');
    }, 1000);

    req.on('close', () => clearInterval(interval));
});

// Client
const source = new EventSource('/events');
source.addEventListener('price', (e) => {
    updateDisplay(JSON.parse(e.data));
});
// Auto-reconnects on disconnect with last event ID tracking

SSE vs WebSockets

SSE

  • One-way: server to client only
  • Uses standard HTTP — compatible everywhere
  • Built-in reconnection and event ID tracking
  • Text-based (UTF-8 strings)
  • Works well with HTTP/2 multiplexing
  • Best for: live feeds, notifications, dashboards

WebSockets

  • Bidirectional: both sides send
  • Custom protocol after HTTP upgrade
  • Manual reconnection logic needed
  • Binary and text support
  • Lower per-message overhead
  • Best for: chat, gaming, collaborative editing

Webhooks

Webhooks are HTTP callbacks: your server registers a URL with a third-party service; when an event occurs in that service, it sends an HTTP POST request to your URL with event data. Webhooks are server-to-server communication, not browser-based.

Key Design Considerations

  • Idempotency: The same webhook may be delivered more than once (the sender retries on network failure or timeout). Your handler must be idempotent — track processed event IDs.
  • Signature verification: The sender signs the payload with a shared secret. Always verify the signature before processing to prevent forged requests.
  • Fast response: Respond with 200 OK as quickly as possible (within 5–30 seconds, depending on provider). If processing is slow, queue the event and process asynchronously — otherwise the sender may time out and retry.
  • Failure handling: Senders typically retry with exponential backoff if they receive a non-2xx response. Return 5xx to trigger retry, not 4xx.
# Stripe webhook handler (Python/Flask)
import stripe

@app.route('/webhook/stripe', methods=['POST'])
def stripe_webhook():
    payload = request.data
    sig_header = request.headers.get('Stripe-Signature')

    try:
        event = stripe.Webhook.construct_event(
            payload, sig_header, STRIPE_WEBHOOK_SECRET
        )
    except ValueError:
        return '', 400    # Invalid payload
    except stripe.error.SignatureVerificationError:
        return '', 400    # Invalid signature

    # Idempotency: check if already processed
    if db.exists('processed_events', event['id']):
        return '', 200

    # Process asynchronously
    queue.enqueue('process_stripe_event', event)
    db.mark_processed('processed_events', event['id'])

    return '', 200    # Respond quickly

Synchronous vs Asynchronous Communication

Synchronous

The caller blocks and waits for the callee to respond before continuing. Tight coupling — if the callee is slow or down, the caller suffers.

  • Simpler to reason about (request-response pairs)
  • Immediate feedback on success or failure
  • Creates dependency chains — if payment service is slow, the order service is slow
  • Used for: user-facing operations requiring immediate response

Asynchronous

The sender dispatches a message and continues immediately. A separate process consumes and handles the message later.

  • Decouples producers and consumers
  • Resilient: messages are buffered if consumer is slow or down
  • Enables load leveling — absorb traffic spikes in the queue
  • More complex: error handling, retries, ordering, at-least-once delivery
  • Used for: background jobs, notifications, event processing

Message Queues

A message queue is a buffer that stores messages from producers until consumers are ready to process them. Producers and consumers are decoupled — they do not need to be available simultaneously.

Core Properties

  • Durability: Messages are persisted to disk. Even if the broker restarts, messages are not lost.
  • Acknowledgment: A message is not removed from the queue until the consumer explicitly acknowledges successful processing. This prevents message loss on consumer crash.
  • Ordering: Most queues deliver messages in FIFO order within a partition, though ordering guarantees vary by system.
  • Visibility timeout: When a consumer reads a message, it becomes invisible to other consumers for a period. If not acknowledged within that period, it becomes visible again (enabling retry on consumer crash).

Queue vs Stream

Aspect Traditional Queue (RabbitMQ, SQS) Log-Based Stream (Kafka)
Message retention Deleted on ACK Retained for configured period (days/weeks)
Multiple consumers Competing consumers (one message → one consumer) Consumer groups read independently; all groups can read same message
Replay Not possible after ACK Any consumer can replay from any offset
Throughput High (100K msg/s typical) Very high (millions msg/s)
Use case Task queues, job scheduling Event sourcing, audit logs, stream processing, CDC
Example: Order Processing Pipeline
# Producer: Order Service
queue.send('order_processing', {
    'order_id': 'ord_123',
    'user_id': 'usr_456',
    'items': [...]
})
# Returns immediately — user sees "order placed"

# Consumer 1: Inventory Service (separate process)
@queue.handler('order_processing')
def reserve_inventory(message):
    items = message['items']
    for item in items:
        inventory.reserve(item['product_id'], item['quantity'])
    queue.ack(message)   # Remove from queue

# Consumer 2: Payment Service (separate process)
@queue.handler('order_processing')
def process_payment(message):
    charge_result = payment.charge(message['user_id'], ...)
    queue.ack(message)

Pub/Sub Pattern

In Pub/Sub (Publish/Subscribe), publishers send messages to a topic without knowing who will receive them. Multiple subscribers can independently receive copies of every message published to the topic. This enables fan-out — one event triggers multiple independent actions.

Message Queue (Point-to-Point)

  • One message → consumed by one consumer
  • Multiple competing consumers share the work
  • Load balancing between consumers
  • Use for: task distribution

Pub/Sub (Broadcast)

  • One message → delivered to all subscribers
  • Each subscriber receives its own copy
  • Independent processing per subscriber
  • Use for: event notifications, fan-out
Example: User Registration Event
# Publisher
eventBus.publish('user.registered', {

Dead Letter Queues (DLQ)

A Dead Letter Queue is a separate queue where messages are routed after failing to be processed successfully after a configured number of retries. Instead of blocking the main queue or silently discarding failed messages, they are held in the DLQ for inspection and manual or automated remediation.

When a Message Goes to the DLQ

  • Processing has been retried more than the maximum configured times
  • The message has exceeded its maximum retention time in the queue
  • The message is unroutable (no matching consumer)
  • The consumer explicitly sends the message to the DLQ (e.g., malformed payload)

DLQ Operations

  • Alerting: Monitor DLQ size. Any message in the DLQ indicates a processing failure that needs investigation.
  • Inspection: Examine failed messages to diagnose bugs or data issues.
  • Replay: After fixing the bug, replay DLQ messages back to the main queue.

Change Data Capture (CDC)

CDC is a pattern that captures changes (inserts, updates, deletes) in a database and publishes them as a stream of events. Rather than polling the database periodically or modifying application code to publish events, CDC reads the database's internal transaction log (e.g., PostgreSQL WAL, MySQL binlog) and converts log entries into events.

Benefits

  • Guaranteed capture: Every committed database change is captured — no event can be missed by application-level logic.
  • Zero application code changes: The database itself is the source of truth; no extra publish calls in business logic.
  • Historical replay: Reprocess all changes from the beginning of the log for new consumers.
  • Multiple downstream systems: One CDC stream feeds many consumers independently.

Tools: Debezium (most widely used, open source), AWS DMS, Striim, Airbyte (with CDC mode)

Delivery Semantics

Delivery semantics define the guarantee a messaging system provides about whether and how many times a message is delivered to a consumer.

Semantic Guarantee Implementation Risk Use case
At-most-once Delivered 0 or 1 times; may be lost Fire-and-forget, no ACK, no retry Message loss Logs, metrics where occasional loss is acceptable
At-least-once Delivered 1 or more times; never lost Retry on failure, ACK only on success Duplicate delivery Most use cases — combined with idempotent processing
Exactly-once Delivered exactly once; never lost, never duplicated Distributed transactions or idempotency keys + dedup High complexity, performance cost Financial transactions, exactly-once semantics in Kafka
Exactly-Once is Rare and Expensive

True exactly-once delivery across distributed systems is extremely difficult and imposes significant overhead. In practice, most systems implement at-least-once delivery and make consumer processing idempotent — i.e., processing the same message twice produces the same result as processing it once. This combination is simpler, more performant, and functionally equivalent to exactly-once for most use cases.
