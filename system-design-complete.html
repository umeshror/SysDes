Introduction to System Design

Module 1  |  5 topics

What is System Design?

System design is the process of defining the architecture, components, modules, interfaces, and data flow of a system to satisfy specified requirements. It bridges the gap between a product specification and its implementation.

At its core, system design asks: given that millions of users need to do X, how do we build software that is fast, reliable, cost-effective, and maintainable?

Why System Design Matters

  • Scale: A design that works for 100 users usually fails at 100 million users. Choices made early — how you store data, how you split components — become load-bearing walls.
  • Cost: Poor design wastes compute, storage, and engineering time. A well-designed cache can cut database costs by 90%.
  • Resilience: Real systems fail. Good design contains failures rather than letting them cascade.
  • Maintainability: Code is read and modified far more than it is written. Design shapes how easy that is.

The System Design Process

  1. Requirements clarification — functional requirements (what it does) vs non-functional (how well it does it: latency, availability, consistency).
  2. Capacity estimation — estimate traffic, storage, and bandwidth needs.
  3. High-level design — sketch major components and their relationships.
  4. Detailed design — deep-dive critical subsystems.
  5. Identify bottlenecks — single points of failure, hotspots, scaling walls.
  6. Tradeoff discussion — no design is perfect; articulate what was sacrificed.

What is a System Design Interview?

A System Design Interview (SDI) is a technical conversation about how to build a large-scale system. Unlike coding interviews, there is no single "correct" answer. The interviewer is assessing your ability to handle ambiguity, make informed trade-offs, and design for scalability and reliability.

Focus Areas
  • Scalability: Can the system handle 10x or 100x more traffic?
  • Architecture: How are components organized and how do they interact?
  • Trade-offs: Why choose X over Y? (e.g., SQL vs NoSQL)
  • Problem Solving: How do you handle edge cases and failures?

Functional vs. Non-functional Requirements

Before designing anything, you must define the scope. This is split into two categories:

Functional Requirements

What the system must do. Features and behaviors.

  • "Users can upload photos."
  • "Users can follow each other."
  • "The system generates a news feed."

Non-functional Requirements

How the system performs. Constraints and qualities.

  • Scalability: Handle 10M daily active users.
  • Availability: 99.9% uptime (Highly available).
  • Latency: Feed generation under 200ms.
  • Consistency: Eventual vs strong consistency.

What are Back-of-the-Envelope Estimations?

These are quick, approximate calculations used to assess if a design is feasible within given constraints. They help determine the scale of the system (e.g., "Do we need 1 server or 1000?").

Common Units to Know
  • 1 Trillion requests/day ≈ 12 Million requests/sec
  • 1 GB = 109 bytes
  • Latency: Memory (100ns) vs SSD (100µs) vs Disk (10ms) vs Network (150ms).

Things to Avoid During System Design Interview

  • Skipping Requirements: Never start designing without clarifying the goal.
  • Ignoring Trade-offs: Don't just pick a technology because it's popular; explain why.
  • Poor Communication: Don't go silent. Think out loud and engage the interviewer.
  • Rigid Thinking: If the interviewer suggests a flaw, be open to adjusting your design.
  • Diving Too Deep Early: Don't design the database schema before the high-level architecture.

Key Characteristics of Distributed Systems

A distributed system is a collection of independent computers that appears to its users as a single coherent system. To build such systems at scale, we must prioritize specific characteristics:

  • Scalability: The ability to handle more load by adding resources (CPU, RAM, nodes).
  • Reliability: The probability the system performs correctly over time, even with failures.
  • Availability: The percentage of time the system is operational and accessible.
  • Efficiency: How effectively the system uses resources (latency and throughput).
  • Fault Tolerance: The ability to continue operating despite one or more component failures.
  • Manageability: How easy it is to operate, monitor, and maintain the system.

Scalability

Scalability is the ability of a system to handle an increasing amount of work by adding resources. A scalable system maintains acceptable performance as load grows.

Vertical Scaling (Scale Up)

Vertical scaling means increasing the capacity of a single machine — adding more CPU cores, RAM, faster storage, or a faster network card.

Advantages

  • No application changes required
  • No distributed system complexity
  • Low-latency access to all data (single machine)
  • Transactions remain simple and consistent

Limitations

  • Hard physical ceiling (largest machine on market)
  • Very expensive at high end (diminishing returns)
  • Single point of failure
  • Requires downtime to upgrade hardware
Real World

Database vertical scaling

A startup runs PostgreSQL on a 4-core, 16 GB RAM machine. As read queries increase, they upgrade to 32 cores and 256 GB RAM. This buys time but eventually hits the ceiling — a single machine can only go so far before cost explodes or the hardware ceiling is reached. At that point they must switch to horizontal scaling strategies (read replicas, sharding).

Horizontal Scaling (Scale Out)

Horizontal scaling means adding more machines to the pool and distributing the workload among them. This requires the application to be designed for distribution: stateless request handling, distributed data storage, and coordination protocols.

Advantages

  • Theoretically unlimited capacity
  • Commodity hardware keeps cost lower
  • Fault tolerance — one machine failing doesn't bring down the system
  • Can scale specific tiers independently

Challenges

  • Distributed systems complexity (coordination, consensus)
  • Data consistency becomes harder
  • Network becomes a factor (latency, partitions)
  • Application must be designed to be stateless or share state externally

Dimensions of Scalability

  • Request scalability: Handle more requests per second (add API servers)
  • Data scalability: Store more data (sharding, object storage)
  • Geographic scalability: Serve users worldwide with low latency (CDN, multi-region)
  • Operational scalability: Maintain system without linear team growth (automation)

Availability

Availability is the proportion of time a system is in a functioning condition. It is typically expressed as a percentage over a year.

Two nines 99% 87.7 hours 7.2 hours Internal dev tools
Three nines 99.9% 8.76 hours 43 minutes Standard web apps

Techniques for High Availability

  • Redundancy: Deploy multiple instances of each component so no single failure causes outage.
  • Failover: Automatically redirect traffic to healthy instances when one fails (active-passive or active-active).
  • Geographic distribution: Deploy across multiple availability zones or regions.
  • Health checks and circuit breakers: Detect and isolate unhealthy components before they cause cascading failures.
  • Graceful degradation: Serve partial functionality rather than total failure (e.g., show cached results when database is slow).
Common Misconception

High availability does not mean zero downtime forever. It means designed downtime is minimized and unplanned downtime is rare and short. Even five-nines systems have maintenance windows.

SLA, SLO, and SLI

SLI (Service Level Indicator)
A quantitative measure of service quality. Example: "The fraction of HTTP requests that complete in under 200 ms."
SLO (Service Level Objective)
A target value for an SLI. Example: "99.9% of requests should complete in under 200 ms."
SLA (Service Level Agreement)
A contract with customers that includes SLOs and consequences for missing them. Example: "If monthly availability falls below 99.9%, customers receive a service credit."

Reliability

Reliability is the probability that a system performs its intended function correctly over a specified period, even under adverse conditions. A reliable system produces correct results and does not corrupt data, even when components fail.

Reliability vs Availability

These two properties are related but distinct:

  • A system that is available but unreliable responds to requests but returns incorrect results (e.g., shows wrong bank balance).
  • A system that is reliable but unavailable gives correct answers whenever it responds, but may be down frequently.
  • The goal is both: always available and always correct.

Techniques for Reliability

  • Replication: Keep multiple copies of data so hardware failure doesn't cause loss.
  • Checksums and data integrity: Detect corruption at rest and in transit.
  • Idempotency: Design operations so retrying a failed request doesn't cause duplicate side effects.
  • Testing: Unit, integration, chaos engineering (deliberately inject failures to find weaknesses).
  • Write-ahead logging (WAL): Record intended changes before applying them so partial failures can be recovered.

Single Point of Failure (SPOF)

A Single Point of Failure is any component whose failure would bring down the entire system. Eliminating SPOFs is a core goal of high-availability design.

Common Sources of SPOF

  • Single load balancer: If the load balancer fails, all traffic is blocked. Fix: deploy an active-passive pair of load balancers.
  • Single database primary: If the primary database crashes, writes are unavailable. Fix: automated failover to a replica.
  • Single datacenter: Power outage, network cut, or natural disaster takes down everything. Fix: multi-region deployment.
  • Shared external service: Your system depends on a third-party API with no fallback. Fix: circuit breakers, caching, alternative providers.

Latency, Throughput, and Bandwidth

Latency

Latency is the time elapsed between sending a request and receiving a response. It is typically measured in milliseconds (ms) and expressed as percentiles rather than averages, because averages hide the tail behavior that users actually experience.

Why Percentiles Matter

If p50 (median) latency is 20 ms but p99 latency is 2000 ms, then 1 in 100 requests takes two full seconds — users experience this as "sometimes the site is slow." The average (e.g., 40 ms) hides this problem entirely.

Throughput

Throughput is the number of operations a system can process per unit of time. Common units include requests per second (RPS), transactions per second (TPS), or bytes per second.

Throughput and latency are related but different: you can have high throughput with high latency (batch processing), or low latency with low throughput (synchronous real-time operations). Optimizing one often harms the other.

Bandwidth

Bandwidth is the maximum rate at which data can be transferred across a network link. It is a ceiling on throughput, not throughput itself. Actual throughput is limited by bandwidth but also by packet loss, protocol overhead, and hardware limits.

Bandwidth estimation example

Capacity Estimation

A video streaming service streams at 4 Mbps per user. With 1 million concurrent users: 4 Mbps × 1,000,000 = 4,000 Gbps = 4 Tbps of egress bandwidth required. This drives decisions around CDN architecture and peering agreements.

CAP Theorem and Consistency Models

CAP Theorem

Interview Classic Critical

The CAP theorem, formulated by Eric Brewer in 2000 and proven by Gilbert and Lynch in 2002, states that a distributed data store can provide at most two of the following three guarantees simultaneously:

Consistency (C)
Every read receives the most recent write, or an error. All nodes in the system see the same data at the same time. From a client's perspective, the system behaves as if there is only one copy of the data.
Availability (A)
Every request to a non-failing node receives a response — not an error. The system is always operational and will respond, though the response may not reflect the most recent write.
Partition Tolerance (P)
The system continues to operate even when network partitions occur — i.e., when messages between nodes are lost or delayed indefinitely.
The Key Insight

In any distributed system operating over a real network, network partitions will happen. Therefore, Partition Tolerance is not optional — it must be accepted. The real choice is between Consistency and Availability during a partition event.

CP Systems: Consistency + Partition Tolerance

During a network partition, a CP system chooses to stop responding rather than risk returning inconsistent data. Clients may receive an error or timeout, but any successful response reflects the latest committed data.

Example: Banking Transfer

Node A and Node B are partitioned. A user transfers $500 from their account. A CP system will refuse to process the transaction rather than risk completing it on one node and not the other. The user gets an error ("service temporarily unavailable") rather than an incorrect balance. This is acceptable for financial systems.

Systems: HBase, ZooKeeper, MongoDB (with majority write concern), etcd, Consul

AP Systems: Availability + Partition Tolerance

During a network partition, an AP system continues serving requests on all nodes. Nodes may have stale data. The system sacrifices consistency in exchange for staying available. After the partition heals, nodes eventually reconcile their state.

Example: Social Media Like Count

Node A and Node B are partitioned. A user likes a post. The count on Node A updates to 1001. A different user reading from Node B sees 1000. This is acceptable — a slightly stale like count is far better than the entire site being unavailable.

Systems: Cassandra, DynamoDB, CouchDB, Riak, DNS

Consistency Models

Consistency models define the rules about when writes become visible to reads. They form a spectrum from strictest to most relaxed, with tradeoffs in latency and availability.

Strong Consistency (Linearizability)

After a write completes, any subsequent read — from any node — will see that write. Operations appear as if executed on a single machine in real time order. This is the strongest and most intuitive model.

  • Implementation: All replicas must acknowledge before write is considered complete. High coordination overhead.
  • Latency: High, because reads and writes must wait for cross-node confirmation.
  • Use cases: Bank balances, inventory counts, leader election.
  • Examples: Google Spanner, etcd, single-node PostgreSQL.

Sequential Consistency

All operations appear to have executed in some sequential order, and the operations of each individual process appear in this sequence in the order specified by the process. Weaker than linearizability — the sequence does not need to match real-time order, but each process's operations must appear in order.

Causal Consistency

Operations that are causally related are seen by all nodes in the same order. Operations that have no causal relationship may be seen in different orders by different nodes.

Example: Comment thread

Alice posts "Is anyone around?" (event A). Bob replies "Yes!" (event B, caused by A). With causal consistency, every user sees A before B, because B causally depends on A. However, unrelated posts from Charlie may appear in any order relative to A and B.

Read-Your-Writes Consistency

A client that writes a value will always see that value (or a more recent one) in subsequent reads, even if other clients still see the old value. This is a practical guarantee that prevents confusing user experiences.

Example: Profile photo update

You upload a new profile photo. The operation succeeds. When you reload your profile page, you see the new photo — not the old one — even though other users might still see the old photo for a few seconds while replicas catch up.

Monotonic Read Consistency

If a client reads value V at time T, all subsequent reads by that client will return V or a more recent value. A client will never read progressively older values (it won't go "backwards in time").

Eventual Consistency

If no new updates are made to a given data item, eventually all reads will return the last updated value. This is the weakest mainstream model — the system makes no guarantee about when convergence happens, only that it will.

  • Implementation: Replicas accept writes locally and sync asynchronously.
  • Latency: Very low — no coordination needed for writes.
  • Use cases: DNS propagation, social media counters, product availability.
  • Examples: Amazon DynamoDB (default), Apache Cassandra, Amazon S3.

PACELC Theorem

Extension of CAP Theorem - Understanding latency-consistency tradeoffs during normal operation

Real Story: The Gap CAP Didn't Address

CAP Theorem became famous for explaining distributed systems behavior during network partitions. But engineers realized something: partitions are rare (happening 0.01% of the time), yet we make consistency vs latency tradeoffs every single day during normal operation. PACELC fills this gap.

What is PACELC?

The PACELC theorem (pronounced "pass-elk") extends CAP by stating:

PACELC Definition

If Partition (P): Choose between Availability (A) and Consistency (C)

Else (E): When system is running normally, choose between Latency (L) and Consistency (C)

This creates four possible system configurations: PA/EL, PA/EC, PC/EL, and PC/EC.

Why PACELC Matters

Consider a typical production system:

  • 99.99% of the time: System runs normally (no partition)
  • 0.01% of the time: Network partition occurs

CAP only addresses the 0.01% case. PACELC addresses both cases, making it far more practical for day-to-day architectural decisions.

Example: Reality Check
Your e-commerce site runs 365 days/year.

Partition time: 0.01% = 52.6 minutes/year
Normal operation: 99.99% = 525,547 minutes/year

CAP helps you plan for 52 minutes.
PACELC helps you optimize for 525,547 minutes.

Which matters more for your users?

The Four PACELC Configurations

1. PA/EL - High Availability + Low Latency

During Partition: Choose Availability (keep serving requests)

Normal Operation: Choose Low Latency (async replication)

Characteristics:

  • Eventually consistent
  • Fast response times (<100ms)< /li>
  • Always available
  • May serve stale data briefly

Examples: Cassandra, DynamoDB, Riak, Voldemort

Use Cases: Social media feeds, product catalogs, recommendation engines, shopping carts, session stores

Real Example: Amazon Shopping Cart

Amazon's shopping cart uses a PA/EL system (Dynamo). When you add an item:

  • Response is instant (<50ms)< /li>
  • Your item is saved locally first
  • Replication happens asynchronously
  • During partition, you can still add items
  • Brief inconsistency is acceptable (cart eventually syncs)

Why: User experience demands instant feedback. Nobody wants to wait 500ms to add to cart. Losing an item temporarily is acceptable; losing the customer isn't.

2. PC/EC - Strong Consistency Always

During Partition: Choose Consistency (may become unavailable)

Normal Operation: Choose Consistency (synchronous replication)

Characteristics:

  • Always strongly consistent
  • Higher latency (100-500ms)
  • May be unavailable during partition
  • No stale reads ever

Examples: PostgreSQL (with sync replication), MongoDB (with majority write concern), HBase, VoltDB

Use Cases: Banking, payments, financial transactions, inventory management, booking systems, critical user data

Real Example: Bank Account Balance

Your bank uses a PC/EC system for account balances:

  • Every transaction waits for replication (~200ms)
  • All replicas must acknowledge before success
  • During partition, may reject transactions
  • You always see accurate balance

Why: Accuracy matters more than speed. Showing wrong balance = legal/regulatory issues. Brief downtime during partition is acceptable; showing incorrect money is not.

3. PA/EC - Rare Configuration

During Partition: Choose Availability

Normal Operation: Choose Consistency

This configuration is rare because it creates operational challenges:

  • You must handle inconsistency during partitions
  • Then reconcile when partition heals
  • Application logic becomes complex

Use Case: Systems with geographic locality where partitions are extremely rare, and you can afford conflict resolution.

4. PC/EL - Rare Configuration

During Partition: Choose Consistency

Normal Operation: Choose Low Latency

This configuration is contradictory and rarely used:

  • Hard to achieve low latency with strong consistency
  • Typically requires expensive infrastructure
  • Only viable with very low replication distance

Latency vs Consistency During Normal Operation

The key insight: even without partitions, you face tradeoffs.

PACELC vs CAP: Key Differences

CAP Theorem

  • Only addresses partition scenario (0.01% of time)
  • Binary choice: A or C during partition
  • Ignores normal operation completely
  • Doesn't consider latency
  • Published 2000, revolutionary at the time
  • Good for understanding failure modes

PACELC Theorem

  • Addresses both partition AND normal operation
  • Considers latency-consistency tradeoff (99.99% of time)
  • More practical for daily decisions
  • Helps choose database and configuration
  • Published 2012 by Daniel Abadi
  • Better for operational architecture

Practical Implementation: Configuring PACELC

Example: Cassandra Configuration
// PA/EL Configuration (default)
CONSISTENCY LEVEL = ONE    // Read from any replica (fast)
REPLICATION = ASYNC        // Don't wait for replicas

Result: 10ms reads, eventually consistent

// PC/EC Configuration (strict)
CONSISTENCY LEVEL = QUORUM // Read from majority (slower)
REPLICATION = QUORUM       // Wait for majority write

Result: 150ms reads, strongly consistent

// You choose based on use case!
Design Principle

Different data, different tradeoffs: Use PA/EL for user-facing features (speed matters). Use PC/EC for critical data (accuracy matters). Same application can use both!

Common Misconceptions

Myth: "PA/EL systems are unreliable because of eventual consistency"

Reality: They're highly reliable. "Eventual" typically means milliseconds. Amazon, Facebook, Netflix use PA/EL for most data.

Myth: "PC/EC is always better because of strong consistency"

Reality: Higher latency hurts user experience. Use PC/EC only where accuracy is critical, not everywhere.

Myth: "I must choose one configuration for my entire system"

Reality: Most systems use both. Shopping cart = PA/EL. Checkout = PC/EC.

Key Takeaway

PACELC is more practical than CAP because systems spend 99.99% of time in normal operation, not partitioned. Understanding the latency-consistency tradeoff helps you make better database choices and configuration decisions for everyday scenarios.

Use PACELC to:

  • Choose the right database for each use case
  • Configure consistency levels appropriately
  • Explain tradeoffs to stakeholders
  • Make informed architecture decisions

Consistent Hashing

Module 2  |  The Algorithm Behind Distributed Caches, DHTs, and Database Sharding

The Problem: Naive Modulo Hashing

The simplest way to distribute keys across N nodes is hash(key) % N. This works perfectly until you add or remove a node — at which point almost every key maps to a different node, causing a massive cache invalidation storm or data migration.

Modulo Hashing Failure at Scale

With 10 nodes: hash("user:42") % 10 = 3 → node 3. Add one node (11 total): hash("user:42") % 11 = 8 → node 8. The key moved. With 1 million keys, ~91% of keys must migrate when you add just 1 of 10 nodes. This is catastrophic for a cache or distributed database.

Consistent Hashing: The Ring

Consistent hashing places both nodes and keys on a virtual hash ring (0 to 232−1). A key is assigned to the first node found clockwise on the ring from its position. When a node is added or removed, only the keys between the new node and its predecessor need to move — approximately K/N keys total (K = total keys, N = nodes).

Adding a node:
Insert Node 4 at hash=40. Only keys between hash=20 and hash=40 (previously owned by Node 2) move to Node 4. All other keys are unaffected.
Removing a node:
Remove Node 2 (hash=50). Its keys are reassigned to Node 3 (its clockwise successor). ~1/N of all keys move.
Key migration formula:
Adding 1 node to a cluster of N: only K/N keys move (vs. ~K×(N-1)/N for modulo hashing).

Virtual Nodes (vnodes): Solving Uneven Distribution

A simple ring has a problem: random placement causes unequal load distribution. Node A might own 40% of the ring; Node B owns 10%. Virtual nodes solve this — each physical node gets M positions on the ring (typically 150–200 vnodes per physical node).

Without vnodes

  • Random hash placement → unequal arc lengths
  • One node may own 5× more keys than another
  • Heterogeneous hardware can't be accounted for

With vnodes (150 per node)

  • Each node's vnodes are spread evenly across the ring
  • Load variance typically <5% across nodes
  • Larger nodes get proportionally more vnodes (weighted)
  • Node failure redistributes load evenly across all others

Real-World Implementations

Amazon DynamoDB
DynamoDB uses consistent hashing across its storage nodes. Each item's partition key is hashed to determine which storage node owns it. DynamoDB automatically splits hot partitions and re-distributes load — this is consistent hashing operating transparently at hyper-scale (millions of requests/sec globally).
Apache Cassandra
Cassandra's ring uses MurmurHash3 with configurable vnodes (default: 256 per node). The replication factor (RF) means each key is stored on RF consecutive nodes clockwise — so data is always available even if RF-1 nodes fail. With RF=3, Cassandra can survive 2 node failures per partition.
Redis Cluster
Redis Cluster uses a fixed 16,384-slot hash ring. Each slot is owned by one primary node. Keys are mapped to slots via CRC16(key) % 16384. This is a simplified consistent hashing variant — no vnodes, but slot assignment is explicit and easily resharded.
Akamai CDN
Consistent hashing was invented by David Karger et al. at MIT in 1997 — directly motivated by the problem of distributing web content across Akamai's cache servers. The original paper described exactly this problem: how to route requests to cache servers such that server additions/removals don't invalidate most cached content.

Consistent Hashing in Database Sharding

FAANG Interview: Design a Distributed Key-Value Store

A standard question. The expected answer mentions consistent hashing for the routing layer:

  1. Client computes ring_position = hash(key)
  2. Client queries a routing layer (or maintains a local cluster map) to find the responsible node
  3. Request goes directly to that node (like Cassandra's coordinator pattern)
  4. Replication copies to the next RF-1 nodes clockwise on the ring
  5. On node failure: successor node absorbs its keys until the failed node recovers
Hotspot Mitigation with Consistent Hashing

If a specific key is extremely hot (celebrity social media post, trending product), consistent hashing still routes it to one node. Solutions: (1) key suffixing — append a random suffix (0–N) to spread the key across N nodes, then aggregate on read; (2) local cache in front of the distributed cache for the hottest keys; (3) read replicas for the hot partition specifically.

Instagram's 2012 peak: vertical first
Instagram ran on a handful of EC2 instances for their first year (vertical scaling). Only after hitting the wall did they introduce sharding and horizontal scale. Lesson: Don't over-engineer. Scale vertically until it's no longer cost-effective, then scale horizontally. "Premature optimization is the root of all evil."

16. Push vs. Pull Architecture

Prometheus (Pull) vs. StatsD (Push)
Prometheus scrapes (pulls) metrics from each service's /metrics endpoint every 15s. Services don't need to know about Prometheus. Easy to discover new services, replay historical scrapes. Downside: what if a service dies between scrapes?

StatsD pushes UDP packets from within the application to a StatsD daemon. Low-overhead fire-and-forget. Downside: UDP is lossy, service must know StatsD address.

Prometheus dominates at FAANG scale (Kubernetes-native). StatsD is common in legacy or non-containerized systems.
Kafka's pull model for consumers
Kafka consumers pull at their own pace — this is intentional. Consumers control their offset. A consumer can slow down, go offline, and resume without losing messages (up to retention period). This "backpressure by design" is why Kafka consumers don't get overwhelmed — they simply slow their polling rate when processing is behind.

19. Stateless Rate Limiting vs. Distributed Rate Limiting

Per-instance rate limiting (stateless)
Each server tracks its own counters in local memory. Fast (no network call) but approximate — 10 servers with 100 RPS limit each = 1000 RPS effectively passes. Acceptable for protecting individual servers from overload, not for API quota enforcement.
Centralized distributed rate limiting (Redis)
All servers increment a shared Redis counter. Accurate across the entire fleet. Redis INCR + EXPIRE is atomic — no race conditions. Latency cost: ~0.5ms per request for the Redis round trip. Used by: Stripe, GitHub, Shopify. Redis Cluster scales this to millions of keys/sec.
Gossip-based (approximate, edge-native)
Cloudflare's edge rate limiting syncs counters between PoPs via gossip. Each PoP's counter may be slightly stale (by milliseconds). Allows up to ~10% over-limit in exchange for no centralized bottleneck. Tradeoff: accuracy vs. availability and latency.

Master Framework: The 5 Trade-off Questions

Use this in every system design interview

IP Address

An IP address is a numerical label assigned to every device on a network for identification and routing.

IPv4 vs IPv6

  • IPv4: 32-bit address space (~4.3 billion addresses). Written as four octets: 192.168.1.1. Exhausted; most new allocations use NAT.
  • IPv6: 128-bit address space (~3.4 × 10^38 addresses). Written as eight groups of hex: 2001:0db8:85a3::8a2e:0370:7334. Eliminates NAT requirement.

Public vs Private Addresses

Private address ranges (10.x.x.x, 172.16-31.x.x, 192.168.x.x) are used within private networks and are not routable on the internet. Network Address Translation (NAT) maps private addresses to a shared public IP when communicating externally.

TCP vs UDP

TCP and UDP are the two primary transport-layer protocols. They represent fundamentally different tradeoffs between reliability and speed.

TCP — Transmission Control Protocol

TCP provides a reliable, ordered, error-checked byte stream between two endpoints. It achieves this through a three-way handshake, acknowledgments, retransmission of lost packets, flow control (preventing sender from overwhelming receiver), and congestion control (preventing sender from overwhelming the network).

TCP Three-Way Handshake

  1. SYN: Client sends a segment with the SYN flag and an initial sequence number.
  2. SYN-ACK: Server acknowledges with its own sequence number and the SYN-ACK flags.
  3. ACK: Client acknowledges. Connection is established.

This handshake adds 1 RTT (round-trip time) of latency before any data can be sent. TLS on top of TCP adds another 1–2 RTTs for the TLS handshake.

UDP — User Datagram Protocol

UDP sends discrete datagrams without connection setup, acknowledgment, ordering, or retransmission. There is no guarantee of delivery, order, or that packets won't be duplicated. However, UDP has no handshake overhead, no head-of-line blocking, and minimal protocol overhead (8-byte header vs TCP's 20+ bytes).

TCP — Use When

  • Data must arrive complete and in order
  • HTTP/1.1, HTTP/2 web requests
  • Database connections (PostgreSQL, MySQL)
  • Email (SMTP, IMAP)
  • File transfers (FTP, SCP)
  • SSH sessions

UDP — Use When

  • Speed matters more than reliability
  • Video and audio streaming (Zoom, YouTube)
  • Online gaming (position updates)
  • DNS queries (single request/response)
  • DHCP, NTP
  • HTTP/3 (QUIC protocol is UDP-based)
Real World: Online Gaming

A player's position update is sent 60 times per second. If one packet is lost, waiting for TCP retransmission means the game would wait ~100–300ms before progressing — causing visible stutter. Instead, UDP is used: if a position packet is lost, the game simply uses the next one. The latency is acceptable and the loss is invisible.

However, in the same game, chat messages use TCP — a chat message that disappears would be a much worse user experience than brief movement lag.

HTTP / HTTPS

HTTP (Hypertext Transfer Protocol) is the foundation of data communication on the web. HTTPS is HTTP with TLS encryption layered on top.

HTTP/1.1

Introduced persistent connections (keep-alive) to reuse TCP connections across multiple requests. However, each connection can only serve one request at a time — a later request must wait for the earlier one to complete. Workaround: browsers open 6–8 parallel TCP connections per host, which creates overhead.

HTTP/2

HTTP/2 introduced request multiplexing over a single TCP connection. Multiple requests and responses can be in-flight simultaneously, interleaved in binary frames. It also includes header compression (HPACK) and optional server push. This significantly reduces the number of TCP connections and eliminates head-of-line blocking at the HTTP layer.

HTTP/3 (QUIC)

HTTP/3 replaces TCP with QUIC, a transport protocol built on UDP. QUIC integrates TLS 1.3, provides multiplexing without TCP's head-of-line blocking (a single lost packet blocks all streams in HTTP/2 over TCP, but not in QUIC), and supports 0-RTT connection resumption for repeat clients.

DNS Recursive Resolution Process

  1. Browser cache: Check local cache (TTL-based).
  2. OS cache and hosts file: Check /etc/hosts and OS DNS cache.
  3. Recursive resolver: Query the ISP's or configured recursive resolver.
  4. Root nameserver: Resolver asks root for the TLD nameserver (e.g., who handles .com?).
  5. TLD nameserver: Returns the authoritative nameserver for the domain.
  6. Authoritative nameserver: Returns the actual IP record for the hostname.
  7. Response is cached at each layer according to TTL values.

TTL and Its Tradeoffs

TTL (Time To Live) controls how long DNS resolvers cache a record. It is measured in seconds.

  • Long TTL (e.g., 86400s = 1 day): Fewer DNS queries, lower latency for repeat visitors. However, changes take up to 1 day to propagate globally. Not suitable for failover scenarios.
  • Short TTL (e.g., 60s): Changes propagate quickly. Good for failover. But high DNS query volume, higher cost, and slightly higher latency for cold clients.

Best practice: Use high TTL normally. 24–48 hours before a planned migration or failover, lower the TTL to 60–300 seconds so clients pick up the change quickly.

DNS Load Balancing

DNS can distribute load by returning multiple A records for the same domain. The DNS resolver or client typically uses one, but over time traffic is distributed. However, DNS load balancing is coarse — it cannot account for server health in real time, and cached records may point to a downed server for the TTL duration.

Geolocation DNS (used by AWS Route 53, Cloudflare) returns different IP addresses based on the geographic location of the requester, routing users to the nearest datacenter.

Checksums

A checksum is a small fixed-size value computed from data that is used to detect errors in transmission or storage. When data is sent or stored, the checksum is computed and included. On receipt or retrieval, the checksum is recomputed and compared.

  • Simple checksums (parity bits): Detect single-bit errors, not suitable for data integrity in storage.
  • CRC (Cyclic Redundancy Check): Detects burst errors. Used in Ethernet, ZIP, and storage.
  • MD5, SHA-256: Cryptographic hash functions. Used for file integrity verification, digital signatures, and content-addressable storage. MD5 is broken for security but still used for non-security checksums.
Real World: Amazon S3 ETags

When uploading a file to S3, AWS computes and stores an ETag (typically an MD5 hash for small files). When you download the file, you can verify the ETag to detect any corruption that occurred during transfer or storage. This is called end-to-end integrity checking.

Nginx as a Reverse Proxy: What It Actually Does

SSL/TLS Termination
Nginx handles the expensive HTTPS handshake and decryption. Requests flow internally as plain HTTP. This keeps TLS certificates centralized and removes crypto load from app servers. A single Nginx instance can handle ~10,000 TLS connections/sec on commodity hardware.
Connection Pooling (Keepalive)
Nginx maintains a pool of persistent connections to upstream app servers (upstream keepalive). Without this, each proxied request requires a new TCP handshake to the backend — 3-way handshake adds ~0.5–2ms per request. With keepalive, the connection is reused: ~0.05ms overhead.
Request Buffering
Nginx fully buffers slow client uploads before forwarding to the app server. This prevents "slow client" attacks from tying up app server threads. The app server sees a fast, complete request — not a slow trickle.
Static File Serving
Nginx serves static files at ~50–100K RPS from disk with sendfile() syscall (zero-copy, kernel-level). App servers (Node.js, Python) max out at ~5K RPS for static files. Always offload statics to Nginx or CDN.

Service Mesh: The Sidecar Proxy Pattern

In a microservices architecture, a service mesh deploys a lightweight reverse proxy (sidecar) beside every service instance. The sidecar handles all network traffic — the app doesn't need to implement retries, mTLS, circuit breaking, or observability itself.

What the sidecar (Envoy) provides:
  • mTLS — automatic mutual TLS between services (zero trust)
  • Circuit breaking — stop sending to failing upstreams
  • Retries with jitter — configurable retry policies

  • Traffic splitting — canary/blue-green at the network layer

Real-world: Lyft, Airbnb, Google
Lyft created Envoy in 2015 because their service-to-service communication had no visibility. Airbnb runs SmartStack (their own service mesh). Google invented gRPC and builds products with their own internal mesh (Traffic Director). Netflix uses Zuul as an edge proxy and Eureka for service discovery — a form of mesh without a dedicated sidecar.

Proxy Use Cases in FAANG System Design Interviews

When to mention proxy in your design
  • Any public-facing API: mention reverse proxy for TLS termination, rate limiting, and DDoS protection at the edge (Cloudflare/CDN)
  • Microservices: mention service mesh (Istio/Envoy) for mTLS, circuit breaking, and distributed tracing without app code changes
  • Database connections: mention a connection proxy (PgBouncer for PostgreSQL, ProxySQL for MySQL) to pool thousands of app connections into tens of DB connections
  • Multi-cloud / egress: forward proxy for controlling which external APIs services can call
PgBouncer — The Database Connection Proxy
PostgreSQL creates a new OS process per connection (~5–10MB RAM each). A Node.js app with 100 instances × 10 connection pool = 1,000 connections = 10GB RAM just for idle connections. PgBouncer sits in front of Postgres and multiplexes thousands of app connections onto ~20–50 actual DB connections. Transactions are serialized through the real connections. Shopify runs PgBouncer in front of all their PostgreSQL clusters. Result: DB can scale to 10K+ app instances without adding more DB connections.

L4 vs. L7 Load Balancing

Layer 4 (Network/Transport)

  • Routes based on IP + TCP/UDP port only
  • No inspection of HTTP headers, URL, cookies

  • Reads HTTP headers, URL paths, cookies, request body
  • Route /api/* to one server group, /static/* to another
  • Sticky sessions via cookie (SERVERID)
  • Header rewriting, request/response transformation
  • WebSocket and HTTP/2 multiplexing aware

Use: Web apps, microservices, content-based routing, canary deployments

Power of Two Choices (P2C) — The Modern Standard

Pick 2 random servers, route to the one with fewer connections. Theoretically proven to reduce max load from O(log N / log log N) (round robin) to O(log log N) — a dramatic improvement at scale. Used by Nginx Plus, HAProxy (with random selection), and most modern service meshes. Netflix uses a variant they call "Hysteresis" which also weighs recent response latency.

Health Checks: Active vs. Passive

Active Health Checks

  • LB periodically probes each backend (HTTP GET /health every 5s)
  • Detects failure BEFORE a real user request fails
  • Costs some bandwidth and server resources
  • Checks should test real dependencies: DB connection, cache reachability

Passive Health Checks

  • Monitor actual traffic responses for failures (5xx, timeouts)
  • Zero overhead when healthy
  • At least one real user sees the error before the server is marked down
  • Good complement to active checks
Health check endpoint best practices
A good /health endpoint: (1) returns 200 only if all critical dependencies are reachable; (2) returns the check results as JSON for debugging; (3) completes in <500ms; (4) never logs at INFO level (it's called every 5 seconds — logs would drown real application logs). Kubernetes distinguishes liveness (is the app running?) from readiness (is the app ready to serve traffic?). Never combine these — a slow DB shouldn't kill a pod.

It auto-scales to handle sudden traffic spikes without any pre-warming (unlike the legacy Classic LB, which needed pre-warming requests). Internally, ALB nodes themselves are behind a Network Load Balancer for multi-AZ distribution. ALB supports: weighted target groups (canary), Lambda as a target (serverless backends), gRPC, and WebSocket protocol upgrades.

The 80/20 Rule of Caching

In most read workloads, 80% of reads hit 20% of the data (Pareto principle). Caching that 20% (the "hot set") eliminates 80% of your DB load. Identify your hot set with a read-frequency histogram. Start with a small cache (even 1% of your data may be enough to capture 80% of reads).

True LRU on every access requires updating a linked list — expensive at Redis's million ops/sec throughput. Cache Problems and Solutions

Cache Stampede (Dog-Piling)

A cached item expires. Simultaneously, 10,000 requests arrive and all miss the cache. All 10,000 go to the DB simultaneously. The DB is overwhelmed.

Solutions:

  • Probabilistic early recomputation: Re-cache slightly before expiry with probability proportional to time-to-expiry. One request rebuilds while others still serve the old value.
  • Mutex/lock: First miss acquires a distributed lock, recomputes, populates cache. Others wait then hit the warm cache.
  • Stale-while-revalidate: Serve stale data; one background thread recomputes. No stampede possible.

Cache Penetration

Requests for keys that never exist in DB or cache bypass the cache on every request, hammering the DB. Classic DDoS vector: query non-existent user IDs.

Solutions:

  • Cache null results: Cache user:99999 → NULL with a short TTL. Future misses are cache hits.
  • Bloom Filter: In-memory probabilistic set membership. If Bloom Filter says "definitely not in DB," skip DB entirely. Instagram uses Bloom Filters for non-existent user lookups.

Cache Avalanche

All cached items expire at the same time (e.g., everything was set with TTL=3600 at 9am → all expire at 10am). Massive cache miss simultaneously.

Solutions:

  • Jitter TTL: TTL = base_ttl + random(0, base_ttl * 0.2). Spreads expiry across time.
  • Layered TTL: Different cache tiers with different TTLs prevent all-at-once expiry.

Cache Coherence

Multiple caching nodes holding different versions of the same data.

Solutions:

  • Write-through: Update cache and DB atomically on every write.
  • Event-driven invalidation: Write → Kafka event → cache invalidation subscriber.
  • TTL-based convergence: Accept brief inconsistency; short TTL bounds staleness.

Redis Deep Dive

Redis is single-threaded but fast
Redis processes commands in a single thread (+ I/O threads in Redis 6+). No locking contention. All operations are O(1) or O(N) on data structure size — predictable latency. ~100K–1M ops/sec per node (benchmark: redis-benchmark -n 1000000). Max RAM: limited to server memory. Typical: 16–128GB instances in production. At Twitter: 8,000+ Redis instances managing session data, rate limits, and real-time counters.
Redis Cluster for horizontal scaling
Redis Cluster shards keyspace into 16,384 slots across N primary nodes. Each primary has 1+ replicas. Clients use cluster-aware libraries (redis-py, Jedis cluster mode) that route to the correct shard. Resharding is online — no downtime. Redis Cluster handles ~1 million ops/sec across a 6-node cluster (3 primary + 3 replica).
Redis Persistence: RDB vs. AOF
RDB (snapshot): Point-in-time snapshot every N minutes. Fast recovery, smaller files. Data loss: up to N minutes of writes. Good for: cache (some data loss acceptable).
AOF (Append-Only File): Every write command logged. Recovery by replaying log. Can sync every write (fsync=always: zero data loss, low throughput) or every second (fsync=everysec: max 1s loss, high throughput). Good for: session store, pub/sub, durable cache.
Hybrid: AOF + RDB — fast load from RDB, then replay AOF tail. Default in Redis 7+.

Object Storage: S3 Architecture & Design Decisions

Amazon S3 is one of the most studied distributed systems. Understanding how it works reveals fundamental distributed storage patterns.

Key-Value Namespace
S3 objects are stored by a flat key (e.g., photos/user42/profile.jpg). There are no real directories — the "/" is just part of the key name. S3 partitions the keyspace by prefix hash, so keys with the same prefix go to the same partition. Implication: If you name all keys with a date prefix (2024-01-15-image.jpg), all January keys hit the same partition → hot partition. Add a random prefix hash to distribute: a7f3/2024-01-15-image.jpg.
Durability: 11 Nines (99.999999999%)
S3 achieves this by storing data in multiple AZs using erasure coding. An object is split into chunks and encoded with parity such that it can be reconstructed even if multiple chunks are lost. This is far cheaper than 3× full replication while providing stronger durability.
Eventual Consistency (Historically) → Strong Now
Until 2020, S3 offered only eventual consistency for LIST operations — a PUT followed immediately by GET/LIST might not return the new object. AWS moved S3 to strong read-after-write consistency in December 2020, at no performance cost. A key lesson: eventual consistency can sometimes be eliminated without sacrificing performance if the architecture allows it.
S3 Pricing Levers
S3 Standard ($0.023/GB) → S3-IA ($0.0125/GB) → S3 Glacier ($0.004/GB) → S3 Glacier Deep Archive ($0.00099/GB). Lifecycle policies auto-tier objects. Netflix saves ~$20M/year by tiering old content to Glacier.

SQL vs NoSQL

SQL (Relational Databases)

  • Structure: Tables with rows and columns; strict schema enforced on write
  • Query language: SQL — declarative, standardized, extremely expressive for joins and aggregations
  • Relationships: First-class support via foreign keys, joins, and referential integrity
  • Transactions: Full ACID guarantees
  • Scaling: Vertical (primary); horizontal sharding is possible but complex
  • Examples: PostgreSQL, MySQL, Oracle, SQL Server, SQLite
  • Best for: Financial systems, e-commerce, ERP, any domain requiring complex joins and strong consistency

NoSQL (Non-Relational Databases)

  • Structure: Varies: documents, key-value pairs, wide columns, graphs
  • Query language: Database-specific APIs; no universal standard
  • Relationships: Denormalized; relationships modeled through embedding or application-level joins
  • Transactions: Varies: many offer at-least-document ACID; distributed ACID is limited
  • Scaling: Designed for horizontal scaling from the ground up
  • Examples: MongoDB, Cassandra, Redis, DynamoDB, Neo4j
  • Best for: High-write workloads, flexible schemas, global distribution, specialized access patterns

ACID Transactions

ACID is an acronym describing the properties that guarantee database transactions are processed reliably, particularly in the event of errors, power failures, and concurrent access.

Atomicity
A transaction is treated as a single unit. Either all of its operations succeed and are committed, or none of them are. There is no partial success. If a transaction transfers money and the debit succeeds but the credit fails, atomicity ensures the debit is rolled back.
Consistency
A transaction brings the database from one valid state to another valid state. All integrity constraints (foreign keys, unique constraints, check constraints) are satisfied both before and after the transaction. A transaction that would violate a constraint is rejected entirely.
Isolation
Concurrent transactions execute as if they were executed serially. The intermediate state of a transaction is not visible to other transactions. The level of isolation can be tuned (Read Uncommitted, Read Committed, Repeatable Read, Serializable) to balance correctness and performance.
Durability
Once a transaction is committed, it remains committed even in the event of a system failure. The database uses write-ahead logging (WAL) and checkpointing to ensure committed data is persisted to durable storage and can be recovered after a crash.
Bank Transfer: All Four Properties
BEGIN;
  UPDATE accounts SET balance = balance - 500 WHERE id = 'alice';
  UPDATE accounts SET balance = balance + 500 WHERE id = 'bob';
COMMIT;
  • Atomicity: If the server crashes after the first UPDATE, the transaction is rolled back — Alice is not debited without Bob being credited.
  • Consistency: Total money in system is preserved (500 moved, not created or destroyed). Constraint: balance >= 0 prevents overdraft.
  • Isolation: A concurrent query checking Alice's balance sees either the original amount or the post-transfer amount, never the intermediate state.
  • Durability: After COMMIT returns, the transfer persists even if the server immediately loses power.

Relational Databases

Relational databases organize data into tables of rows and columns. Relations between entities are expressed through foreign keys. SQL provides a powerful declarative query language for selecting, joining, filtering, and aggregating data.

Strengths

  • Full ACID transactions, including multi-table transactions
  • Complex queries using JOINs, subqueries, window functions, CTEs
  • Referential integrity enforced by the database itself
  • Mature tooling, extensive operational knowledge, decades of battle-testing
  • Schema validation prevents bad data from entering the system

Limitations

  • Horizontal scaling is complex — sharding requires application changes and sacrifices some SQL features
  • Schema migrations on large tables require careful coordination (ALTER TABLE on 500M row table is dangerous)
  • Object-relational impedance mismatch: mapping object graphs to relational tables requires effort (solved partially by ORMs)

Key Systems

  • PostgreSQL: Most feature-rich open-source RDBMS. Excellent for complex queries, JSON support (JSONB), full-text search, geospatial (PostGIS). Default choice for new projects.
  • MySQL: Dominant in web applications (LAMP stack). InnoDB storage engine provides full ACID. Slightly simpler but less feature-rich than PostgreSQL.
  • Google Spanner: Globally distributed relational database with external consistency (effectively linearizable transactions across datacenters). Achieves CAP "CP with very high availability" through GPS clock synchronization (TrueTime).

Document Databases

Document databases store semi-structured data as documents (typically JSON or BSON). Each document is self-contained and can have a different structure. Documents are grouped in collections (analogous to tables). Documents can contain nested objects and arrays, allowing rich object graphs to be stored without joins.

When to Use

  • Data has variable attributes per record (different product types have different fields)
  • The natural representation is a document (blog post with metadata, e-commerce product with variants)
  • Rapid schema evolution is needed
  • The entire document is typically accessed together

Key-Value Stores

Key-value stores provide the simplest data model: every value is stored and retrieved by a unique key. They are extremely fast (O(1) average read/write) and horizontally scalable, but offer limited query capabilities.

Use Cases

  • Caching: Redis and Memcached are the canonical choices. Store expensive query results, API responses, computed values.
  • Session management: Store user sessions keyed by session ID. TTL ensures automatic cleanup.
  • Rate limiting: Atomic increment operations in Redis allow efficient rate limit counters.
  • Configuration and feature flags: Store and quickly retrieve configuration keyed by service or feature name.
  • Distributed locks: Redis' SETNX (set if not exists) provides atomic lock acquisition.

Wide-Column Databases

Wide-column databases (also called column-family databases) organize data by rows, where each row can have a different set of columns. Columns are stored together on disk, making range queries on column families very efficient. They are designed for massive write throughput and horizontal scalability.

Data Model

Data is organized as: keyspace → table → partition key → clustering key → column values. The partition key determines which node stores the row. The clustering key determines the ordering of rows within a partition.

Cassandra: Time-series user events
CREATE TABLE user_events (
    user_id   UUID,
    event_time TIMESTAMP,
    event_type TEXT,
    metadata  MAP<TEXT, TEXT>,
    PRIMARY KEY (user_id, event_time)
) WITH CLUSTERING ORDER BY (event_time DESC);

-- This allows highly efficient queries:
SELECT * FROM user_events
WHERE user_id = 'abc123'
  AND event_time > '2024-01-01'
LIMIT 50;

All events for user 'abc123' are stored on the same partition (same node), making the range query a single-node sequential scan — extremely fast.

When to Use

  • Very high write throughput (millions of writes per second)
  • Time-series or append-only data
  • Global distribution with multi-region writes
  • Read patterns are known and involve partition + range scans

Graph Databases

Graph databases store data as nodes (entities) and edges (relationships), with properties on both. They are optimized for traversing relationships — queries that require following many hops between connected data. In relational databases, the same query would require multiple expensive JOIN operations.

Strengths

  • Relationship traversal is O(number of edges traversed), not O(table size)
  • Natural modeling for highly connected domains
  • Pattern matching on relationship structures
Neo4j Cypher: Shortest path between people
MATCH path = shortestPath(
  (alice:Person {name: 'Alice'})-[:KNOWS*]-(bob:Person {name: 'Bob'})
)
RETURN path, length(path) AS degrees_of_separation

Finding the shortest path in a social graph. Equivalent SQL would require recursive CTEs and is often impractical for large graphs.

Use Cases

  • Social networks (friends-of-friends, recommendations)
  • Fraud detection (detect suspicious transaction patterns)
  • Knowledge graphs (entity relationships, ontologies)
  • Network and IT operations (dependency graphs)
  • Recommendation engines

Time Series Databases

Time series databases are optimized for storing and querying sequences of time-stamped data points. They provide efficient compression of timestamped numeric data, built-in time-based aggregation functions, and are designed for extremely high write throughput of append-only data.

Key Features

  • Automatic rollup and downsampling: Aggregate raw data into hourly/daily summaries to reduce storage.
  • Retention policies: Automatically delete old raw data while keeping downsampled summaries.
  • Efficient range queries: Query data between two timestamps efficiently.
  • High write throughput: Handle millions of data points per second.
InfluxDB: IoT sensor query
-- Average temperature per 5-minute window over last 24 hours
SELECT MEAN("temperature") AS avg_temp
FROM "sensor_readings"
WHERE "sensor_id" = 'sensor_001'
  AND time >= now() - 24h
GROUP BY time(5m)

Examples: InfluxDB, TimescaleDB (PostgreSQL extension), Prometheus (optimized for metrics), Apache Druid, QuestDB

Full-Text Search Engines

Full-text search engines are optimized for searching within text content — handling natural language, fuzzy matching, relevance ranking, and stemming. They are not primary databases; they are used alongside relational or document databases to provide rich search capabilities.

How They Work

Text is tokenized, normalized (lowercased, stemmed), and stored in an inverted index: a mapping from each unique term to the list of documents containing it. Queries look up terms in the index and compute relevance scores (TF-IDF, BM25) to rank results.

Capabilities

  • Full-text search with relevance ranking
  • Fuzzy matching (handles typos: "seach" → "search")
  • Faceted search (filter and count by category, price range, etc.)
  • Autocomplete and type-ahead
  • Geospatial search
  • Log analysis (Elasticsearch as part of ELK stack)

Examples: Elasticsearch, Apache Solr, Typesense, Meilisearch, Algolia (managed)

Vector Databases

Vector databases store high-dimensional numerical vectors (embeddings produced by machine learning models) and support efficient approximate nearest-neighbor (ANN) search — finding vectors most similar to a query vector.

Why They Matter

Modern ML models (BERT, GPT, CLIP, Stable Diffusion) encode semantic meaning into vectors. Searching by vector similarity enables semantic search ("find documents about financial risk" even if those exact words don't appear), image similarity, recommendation systems, and retrieval-augmented generation (RAG) for LLMs.

Indexing Algorithms

  • HNSW (Hierarchical Navigable Small World): Builds a multilayer graph structure. O(log n) query time. High memory usage. Best accuracy/speed tradeoff. Used by Pinecone, Weaviate, Qdrant.
  • IVF (Inverted File Index): Clusters vectors; searches only nearby clusters. Lower memory. Used by Faiss.
  • ANNOY: Tree-based index built by Spotify. Low latency, read-optimized.

Examples: Pinecone, Weaviate, Qdrant, Chroma, Milvus, pgvector (PostgreSQL extension)

B-Tree vs. LSM-Tree: The Fundamental Storage Engine Divide

B-Tree (Read-Optimized)

  • Data stored in balanced tree of fixed-size pages (~4KB–16KB each)
  • In-place updates — modify existing page on disk
  • Read: O(log N) — follow pointers from root to leaf
  • Write: O(log N) — but may trigger page splits + WAL write
  • Random I/O pattern — reads scattered across disk

Used by: PostgreSQL, MySQL (InnoDB), SQLite, Oracle, SQL Server

Sweet spot: Read-heavy OLTP, under ~10K writes/sec per node

LSM-Tree (Write-Optimized)

  • All writes go to memory (MemTable), then sequential SSTable files
  • No in-place updates — appends only, compaction merges periodically
  • Write: O(1) amortized — always sequential, ultra-high throughput
  • Read: more expensive — must check MemTable + multiple SSTables
  • Uses Bloom Filters to avoid reading SSTables that don't contain the key

Used by: Cassandra, RocksDB, LevelDB, HBase, InfluxDB, Kafka log

Sweet spot: Write-heavy workloads, time-series, IoT, >100K writes/sec

Write-Ahead Log (WAL): The Crash Recovery Backbone

What is the WAL?
Before any data page is modified, the change is written to a sequential append-only log (the WAL). On crash, the database replays the WAL to recover to a consistent state. The WAL is why databases can guarantee durability (the 'D' in ACID) even without fsync on every data page write.
Why sequential writes are critical
Sequential HDD writes: ~100–200 MB/s. Random HDD writes: ~0.5–1 MB/s (100–400× slower). By making the WAL sequential (always append to one file), PostgreSQL achieves predictable, fast durability writes regardless of the random I/O needed for the actual B-Tree pages.
WAL and Replication
PostgreSQL streaming replication works by shipping WAL records to replicas in real time. The replica replays the WAL, stay in sync. This is how you get a hot standby with <1 second replication lag. WAL decoding (logical replication) lets you also stream changes to Kafka for change data capture (CDC).

MVCC: How Databases Handle Concurrent Reads and Writes

Multi-Version Concurrency Control (MVCC) is how PostgreSQL, MySQL InnoDB, and Oracle allow readers to never block writers and writers to never block readers. Each row keeps multiple versions. Each transaction sees a snapshot of the DB at its start — no row-level read locks needed.

How PostgreSQL MVCC works
Every row has a xmin (transaction that created it) and xmax (transaction that deleted/updated it). A SELECT sees all rows where xmin <= my_txn_id < xmax. Updates create a NEW row version; the old version stays for in-flight transactions. VACUUM periodically reclaims old row versions (dead tuples). High update load + delayed VACUUM = table bloat.

Query Execution: What EXPLAIN ANALYZE Tells You

How to Read a Query Plan

Run EXPLAIN (ANALYZE, BUFFERS) SELECT ... in PostgreSQL. Look for:

  • Seq Scan on large table → missing index. Add one.
  • Nested Loop with large outer set → consider Hash Join if both sides are large.
  • High buffer hits from shared_buffers → good (data is cached in RAM). High disk reads → increase shared_buffers or add RAM.
  • Rows estimate vs. actual huge mismatch → stale statistics. Run ANALYZE.
Real-world: Shopify's database optimizations
Shopify runs one of the largest Rails+MySQL stacks in the world (~$7.5B GMV/day through a monolith). Key lessons: (1) every query must have an index — no full-table scans in production; (2) use covering indexes to avoid secondary row lookups (index-only scans); (3) use pt-query-digest to identify the top 10 slow queries — fix those before adding hardware; (4) aggressively denormalize read-heavy tables with background jobs to maintain derived data.

Indexing

An index is a separate data structure (typically a B+ tree) that maintains a sorted copy of one or more columns, enabling the database to locate rows without scanning the entire table.

How Indexes Improve Query Performance

Without an index on email, finding a user requires scanning every row in the table — O(n). With a B+ tree index, the lookup is O(log n), and for a table with 100 million rows, this can mean the difference between 100 million disk reads and 3–4 disk reads.

Types of Indexes

  • B+ tree index (default): Good for equality (=), range (>, <, BETWEEN), prefix (LIKE 'abc%'), and ORDER BY queries.
  • Hash index: O(1) equality lookups. Cannot support range queries. Useful for exact-match lookups like session ID lookups.
  • Composite index: Index on multiple columns (a, b, c). Can satisfy queries on a, a,b, or a,b,c but not b alone (leftmost prefix rule).
  • Covering index: An index that contains all columns needed to satisfy a query, so the database never needs to access the table rows (index-only scan).
  • Partial index: Index only rows matching a condition. Example: index only active users. Smaller and faster than full index for selective queries.
  • GIN/GiST index (PostgreSQL): For full-text search, JSONB, arrays, and geospatial data.

Index Tradeoffs

  • Each index increases write time (insert, update, delete must update all indexes on affected columns).
  • Indexes consume storage (often 10–30% of table size per index).
  • Too many indexes cause query planner confusion and slow writes more than they help reads.
Index Selection Guidelines
  • Always index foreign key columns (prevents full table scans on joins)
  • Index columns used in WHERE clauses of frequent queries
  • Index columns used in ORDER BY or GROUP BY
  • Do not index columns with low cardinality (e.g., boolean, status with 3 values) unless used as part of a selective composite index
  • Use EXPLAIN / EXPLAIN ANALYZE to verify queries actually use indexes

Query Optimization

Query optimization involves rewriting queries to use indexes efficiently, avoiding common anti-patterns, and ensuring the query planner has accurate statistics to generate optimal execution plans.

Common Anti-Patterns and Fixes

-- ANTI-PATTERN: Function on indexed column (breaks index use)
SELECT * FROM orders WHERE YEAR(created_at) = 2024;

-- FIX: Range scan (index-friendly)
SELECT * FROM orders
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';

-- ANTI-PATTERN: N+1 queries (query per row)
users = db.query("SELECT * FROM users LIMIT 100")
for user in users:
    orders = db.query("SELECT * FROM orders WHERE user_id = ?", user.id)
-- Executes 1 + 100 = 101 queries

-- FIX: Single JOIN query
SELECT u.*, o.*
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
LIMIT 100;

-- ANTI-PATTERN: SELECT * (fetches unused columns, wider rows)
SELECT * FROM products;

-- FIX: Select only needed columns
SELECT id, name, price, stock FROM products;

-- ANTI-PATTERN: Implicit type conversion breaks index
SELECT * FROM users WHERE id = '12345';  -- id is INT, comparing to VARCHAR

-- FIX: Match types
SELECT * FROM users WHERE id = 12345;

EXPLAIN Plans

Use EXPLAIN ANALYZE in PostgreSQL or EXPLAIN in MySQL to see the query execution plan. Key things to look for:

  • Seq Scan: Full table scan — typically bad on large tables. Indicates missing index or non-selective condition.
  • Index Scan: Uses B-tree index. Good.
  • Index Only Scan: Fully covered by index. Best case.
  • Nested Loop vs Hash Join vs Merge Join: Different join algorithms with different performance characteristics.
  • Actual rows vs Estimated rows: Large discrepancy means stale statistics — run ANALYZE to update.

Read Replicas

Read replicas are copies of the primary database that receive a continuous stream of changes from the primary and can serve read queries. Since most applications are read-heavy (often 90%+ reads), distributing read traffic across multiple replicas dramatically increases read capacity without affecting write performance.

Replication Process

  1. Application writes to the primary.
  2. Primary writes to its WAL.
  3. WAL changes are streamed to replicas (streaming replication).
  4. Replicas apply the WAL changes to their local copy.
  5. Read queries are directed to replicas by the application or a read-aware connection pool.

Replication Lag

Replicas are typically slightly behind the primary (seconds to milliseconds under normal load). Applications must account for this:

  • Reads that must reflect the most recent writes should go to the primary.
  • Reads tolerant of slight staleness (user list, product catalog) can go to replicas.
  • After writing, a subsequent read may see stale data if routed to a replica. Pattern: route reads to primary for a short window after a user's own writes.

Denormalization

Normalization eliminates redundancy to ensure data integrity. Denormalization deliberately introduces redundancy to reduce the number of joins required for common queries, trading write complexity for read performance.

Normalized Schema

orders      (order_id, user_id, product_id, amount)
users       (user_id, name, email)
products    (product_id, title, category)

-- Every order query requires JOINs:
SELECT o.*, u.name, p.title
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN products p ON o.product_id = p.id;

Denormalized Schema

orders (
  order_id,
  user_id,    user_name,    -- duplicated
  product_id, product_title,-- duplicated
  amount
)

-- No joins needed:
SELECT * FROM orders WHERE order_id = 123;

Tradeoff: if a user changes their name, all their orders must be updated too.

Materialized Views

A materialized view is a pre-computed, physically stored result of a query. Unlike a regular (virtual) view which re-executes the query on each access, a materialized view stores the results and must be explicitly or automatically refreshed when the underlying data changes.

-- Create materialized view: daily revenue by product category
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT
    DATE_TRUNC('day', created_at) AS day,
    category,
    SUM(amount) AS revenue,
    COUNT(*) AS order_count
FROM orders
JOIN products ON orders.product_id = products.id
GROUP BY day, category;

-- Index the materialized view for fast queries
CREATE INDEX ON daily_revenue (day, category);

-- Fast query — no aggregation at query time
SELECT * FROM daily_revenue
WHERE day = '2024-01-15';

-- Refresh periodically (can be automated via cron or trigger)
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;

Use cases: Analytics dashboards, aggregate reports, denormalized join results. Not suitable for data that must be absolutely real-time.

Connection Pooling

Establishing a database connection is expensive: it involves TCP handshake, authentication, session initialization, and memory allocation on the database server. Under high traffic, creating a new connection per request wastes time and exhausts database connection limits.

A connection pool maintains a pool of open, pre-established connections. When an application request needs a database connection, it borrows one from the pool, uses it, and returns it. Other requests can reuse the same physical connection.

Pool Configuration

  • Pool size: Too small → requests queue waiting for connections. Too large → database overloaded with concurrent queries. Typical rule: pool size = (core_count × 2) + effective_spindle_count per application server.
  • Maximum wait time: If no connection is available within this time, return an error rather than waiting indefinitely.
  • Health checking: Test idle connections before handing them to callers.

Tools: PgBouncer (PostgreSQL), ProxySQL (MySQL), HikariCP (Java), asyncpg pool (Python), ActiveRecord connection pool (Ruby on Rails)

Vertical Partitioning

Vertical partitioning splits a table by columns — separating "hot" (frequently accessed) columns from "cold" (rarely accessed or large) columns into separate tables, joined by the primary key.

-- Before: one wide table
users (
    id, name, email, password_hash,  -- Hot: accessed on every login
    bio TEXT,                         -- Cold: only shown on profile page
    full_resume TEXT,                 -- Cold: rarely accessed
    raw_settings JSONB               -- Cold: large blob
)

-- After: vertically partitioned
users_core (id, name, email, password_hash)   -- Fits in cache, fast
users_profile (user_id, bio, full_resume, raw_settings)  -- Loaded on demand

Benefits: Narrower rows fit more records per page, improving cache efficiency and scan speed. Frequently accessed core data does not need to be loaded alongside large cold data.

Sharding

Sharding (horizontal partitioning) distributes rows of a table across multiple independent database instances (shards), each owning a subset of the data. Each shard is a fully functional, independent database with its own CPU, memory, disk, and connection pool.

Sharding Strategies

  • Range-based sharding: Partition by value ranges (user_id 1–1,000,000 → Shard 1; 1,000,001–2,000,000 → Shard 2). Simple, supports range queries within a shard. Risk: uneven distribution if data is not uniformly distributed across the range.
  • Hash-based sharding: shard = hash(shard_key) % num_shards. Uniform distribution. Consistent hashing variant minimizes remapping when shard count changes. Range queries across shards are inefficient.
  • Directory-based sharding: A separate lookup service maps entity IDs to shard numbers. Most flexible (can move entities between shards). Requires an additional lookup per request.
  • Geo-based sharding: Route data by geographic region. Users in EU → EU shard (for data residency compliance). Users in US → US shard.

Choosing the Shard Key

The shard key is the most important architectural decision in a sharded system. A good shard key:

  • Has high cardinality (many distinct values)
  • Distributes data and traffic evenly across shards (avoids hotspots)
  • Aligns with your most common query patterns (queries against the shard key are single-shard)
  • Rarely changes (changing the shard key requires re-sharding)
Instagram sharding strategy

Instagram shards by user_id. This means all of a user's data (posts, likes, followers) lives on the same shard, making per-user queries single-shard. The shard key is computed using the lower 13 bits of the user ID after masking.

Challenges of Sharding

  • Cross-shard queries: Queries that need data from multiple shards must be executed on each relevant shard and the results merged by the application — expensive and complex.
  • Cross-shard joins: Joins across shards are not supported by the database — must be performed application-side.
  • Cross-shard transactions: Two-phase commit is required for atomic transactions spanning multiple shards, adding latency and complexity.
  • Resharding: When a shard is full, adding new shards requires migrating data — a complex, slow, and risky operation.
  • Hotspots: If one shard key value receives disproportionate traffic (e.g., a celebrity user), that shard becomes a bottleneck. Mitigations: virtual sharding, prefix injection to distribute writes.

Data Compression

Data compression reduces the on-disk size of database files, which reduces storage cost, increases effective cache size (compressed data fits more in buffer pool), and reduces I/O bandwidth requirements — which can actually improve performance despite the CPU cost of decompression.

Compression Types

  • Row-level compression: Each row is compressed individually. Low CPU overhead. Moderate compression ratio.
  • Page-level compression: Entire database pages (8KB–32KB) are compressed as a unit. Better compression ratio than row-level due to cross-row pattern matching.
  • Column-store compression: Columnar databases (Redshift, BigQuery) store all values of a column together. Since values within a column are often similar, compression ratios of 10:1 to 20:1 are common (vs 2:1–4:1 for row stores).
  • Dictionary encoding: Store repeated string values as integer codes. One row per unique string. Extremely effective for low-cardinality string columns.

What is an API?

An API (Application Programming Interface) is a defined contract that specifies how software components should communicate. In the context of system design, APIs define how clients (web browsers, mobile apps, other services) interact with servers. A well-designed API is consistent, predictable, secure, and versioned.

API Design Principles

  • Consistency: Naming conventions, error formats, and response structures should be uniform across all endpoints.
  • Backward compatibility: Existing clients must not break when the API evolves. Add fields, do not remove them. Version breaking changes.
  • Least surprise: Behavior should match what the name and documentation imply.
  • Proper error responses: Return informative error codes and messages, not generic 500 errors.
  • Security by default: Authenticate and authorize all sensitive endpoints. Validate all input.

Idempotency

An operation is idempotent if performing it multiple times produces the same result as performing it once. This is critical for reliability: in distributed systems, network failures can cause clients to retry requests without knowing if the original succeeded.

HTTP Method Idempotency

Method Idempotent Safe (read-only) Notes
GET Yes Yes Read only, no side effects
HEAD Yes Yes Like GET, returns only headers
OPTIONS Yes Yes Describes allowed methods
PUT Yes No Replace resource; same payload → same result
DELETE Yes No Delete twice → still deleted (may return 404 on second)
POST No No Creates new resource each time
PATCH Not always No Depends on implementation

Idempotency Keys

For non-idempotent operations (like POST to create a payment), clients can include an idempotency key — a unique identifier for the request. The server stores the key and the result of the first execution. If the same key is received again, the server returns the stored result without re-executing.

POST /api/payments HTTP/1.1
Idempotency-Key: a8098c1a-f86e-11da-bd1a-00112444be1e
Content-Type: application/json

{ "amount": 99.99, "currency": "USD", "card": "tok_visa" }

Server implementation:

def create_payment(idempotency_key, payload):
    # Check if this request was already processed
    cached = redis.get(f"idem:{idempotency_key}")
    if cached:
        return json.loads(cached)   # Return stored result

    # Process for the first time
    result = payment_processor.charge(payload)

    # Store result keyed by idempotency key (TTL = 24 hours)
    redis.setex(f"idem:{idempotency_key}", 86400, json.dumps(result))
    return result

API Architectural Styles

Different API paradigms make different tradeoffs between flexibility, performance, simplicity, and tooling.

REST API Design

REST (Representational State Transfer) is an architectural style that uses HTTP methods and URLs to create a uniform interface for accessing and manipulating resources. REST is stateless — each request contains all information needed to process it.

REST Constraints

  • Stateless: Server holds no session state. All state is in the request.
  • Uniform interface: Resources identified by URIs; resources manipulated through representations; self-descriptive messages; HATEOAS.
  • Layered system: Client cannot tell whether it's communicating with an origin server or a middleman (cache, load balancer).
  • Cacheable: Responses must indicate if they are cacheable.

Resource-Based URL Design

# Resources are nouns, not verbs
GET    /users              — List users
GET    /users/123          — Get user 123
POST   /users              — Create user
PUT    /users/123          — Replace user 123
PATCH  /users/123          — Partially update user 123
DELETE /users/123          — Delete user 123

# Nested resources for relationships
GET    /users/123/orders   — Orders belonging to user 123
POST   /users/123/orders   — Create order for user 123
GET    /users/123/orders/456 — Specific order for specific user

# Avoid verbs in URLs:
POST /users/123/activate   — Acceptable for actions with no resource representation
GET  /search?q=term        — Query parameters for filtering/searching

REST API Best Practices

  • Use plural nouns for collections (/users, not /user)
  • Return appropriate HTTP status codes (201 for created, 204 for no content)
  • Provide pagination for list endpoints (?page=2&limit=20 or cursor-based)
  • Version your API (/api/v1/ or Accept: application/vnd.api+json;version=1)
  • Return consistent error format with machine-readable error codes
  • Use HTTPS always

GraphQL Deep Dive

GraphQL is a query language for APIs and a runtime for executing those queries. Rather than exposing a collection of fixed endpoints that return predetermined data shapes, GraphQL exposes a single endpoint where clients specify exactly what data they need using a typed query language.

Core Problems GraphQL Solves

  • Over-fetching: REST endpoints return a fixed data shape. Fetching GET /users/123 returns all user fields even if you only need name and email.
  • Under-fetching (N+1 requests): Getting a list of posts with each author's name requires one request for posts, then one per post for author details.
  • Client-specific data requirements: Mobile and web clients may need different subsets of data but REST uses the same endpoint for both.
# Single GraphQL query — client specifies exactly what it needs
query {
  user(id: "123") {
    name
    email
    recentOrders(limit: 5) {
      id
      total
      status
      items {
        productName
        quantity
      }
    }
  }
}

# Server returns exactly this structure — no more, no less

GraphQL Schema

GraphQL APIs are strongly typed. The schema defines all types, queries, mutations, and subscriptions, and serves as a contract between client and server. Introspection allows clients to query the schema itself, enabling powerful tooling (auto-generated documentation, type-safe client code).

type User {
  id: ID!
  name: String!
  email: String!
  orders(limit: Int = 10): [Order!]!
}

type Order {
  id: ID!
  total: Float!
  status: OrderStatus!
  items: [OrderItem!]!
}

enum OrderStatus { PENDING PROCESSING SHIPPED DELIVERED }

type Query {
  user(id: ID!): User
  users(page: Int, limit: Int): [User!]!
}

type Mutation {
  createUser(name: String!, email: String!): User!
  updateOrder(id: ID!, status: OrderStatus!): Order!
}

type Subscription {
  orderStatusChanged(orderId: ID!): Order!
}

Tradeoffs

Advantages

  • Client fetches exactly what it needs — no over/under-fetching
  • Single endpoint simplifies API versioning
  • Strong typing catches client/server mismatches at build time
  • Introspection enables self-documenting APIs
  • Subscriptions provide real-time capability

Challenges

  • HTTP-level caching is harder (single endpoint, complex queries)
  • N+1 query problem if not handled with DataLoader batching
  • Complex queries can be expensive — need query cost analysis and rate limits
  • Steeper learning curve than REST
  • Not ideal for simple CRUD APIs where REST is simpler

Resilience Patterns: The Circuit Breaker

Named after the electrical circuit breaker: when a downstream service is failing, stop sending requests to it (open the circuit) to prevent cascading failures and allow it time to recover.

stateDiagram-v2 [*] --> Closed Closed --> Open: Failure threshold\nexceeded (e.g. 50% in 10s) Open --> HalfOpen: After reset timeout\n(e.g. 30 seconds) HalfOpen --> Closed: Test request succeeds HalfOpen --> Open: Test request fails note right of Closed: Normal operation\nAll requests pass note right of Open: STOP sending requests\nFail fast, return fallback note right of HalfOpen: Allow one trial request\nto test recovery
Why Circuit Breakers Matter: Amazon's 2012 Outage
In 2012, an Amazon service experienced cascading failures because one upstream dependency slowed, causing callers to queue requests, exhausting thread pools, causing more timeouts, causing more requests to queue — a cascade. Circuit breakers prevent this: when the upstream is slow, fail fast immediately rather than queuing indefinitely. Fail fast = bounded latency.
Netflix Hystrix → Resilience4j
Netflix invented Hystrix for circuit breaking in their Java services. It became the industry standard. Hystrix is now in maintenance mode; Resilience4j is the successor. Polly is the .NET equivalent. At Netflix, wrapping each external call in a circuit breaker reduced cascading failures from seconds of outage to milliseconds of fallback responses. Netflix's degraded experience (low-res video, no personalization, cached recommendations) is graceful degradation via circuit breakers.
Parameters to tune
Failure rate threshold: 50% of last N calls failed → open. Slow call threshold: 50% of calls >2s → also open. Reset timeout: Try again after 30s in OPEN state. These must be tuned per service — too sensitive and you'll open on transient blips; too loose and the cascade happens before the breaker opens.

Retry Strategies: When and How to Retry

Naive Retry (DO NOT do this)

  • Retry immediately on failure, N times
  • If 100 clients all retry simultaneously → thundering herd
  • Can amplify load on an already-failing service by 100×
  • Makes cascading failures worse, not better

Exponential Backoff + Jitter (correct approach)

  • Retry delay doubles each attempt: 100ms, 200ms, 400ms, 800ms…
  • Add jitter: random ±25% to each delay to desynchronize clients
  • Cap at max delay (e.g., 30 seconds)
  • Use idempotent requests only — never retry non-idempotent (POST payments)
AWS SDKs Use Exponential Backoff + Jitter by Default

AWS's "Retry Architecture" paper (2015) showed that adding jitter reduced retry-storm magnitude by 50× compared to fixed backoff. All AWS SDKs implement this. When writing your own retry logic, use: sleep(pow(2, attempt) * 100ms + random(0, 100ms)).

Bulkhead Pattern: Isolating Failures

Named after compartments in a ship's hull — if one compartment floods, the others stay dry. In software: isolate resources (thread pools, connection pools) per downstream dependency.

Thread Pool Bulkhead
Give each downstream service its own thread pool. Service A: 20 threads. Service B: 20 threads. If Service B starts hanging, only Service B's 20 threads fill up — not all 200 shared threads. Service A continues operating normally. Without bulkheads, slow Service B fills all shared threads, making the entire application unresponsive to all requests.
Semaphore Bulkhead
Limit concurrent requests to a service with a counting semaphore (N permits). Faster than thread pool isolation, but doesn't protect against slow calls blocking the calling thread. Used for non-blocking async calls where thread pool isolation is overkill.

Authentication and Authorization

Authentication vs Authorization

Authentication (AuthN)
Verifying who the entity is. Answering: "Are you really Alice?" Methods: password + username, cryptographic certificates, biometrics, hardware tokens.
Authorization (AuthZ)
Determining what the authenticated entity is allowed to do. Answering: "Alice, can you delete this resource?" Methods: RBAC, ABAC, ACLs.
Sequence

Authentication always happens before authorization. You cannot determine what someone is allowed to do until you know who they are.

Session-Based Authentication (Stateful)

The server creates and stores a session object after successful login. A session ID is sent to the client (usually as an HTTP-only cookie). On subsequent requests, the client sends the session ID; the server looks it up in the session store to retrieve user context.

Flow

  1. Client sends credentials (username + password).
  2. Server authenticates credentials against database (compare bcrypt hash).
  3. Server creates session: stores session data in Redis keyed by session ID.
  4. Server sends session ID in Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax
  5. Client sends Cookie: session_id=abc123 on every request.
  6. Server looks up session in Redis to retrieve user identity and permissions.

Token-Based Authentication (Stateless)

After successful authentication, the server issues a signed token (typically a JWT) containing claims about the user. The client stores the token and includes it in subsequent requests. The server verifies the token's signature — no server-side storage needed.

JWT — JSON Web Tokens

A JWT is a compact, URL-safe token format consisting of three Base64URL-encoded parts separated by dots: header, payload, signature.

# Structure
header.payload.signature

# Header (algorithm + type)
{ "alg": "HS256", "typ": "JWT" }

# Payload (claims)
{
  "sub": "user_123",        # Subject (user ID)
  "name": "Alice Smith",
  "role": "admin",
  "iat": 1704067200,        # Issued at (Unix timestamp)
  "exp": 1704070800         # Expiration (Unix timestamp)
}

# Signature = HMAC-SHA256(
#     base64url(header) + "." + base64url(payload),
#     secret_key
# )

JWT Verification

The server verifies the token by recomputing the signature using the secret key and comparing it to the signature in the token. If they match, the token is authentic and unmodified. The server can then extract the claims from the payload without any database lookup.

Access Token + Refresh Token Pattern

  • Access token: Short-lived (15 minutes). Used for API requests. If compromised, exposure window is small.
  • Refresh token: Long-lived (7–30 days). Stored securely (HttpOnly cookie or secure storage). Used only to obtain new access tokens. Can be revoked by deleting from database.

OAuth 2.0 / OAuth2

OAuth 2.0 is an authorization framework that enables a third-party application (client) to obtain limited access to a user's account on a service (resource server), without the user sharing their credentials with the third party.

Authorization Code Flow (Most Secure — for Web Apps with Backend)

  1. User clicks "Login with Google" on your app.
  2. Your app redirects user to Google's authorization endpoint with client_id, redirect_uri, scope, and a state parameter (CSRF protection).
  3. User logs into Google and grants permission to your app.
  4. Google redirects back to your redirect_uri with a short-lived authorization code.
  5. Your backend exchanges the authorization code for an access token and optionally a refresh token, using the client secret (server-side only — never exposed to browser).
  6. Your app uses the access token to call Google APIs on the user's behalf.

Webhooks

Webhooks are HTTP callbacks: your server registers a URL with a third-party service; when an event occurs in that service, it sends an HTTP POST request to your URL with event data. Webhooks are server-to-server communication, not browser-based.

Key Design Considerations

  • Idempotency: The same webhook may be delivered more than once (the sender retries on network failure or timeout). Your handler must be idempotent — track processed event IDs.
  • Signature verification: The sender signs the payload with a shared secret. Always verify the signature before processing to prevent forged requests.
  • Fast response: Respond with 200 OK as quickly as possible (within 5–30 seconds, depending on provider). If processing is slow, queue the event and process asynchronously — otherwise the sender may time out and retry.
  • Failure handling: Senders typically retry with exponential backoff if they receive a non-2xx response. Return 5xx to trigger retry, not 4xx.

Synchronous vs Asynchronous Communication

Synchronous

The caller blocks and waits for the callee to respond before continuing. Tight coupling — if the callee is slow or down, the caller suffers.

  • Simpler to reason about (request-response pairs)
  • Immediate feedback on success or failure
  • Creates dependency chains — if payment service is slow, the order service is slow
  • Used for: user-facing operations requiring immediate response

Asynchronous

The sender dispatches a message and continues immediately. A separate process consumes and handles the message later.

  • Decouples producers and consumers
  • Resilient: messages are buffered if consumer is slow or down
  • Enables load leveling — absorb traffic spikes in the queue
  • More complex: error handling, retries, ordering, at-least-once delivery
  • Used for: background jobs, notifications, event processing

Message Queues

A message queue is a buffer that stores messages from producers until consumers are ready to process them. Producers and consumers are decoupled — they do not need to be available simultaneously.

Core Properties

  • Durability: Messages are persisted to disk. Even if the broker restarts, messages are not lost.
  • Acknowledgment: A message is not removed from the queue until the consumer explicitly acknowledges successful processing. This prevents message loss on consumer crash.
  • Ordering: Most queues deliver messages in FIFO order within a partition, though ordering guarantees vary by system.
  • Visibility timeout: When a consumer reads a message, it becomes invisible to other consumers for a period. If not acknowledged within that period, it becomes visible again (enabling retry on consumer crash).

Pub/Sub Pattern

In Pub/Sub (Publish/Subscribe), publishers send messages to a topic without knowing who will receive them. Multiple subscribers can independently receive copies of every message published to the topic. This enables fan-out — one event triggers multiple independent actions.

Message Queue (Point-to-Point)

  • One message → consumed by one consumer
  • Multiple competing consumers share the work
  • Load balancing between consumers
  • Use for: task distribution

Pub/Sub (Broadcast)

  • One message → delivered to all subscribers
  • Each subscriber receives its own copy
  • Independent processing per subscriber
  • Use for: event notifications, fan-out

Dead Letter Queues (DLQ)

A Dead Letter Queue is a separate queue where messages are routed after failing to be processed successfully after a configured number of retries. Instead of blocking the main queue or silently discarding failed messages, they are held in the DLQ for inspection and manual or automated remediation.

When a Message Goes to the DLQ

  • Processing has been retried more than the maximum configured times
  • The message has exceeded its maximum retention time in the queue
  • The message is unroutable (no matching consumer)
  • The consumer explicitly sends the message to the DLQ (e.g., malformed payload)

DLQ Operations

  • Alerting: Monitor DLQ size. Any message in the DLQ indicates a processing failure that needs investigation.
  • Inspection: Examine failed messages to diagnose bugs or data issues.
  • Replay: After fixing the bug, replay DLQ messages back to the main queue.

CDC is a pattern that captures changes (inserts, updates, deletes) in a database and publishes them as a stream of events. Rather than polling the database periodically or modifying application code to publish events, CDC reads the database's internal transaction log (e.g., PostgreSQL WAL, MySQL binlog) and converts log entries into events.

Delivery Semantics

Delivery semantics define the guarantee a messaging system provides about whether and how many times a message is delivered to a consumer.

Semantic Guarantee Implementation Risk Use case
At-most-once Delivered 0 or 1 times; may be lost Fire-and-forget, no ACK, no retry Message loss Logs, metrics where occasional loss is acceptable
At-least-once Delivered 1 or more times; never lost Retry on failure, ACK only on success Duplicate delivery Most use cases — combined with idempotent processing
Exactly-once Delivered exactly once; never lost, never duplicated Distributed transactions or idempotency keys + dedup High complexity, performance cost Financial transactions, exactly-once semantics in Kafka
Exactly-Once is Rare and Expensive

True exactly-once delivery across distributed systems is extremely difficult and imposes significant overhead. In practice, most systems implement at-least-once delivery and make consumer processing idempotent — i.e., processing the same message twice produces the same result as processing it once. This combination is simpler, more performant, and functionally equivalent to exactly-once for most use cases.

Event-Driven Architecture

In event-driven architecture, services communicate by emitting and consuming events rather than through direct API calls. An event represents something that happened — a fact about a past state change. Services react to events without needing to know which service produced them.

Event vs Command

Event

  • Describes something that happened: OrderPlaced, UserRegistered, PaymentFailed
  • Immutable fact — you cannot un-happen an event
  • Named in past tense
  • Producer does not know or care who processes it
  • Multiple consumers may react independently

Command

  • Requests something to happen: PlaceOrder, SendEmail, ProcessPayment
  • May be rejected or fail
  • Named in imperative form
  • Directed at a specific recipient
  • One receiver (typically)

CQRS — Command Query Responsibility Segregation

CQRS separates the model used for writing data (commands) from the model used for reading data (queries). These two responsibilities have fundamentally different requirements — writes need strong consistency and complex validation; reads need performance and flexible projections.

Architecture

# Write side (Command Model)
POST /orders
  → Validates business rules
  → Updates normalized write database
  → Publishes OrderCreated event

# Read side (Query Model) — separate database, optimized for reads
GET /orders/summary        → Returns pre-aggregated summary
GET /user/123/order-history → Returns denormalized view
GET /dashboard/stats        → Returns materialized analytics

# Synchronization
Event bus: OrderCreated → Update read model asynchronously

Benefits

  • Read and write stores can be scaled independently
  • Read models can be denormalized, cached, and optimized without affecting write integrity
  • Multiple read projections of the same data (different views for mobile vs desktop vs analytics)
  • Commands can enforce complex business invariants without sacrificing query performance

Costs

  • Eventual consistency between write and read models — reads may be slightly stale
  • More complex — two models to maintain, synchronization infrastructure
  • Justified primarily when read and write patterns differ significantly (e.g., 95% reads)

Event Sourcing

Event sourcing stores the complete history of changes to a domain object as an append-only sequence of events, rather than storing only the current state. The current state is derived by replaying events from the beginning (or from a snapshot).

Traditional State vs Event Sourcing

# Traditional: Only current state stored
accounts table: { id: 123, balance: 450.00 }

# Event sourcing: All events stored
events: [
  { type: "AccountOpened",     amount: 0,    ts: "2024-01-01" },
  { type: "MoneyDeposited",    amount: 500,  ts: "2024-01-15" },
  { type: "MoneyWithdrawn",    amount: 50,   ts: "2024-01-20" }
]
# Current balance = replay: 0 + 500 - 50 = 450

Advantages

  • Complete audit trail: Every change is recorded with full context. Invaluable for compliance, debugging, and customer support.
  • Time travel: Reconstruct the state at any point in time by replaying events up to that timestamp.
  • Event replay: If a bug is found in a read projection, fix the projection logic and rebuild it from events.
  • Natural fit with CQRS: Events are published to build multiple read projections.

Challenges

  • Querying current state requires replaying events (mitigated by snapshots — persist state periodically, replay only from last snapshot)
  • Event schema evolution — once events are stored, changing their schema is complex
  • Conceptual complexity — unfamiliar paradigm for most developers
  • Eventually consistent read models

Serverless Architecture

Serverless is a cloud execution model where the cloud provider dynamically manages infrastructure provisioning and scaling. Developers deploy functions (FaaS — Function as a Service), and the provider runs them in stateless compute containers that are created on demand and destroyed when idle.

Execution Model

  • Event-triggered: Functions are invoked by events — HTTP requests, queue messages, database changes, scheduled timers, file uploads.
  • Stateless: No state is preserved between invocations. External state (database, cache, object storage) must be used.
  • Ephemeral containers: Each invocation runs in a fresh (or reused) container. Local filesystem is temporary.
  • Automatic scaling: From 0 to millions of concurrent invocations. No capacity planning.
  • Pay-per-execution: Billed for compute time consumed, not for idle capacity.

Cold Start Problem

When a function has not been invoked recently, the provider must provision a new container, load the runtime, and initialize the function before execution. This cold start latency can range from 100ms (lightweight Node.js) to 10 seconds (Java with heavy JVM initialization). Mitigations: keep functions warm with scheduled pings, use provisioned concurrency (reserved warm containers), minimize function package size.

Peer-to-Peer Architecture

In P2P architecture, all nodes (peers) are functionally equivalent and can act as both client and server. There is no dedicated central server — peers directly communicate with each other, share resources, and form a self-organizing overlay network.

Structured vs Unstructured P2P

  • Unstructured P2P (BitTorrent): Peers connect randomly. Finding content requires flooding or random walk queries. Resilient but inefficient for search.
  • Structured P2P (Kademlia DHT): Peers and content are organized according to a distributed hash table. Any peer can be found in O(log N) hops. Used by BitTorrent DHT, IPFS, Ethereum peer discovery.
  • Hybrid P2P (early Spotify): Central servers handle discovery and metadata; data transfer is direct peer-to-peer. Combines manageability of central infrastructure with P2P efficiency for bulk transfer.

Service Discovery

In a dynamic environment where services are deployed as containers and instances are added or removed constantly, services cannot be reached at hardcoded IP addresses. Service discovery is the mechanism by which services find each other.

Client-Side Discovery

The client queries a service registry to get a list of available instances of the target service, then selects one using a load balancing strategy and calls it directly.

# Client code
instances = registry.get_instances("payment-service")
# → [{ host: "10.0.1.5", port: 8080 }, { host: "10.0.1.6", port: 8080 }]

selected = round_robin_select(instances)
response = http.post(f"http://{selected.host}:{selected.port}/charge", body)

Pros: No extra network hop (client calls service directly). Client controls load balancing logic.
Cons: Every client must implement discovery and load balancing logic. Client is coupled to the registry API. Used by: Netflix Ribbon + Eureka.

Server-Side Discovery

The client calls a fixed endpoint (load balancer or API gateway). The load balancer queries the registry and routes to an available instance. The client knows nothing about discovery.

Pros: Client is simple — no discovery logic. Load balancing is centralized.
Cons: Load balancer is an extra network hop. Load balancer must be highly available. Used by: Kubernetes Services, AWS ALB.

Service Registry Systems

  • Consul: Service registry with health checking, DNS interface, and KV store. Uses Raft for strong consistency. Widely used outside Kubernetes.
  • etcd: Strongly consistent distributed KV store. Kubernetes stores all cluster state in etcd.
  • Kubernetes Services + CoreDNS: Services are registered in etcd; CoreDNS answers DNS queries for service names within the cluster. Standard for containerized environments.
  • Eureka (Netflix): AP-mode service registry — favors availability over consistency. Instances self-register. Used in JVM-based microservices.

Circuit Breaker Pattern

The circuit breaker pattern prevents a service from repeatedly calling a downstream service that is failing, giving the failing service time to recover and preventing thread pool exhaustion from piling up slow calls.

States

  • Closed: Normal operation. Requests pass through. The circuit breaker counts failures. If the failure rate exceeds a threshold (e.g., 50% of last 10 requests), the circuit opens.
  • Open: All requests are rejected immediately without calling the downstream service. Returns a fast failure (or cached fallback) to the caller. After a timeout period (e.g., 30 seconds), transitions to half-open.
  • Half-Open: Allows a limited number of requests through as a probe. If they succeed, the circuit closes. If they fail, the circuit opens again.
stateDiagram-v2
  Closed --> Open : failure rate exceeds threshold
  Open --> HalfOpen : timeout expires (probe allowed)
  HalfOpen --> Closed : probe requests succeed
  HalfOpen --> Open : probe requests fail

Circuit breaker state machine

# Pseudo-implementation
class CircuitBreaker:
    def __init__(self, failure_threshold=5, timeout=30):
        self.state = "CLOSED"
        self.failure_count = 0
        self.failure_threshold = failure_threshold
        self.last_failure_time = None
        self.timeout = timeout

    def call(self, fn, *args):
        if self.state == "OPEN":
            if time.time() - self.last_failure_time > self.timeout:
                self.state = "HALF_OPEN"
            else:
                raise CircuitOpenError("Circuit is open")

        try:
            result = fn(*args)
            if self.state == "HALF_OPEN":
                self.state = "CLOSED"
                self.failure_count = 0
            return result
        except Exception as e:
            self.failure_count += 1
            self.last_failure_time = time.time()
            if self.failure_count >= self.failure_threshold:
                self.state = "OPEN"
            raise

Libraries: Hystrix (Netflix, JVM), Resilience4j (Java), Polly (.NET), go-resilience (Go), pybreaker (Python)

Bulkhead Pattern

The bulkhead pattern isolates components of an application into pools so that if one fails, the others continue functioning. Named after the bulkheads on a ship that contain flooding to a single compartment.

Thread Pool Isolation

Each downstream dependency gets its own thread pool. If the payment service is slow and its thread pool fills up, those threads cannot spill over and starve the threads handling other dependencies (order service, user service). The payment pool is the only casualty.

# Separate executors per downstream service
payment_executor  = ThreadPoolExecutor(max_workers=10)
inventory_executor = ThreadPoolExecutor(max_workers=20)
user_executor     = ThreadPoolExecutor(max_workers=15)

# If payment service hangs, only payment_executor fills up
# Other executors are unaffected
try:
    result = payment_executor.submit(call_payment_service, order).result(timeout=2)
except TimeoutError:
    return fallback_response()

Connection Pool Isolation

Similarly, database connection pools can be isolated per service or query type. Write operations get a separate pool from read operations; batch jobs get a separate pool from real-time requests.

Sidecar Pattern

The sidecar pattern places a helper container alongside the main application container, sharing the same network namespace and lifecycle. The sidecar handles infrastructure concerns so the application does not have to.

Common Sidecar Responsibilities

  • Proxy and traffic management: Envoy proxy intercepts all inbound and outbound network traffic, providing load balancing, retries, circuit breaking, and mTLS without application changes.
  • Log forwarding: Fluentd sidecar tails the application's log files and ships them to a central log aggregation system.
  • Metrics scraping: Prometheus exporter sidecar exposes application metrics in Prometheus format.
  • Configuration synchronization: Consul-template or Vault Agent sidecar writes secrets and configuration from the registry to the local filesystem where the application can read them.

Backend for Frontend (BFF) Pattern

Instead of a single general-purpose API serving all client types, the BFF pattern creates a dedicated backend for each type of client (mobile, web, partner API). Each BFF is tailored to its client's specific needs — data shape, bandwidth constraints, and interaction patterns.

Service Mesh

A service mesh is a dedicated infrastructure layer for managing service-to-service communication. Rather than implementing communication concerns (retries, timeouts, circuit breaking, mutual TLS, observability) in each service, the service mesh handles them via a data plane of sidecar proxies and a control plane that configures those proxies.

Components

  • Data plane: Sidecar proxies (Envoy) injected into each service pod. Intercept all inbound and outbound traffic. Enforce policy, collect telemetry.
  • Control plane: Centralized management system (Istio, Linkerd) that distributes configuration to all proxies — routing rules, security policies, health checking parameters.

Capabilities

  • Mutual TLS (mTLS) for all service-to-service communication — automatic, zero-configuration encryption and identity verification
  • Traffic management: canary deployments, A/B testing, traffic mirroring, fault injection
  • Observability: distributed tracing, per-service latency and error rate metrics automatically, without application code changes
  • Resilience: configurable retries, timeouts, circuit breaking at the proxy level

Strangler Fig Pattern

The Strangler Fig pattern provides a strategy for incrementally migrating a legacy monolith to a microservices architecture. Named after the strangler fig tree that grows around its host, eventually replacing it.

Process

  1. Introduce a facade: Place a routing layer (API gateway or reverse proxy) in front of the monolith. Initially it passes all traffic through unchanged.
  2. Identify a slice to extract: Choose a bounded context with clear boundaries (e.g., user authentication, notifications). Implement it as a new microservice.
  3. Route traffic to the new service: Update the facade to route the relevant paths to the new service. The monolith still handles everything else.
  4. Validate and remove: After the new service is proven in production, remove the corresponding code from the monolith.
  5. Repeat: Continue extracting slices until the monolith is empty or small enough to be acceptable.

Risk Management

  • Parallel running: Run the new service alongside the monolith logic, compare results, before switching traffic.
  • Canary routing: Route 5% of traffic to the new service, monitor, then gradually increase.
  • Feature flags: Control which users experience the new service.
  • Quick rollback: The facade makes it trivial to route all traffic back to the monolith if the new service has issues.

Database Indexing

An index is a data structure designed to improve the speed of data retrieval operations on a database table at the cost of additional storage and slower writes (INSERT/UPDATE).

B-Trees / B+ Trees

  • Type: On-disk, balanced trees.
  • Usage: Standard in RDBMS (MySQL, PostgreSQL).
  • Pros: Predictable performance, efficient range queries.
  • Cons: Slower random writes compared to LSM.

LSM Trees (Log-Structured Merge-Tree)

  • Type: Append-only logs + merged sorted slices.
  • Usage: NoSQL (Cassandra, LevelDB, RocksDB).
  • Pros: Extremely fast writes (sequential).
  • Cons: "Write amplification", complex read paths.

Replication Models

Model Logic When to use
Single Leader 1 Primary (Writes) $\rightarrow$ Many Replicas (Reads). Read-heavy workloads.
Multi Leader Multiple nodes accept writes. Multi-datacenter setups.
Leaderless Client writes to $N$ nodes (Quorum). High availability (Amazon Dynamo).

Horizontal Partitioning (Sharding)

Splitting a large dataset across multiple database instances using a Shard Key.

Shard Key
The column used to determine where data lives (e.g., user_id). Choosing a poor key leads to Hotspots.

Sharding Strategies

  • Range-based: ID 1-100 on Node A, 101-200 on Node B. Easy ranges, but high skew risks.
  • Hash-based: hash(id) % count. Even distribution, but harder to add nodes.
  • Directory-based: Lookup table to find where an ID lives. Flexible, but lookup is a bottleneck.

Database Federation (Vertical Partitioning)

Real Story: Amazon's Evolution

In early 2000s, Amazon ran on a giant Oracle database handling everything: users, products, orders, inventory. As they scaled, this became a bottleneck. They pioneered database federation - splitting into separate databases: Users DB, Products DB, Orders DB, each owned by different teams. This enabled Amazon to scale to millions of transactions per day.

What is Database Federation?

Database Federation (also called functional partitioning or vertical partitioning) is an architectural pattern where you split your application's database by business function or bounded context, creating multiple independent databases.

Instead of one monolithic database containing all tables, you create separate databases for different parts of your application:

  • User Service DB: users, profiles, authentication
  • Product Service DB: products, categories, reviews
  • Order Service DB: orders, order_items, shipping
  • Payment Service DB: transactions, payment_methods
  • Inventory Service DB: stock, warehouses, suppliers

Federation vs Sharding - Critical Difference

These are often confused but fundamentally different:

Sharding (Horizontal Partitioning)

What: Split the same table across multiple databases

Example:

Database 1: users WHERE id 1-1,000,000
Database 2: users WHERE id 1,000,001-2,000,000
Database 3: users WHERE id 2,000,001-3,000,000

Schema: Identical across all shards

Split by: Data range (shard key like user_id)

Goal: Scale a single large table

Federation (Vertical Partitioning)

What: Split different tables into separate databases

Example:

Database 1: users, profiles, auth_tokens
Database 2: products, categories, reviews
Database 3: orders, order_items, shipping

Schema: Different per database

Split by: Business domain/function

Goal: Scale entire application architecture

Advantages of Federation

1. Independent Scaling

Each database can scale based on its specific needs:

  • Product Catalog: Add read replicas (read-heavy)
  • Orders: Shard by order_id (write-heavy)
  • Users: Aggressive caching (mostly reads)
  • Payments: Keep small with strong ACID (critical data)

2. Team Autonomy & Velocity

Different teams own different databases:

  • Make schema changes independently
  • Choose optimal database technology per domain
  • Deploy updates without coordinating with other teams
  • Take ownership of performance and reliability

3. Technology Diversity

Use the best database for each workload:

  • User profiles: PostgreSQL (relational data)
  • Product catalog: Elasticsearch (full-text search)
  • Session data: Redis (fast cache)
  • Order history: MongoDB (flexible schema)
  • Analytics: Snowflake (data warehouse)

4. Fault Isolation

Failure in one database doesn't affect others:

  • Payment DB goes down → orders can still be created (process payments later)
  • Product DB slow → users can still checkout (product data cached)
  • Blast radius is limited to one domain

5. Simpler Per-Database Operations

Smaller databases are easier to manage:

  • Faster backups (500 GB vs 10 TB)
  • Quicker restores
  • Easier schema migrations
  • Better query performance (fewer tables)

Challenges and Tradeoffs

1. Cross-Database Joins

Problem: Can't JOIN across databases

Problem Example
// Before Federation (Easy):
SELECT users.name, orders.total
FROM users
JOIN orders ON users.id = orders.user_id
WHERE users.country = 'US';

// After Federation (Hard):
// Users in "users_db", Orders in "orders_db"
// Can't JOIN across databases!

Solutions:

  • Application-level joins: Fetch from both DBs, join in code
  • Data duplication: Store user_name in orders_db
  • Separate analytics DB: ETL data to warehouse for reporting
  • API composition: User Service API + Order Service API

2. Distributed Transactions

Problem: Transactions can't span databases atomically

Transaction Challenge
// Need atomic operation across 3 databases:
BEGIN TRANSACTION;
  UPDATE inventory_db.stock SET quantity = quantity - 1;  // DB1
  INSERT INTO orders_db.orders VALUES (...);               // DB2
  INSERT INTO payments_db.transactions VALUES (...);       // DB3
COMMIT;

// This doesn't work with federation!

Solutions:

  • SAGA pattern: Chain of local transactions with compensation
  • Eventual consistency: Accept that operations complete asynchronously
  • Two-Phase Commit (2PC): Distributed transaction protocol (slow, avoid if possible)
  • Event sourcing: Use event log to maintain consistency

3. Data Duplication

You'll need to duplicate some reference data:

  • Store user_name in orders_db (even though it's in users_db)
  • Store product_name in order_items (even though it's in products_db)
  • This is intentional denormalization for performance

4. Operational Complexity

More databases = more to manage:

  • Multiple backups to coordinate
  • Multiple monitoring dashboards
  • Multiple disaster recovery plans
  • Need more database expertise on team

When to Use Database Federation

Federation is Right When
  • Clear Bounded Contexts: Your application has distinct business domains (users, products, orders)
  • Different Scaling Needs: Some parts need heavy reads, others heavy writes
  • Team Organization: You have multiple teams that want autonomy
  • Microservices Architecture: Each service owns its own database
  • Monolith Bottleneck: Single database can't handle all load
  • Technology Diversity Needed: Different workloads need different database types
Don't Use Federation When
  • Small Application: One database works fine (don't over-engineer)
  • Heavy Cross-Domain Queries: You frequently need to join across domains
  • Strong Transactional Requirements: You need ACID across all data
  • Limited Team: You don't have expertise to manage multiple databases
  • Tight Coupling: Your domains aren't actually independent

Federation + Sharding Combined

For maximum scale, combine both patterns:

Hybrid Approach at Scale
1. Federation by Domain:
   ├── Users Database
   ├── Products Database  
   └── Orders Database

2. Then Shard Within Each:
   
   Orders Database (Federated)
   ├── Orders Shard 1: order_id 1-1M
   ├── Orders Shard 2: order_id 1M-2M
   └── Orders Shard 3: order_id 2M-3M
   
   Users Database (Federated)
   ├── Users Shard 1: user_id 1-10M
   └── Users Shard 2: user_id 10M-20M

This gives you both:
• Domain isolation (federation)
• Data distribution (sharding)

Migration Strategy

Moving from monolith to federation:

  1. Identify Bounded Contexts: Map your domains (users, products, orders)
  2. Start with One Domain: Extract least coupled domain first
  3. Create New Database: Copy relevant tables to new DB
  4. Dual Write: Write to both old and new DB temporarily
  5. Migrate Reads: Point reads to new DB incrementally
  6. Remove from Monolith: Delete tables from old DB once fully migrated
  7. Repeat: Extract next domain
Key Takeaway

Database Federation splits your database by business function, enabling independent scaling, team autonomy, and technology diversity. It's essential for microservices architectures but adds complexity in cross-database operations. Use it when your application has clear domain boundaries and different scaling needs per domain.

The 8 Fallacies of Distributed Computing

Originally enumerated by L. Peter Deutsch and James Gosling at Sun Microsystems. Every distributed system that ignores these eventually breaks in production.

# Fallacy The Real-World Pain Mitigation
1 "The network is reliable" Packets are dropped, NIC crashes, cables are unplugged. 1 in every 10M TCP packets retransmits. Retries, idempotency, circuit breakers
2 "Latency is zero" Cross-AZ: 0.5–2ms. Cross-region (US <-> EU): 80–100ms. Cross-continent: 150–300ms. Async communication, minimize hops, co-locate
3 "Bandwidth is infinite" Chatty microservices generate 10GB/day of internal traffic. N+1 query fan-outs saturate links. Data compression, pagination, projection

6 "There is one administrator" Infra team, DB team, app team, SRE team, security team all have different constraints Clear ownership, runbooks, IaC
7 "Transport cost is zero" AWS cross-region data transfer: $0.09/GB. 10TB/month = $900/month just for data movement. Data locality, compression, CDN
8 "The network is homogeneous" Mobile clients have 200ms latency + 2% packet loss. Corporate proxies strip headers. Adaptive protocols, fallback mechanisms

Byzantine Fault Tolerance (BFT)
A Byzantine fault is when a node sends arbitrary, incorrect, or conflicting messages — possibly maliciously. Tolerating F Byzantine faults requires 3F+1 nodes (vs. just 2F+1 for crash faults). BFT is used in: blockchain consensus (Tendermint, BFT-SMaRt), aircraft flight control systems, and some financial infrastructure. Most distributed databases only handle crash faults (much simpler).
The Two Generals Problem
Two generals must coordinate an attack via messenger — but messengers can be captured. The problem proves that it is impossible to achieve guaranteed consensus over an unreliable channel. Real-world: TCP's 3-way handshake is the practical "good enough" solution — it doesn't guarantee perfect agreement but makes the probability of desynchronization negligible.

Exactly-Once Semantics: Theory vs. Reality

At-Most-Once

  • Fire and forget — no retry
  • May lose messages
  • UDP, StatsD metrics

At-Least-Once

  • Retry until acknowledged
  • May deliver duplicates
  • Most queues: Kafka (default), SQS

Exactly-Once

  • No loss, no duplicates
  • Requires idempotency keys + transactional state
  • Kafka exactly-once (transactions API, ~2019)
  • Payment processing, financial ledgers
Exactly-Once is an Illusion — Idempotency is the Reality

True exactly-once delivery across systems is extremely expensive (2PC, distributed transactions). Most engineering teams implement at-least-once delivery + idempotent consumers. An idempotent consumer stores a processed-message-id set. If a message is re-delivered (duplicate), the consumer detects it and skips. Stripe generates an idempotency key per payment — if the request is retried, the same charge is not double-applied.

FLP Impossibility: Why Consensus is Hard

Fischer, Lynch, Patterson (1985) — Nobel Prize level insight
It is impossible to design a deterministic consensus algorithm that guarantees both safety (all nodes agree on the same value) and liveness (the algorithm always terminates) in a purely asynchronous system where even one node can fail by crashing.

Practical interpretation: Raft and Paxos work around FLP by using timeouts and leader election. They may fail to make progress during extreme network partitions (sacrificing liveness), but they never make incorrect decisions (maintaining safety). This is the "bias toward safety" principle: it's better to stop (be unavailable) than to make a wrong decision.

Leaderless replication (Dynamo-style)
No single leader. Any node accepts reads/writes. Uses quorum: write to W of N nodes; read from R of N nodes. Set W + R > N to guarantee reading at least one node with the latest write. Common setting: N=3, W=2, R=2. Cassandra, Riak, and Voldemort use this model. Trade-off: no strict ordering, conflicts possible — resolved by last-write-wins or CRDTs.

Time, Ordering & Clocks in Distributed Systems

The Problem: Clocks in Distributed Systems Are Unreliable

In a single machine, System.currentTimeMillis() gives consistent ordering. In a distributed system of N machines, each has its own clock — and clocks drift, jump, and disagree. NTP syncs clocks to within a few milliseconds — but a few ms is an eternity for systems handling millions of requests per second. We cannot use wall-clock time to determine ordering of distributed events.

Wall Clocks Are Not Monotonic

NTP can jump a clock backwards to correct drift. If event A is timestamped 10:00:00.500 and event B is timestamped 10:00:00.490 (after NTP corrected the clock), it appears B happened before A — even if A was processed first. This is why you must never use wall-clock time for ordering in distributed systems.

Lamport Clocks: Logical Ordering Without a Global Clock

The Algorithm (Leslie Lamport, 1978)
Each node maintains a counter L. Rules: (1) Increment L before any event. (2) When sending a message, include L. (3) On receive: L = max(L, received_L) + 1.
If event A caused event B (A happened-before B), then L(A) < L(B). But the converse is NOT guaranteed — two events may have the same or inverted Lamport timestamps without one causing the other (concurrent events).
Limitation
Lamport clocks can't distinguish between concurrent events and causally related events. If A has Lamport time 5 and B has Lamport time 7, B may have happened after A OR B may have happened concurrently with A (just at a node with a higher counter). This is where vector clocks come in.

Vector Clocks: Tracking Causality

sequenceDiagram participant A as Node A participant B as Node B participant C as Node C Note over A: [1,0,0] Event a1 A->>B: Send msg [1,0,0] Note over B: [1,1,0] Event b1 Note over A: [2,0,0] Event a2 B->>C: Send msg [1,1,0] Note over C: [1,1,1] Event c1 A->>C: Send msg [2,0,0] Note over C: [2,1,2] merge: max each + 1
Reading vector clocks
Vector [A:2, B:1, C:0] for event X means: "X has seen all of A's events up to A:2, all of B's events up to B:1, and none of C's." To compare two events X and Y: if every element of X's vector ≤ Y's vector, X happened-before Y. If neither is ≤ the other → concurrent events (potential conflict).
Where vector clocks are used
Amazon DynamoDB: Uses vector clocks (Dynamo paper, 2007) to detect concurrent writes to the same key. When a conflict is detected, all versions are returned to the client for semantic reconciliation (the application decides which value is correct). Riak: Uses dvv (Dotted Version Vectors) — a more efficient variant. Git: Conceptually similar — merge conflicts are concurrent edit detection.

Hybrid Logical Clocks (HLC)

HLC = max(NTP wall clock, logical component). It advances with real time where possible, falls back to logical increments when clocks are ahead. This gives you both:

  • Real-time approximation (useful for humans and debugging)
  • Causal ordering guarantees (useful for distributed systems correctness)
Used by:

The Innovation
Every Google datacenter has GPS receivers and atomic clocks. TrueTime's TT.now() API returns an interval [earliest, latest] — NOT a single timestamp. Spanner's commit protocol: before committing, wait until TT.now().earliest is past the transaction's commit timestamp. This ensures the commit is globally after all reads. Cost: ~7ms added latency per external-consistency write. Benefit: true global linearizability across continents.
Why other systems can't have this
GPS + atomic clock infrastructure costs millions per DC. Maintaining the global TrueTime service requires Google-scale investment. Others approximate it with tighter NTP (±1ms in some data centers), but can't guarantee the bound.

The Consensus Problem

Consensus is the problem of getting a set of distributed nodes to agree on a single value or decision, even when some nodes fail or messages are delayed. This is fundamental to implementing replicated state machines, distributed databases, distributed locks, and any system requiring coordination.

Requirements for a Consensus Algorithm

  • Agreement: All non-faulty nodes decide on the same value.
  • Validity: The decided value must have been proposed by some node (not invented).
  • Termination: All non-faulty nodes eventually decide (liveness).
  • Fault tolerance: The algorithm continues to work despite some nodes failing.

FLP Impossibility

The Fischer-Lynch-Paterson (FLP) theorem proves that in an asynchronous system where even one node can fail, it is impossible to guarantee that a consensus algorithm will always terminate. In practice, systems work around this by using timeouts and probabilistic liveness guarantees — they may not terminate in theory but do in practice under realistic conditions.

Raft Consensus Algorithm

Raft is a consensus algorithm designed to be more understandable than Paxos while providing the same guarantees. It decomposes consensus into three relatively independent subproblems: leader election, log replication, and safety.

Node States

  • Leader: Exactly one leader at a time (per term). Handles all client requests. Sends log entries and heartbeats to followers.
  • Follower: Passive — responds to RPCs from leaders and candidates. If no heartbeat received within election timeout, converts to candidate.
  • Candidate: Attempting to become leader. Sends RequestVote RPCs to all other nodes.

Leader Election

  1. All nodes start as followers with a randomized election timeout (150–300ms).
  2. A follower that times out without receiving a heartbeat becomes a candidate and increments its term number.
  3. The candidate votes for itself and sends RequestVote RPCs to all other nodes.
  4. A node grants its vote if: it has not voted in this term, and the candidate's log is at least as up-to-date as the voter's log.
  5. If the candidate receives votes from a majority (N/2 + 1), it becomes the leader.
  6. If multiple candidates split the vote, the election times out and a new election begins. Randomized timeouts reduce split vote probability.

Log Replication

  1. Client sends command to the leader.
  2. Leader appends the command to its log as a new entry (with the current term).
  3. Leader sends AppendEntries RPCs to all followers in parallel.
  4. When a majority has written the entry to their logs, the leader commits the entry.
  5. Leader applies the committed entry to its state machine and responds to the client.
  6. Leader notifies followers of the commit in subsequent AppendEntries. Followers apply committed entries.

Safety Guarantee

Raft guarantees that if a log entry is committed at index i with term T, any future leader's log will contain that entry at index i. This is enforced by the election restriction: a candidate cannot win an election unless its log is at least as up-to-date as a majority of nodes' logs.

Paxos Algorithm

Paxos is the original consensus algorithm, proposed by Leslie Lamport in 1989. It is provably correct but notoriously difficult to understand and implement correctly. Most practical consensus systems either implement Multi-Paxos (an optimized variant) or Raft (which was designed as a more understandable alternative).

Roles

  • Proposer: Proposes values to be agreed upon.
  • Acceptor: Votes on proposals. A quorum of acceptors must accept a value for consensus.
  • Learner: Learns which value was chosen after a quorum of acceptors has accepted it.

Phase 1: Prepare

  1. Proposer chooses a unique proposal number N and sends Prepare(N) to a quorum of acceptors.
  2. Each acceptor that has not responded to a Prepare with a higher number responds with: a promise not to accept any proposal numbered less than N, and the highest-numbered proposal it has already accepted (if any).

Phase 2: Accept

  1. If the proposer receives responses from a quorum, it sends Accept(N, V) where V is either the value from the highest-numbered prior accepted proposal (if any), or the proposer's own chosen value.
  2. Each acceptor accepts the proposal unless it has already responded to a Prepare with a higher number.
  3. If a quorum of acceptors accepts the proposal, the value V is chosen.

Split Brain Problem

Split brain occurs when a network partition causes multiple nodes to independently believe they are the leader (or the authoritative node), leading to conflicting decisions and data divergence. After the partition heals, the system has two incompatible versions of the truth.

Example Scenario

A 5-node cluster is partitioned into two groups: {A, B} and {C, D, E}. Both groups elect their own leader. Both leaders accept writes. When the partition heals, the cluster has two conflicting sets of writes that must be reconciled or one discarded.

Prevention via Quorum

Quorum-based systems prevent split brain by requiring that any decision must be acknowledged by a majority (N/2 + 1) of nodes. In a 5-node cluster, quorum is 3. During a {2} vs {3} partition, only the group of 3 can form a quorum and continue operating. The group of 2 stops accepting writes, preventing split brain.

Leader Election

Leader election is the process by which a group of distributed nodes selects one node to act as the coordinator or primary. Common algorithms:

  • Bully algorithm: Each node has a unique priority. When a node notices the leader is gone, it sends election messages to all nodes with higher priority. If no higher-priority node responds, it becomes the leader. Simple but generates O(N^2) messages.
  • Ring algorithm: Nodes are arranged logically in a ring. Each node forwards election messages around the ring. The node with the highest ID that the message passes through becomes the leader. O(N) messages.
  • Raft election: As described above — randomized timeouts with term numbers. Used in modern systems.
  • External coordination: Use ZooKeeper, etcd, or Consul to run an election and store the result. Services watch the stored key; whoever wins the distributed lock becomes leader.

Quorum

A quorum is the minimum number of nodes that must agree for an operation to proceed. For a cluster of N nodes, the standard quorum is N/2 + 1 (strict majority). Using a quorum ensures that any two quorums overlap by at least one node — meaning any decision made by one quorum is visible to any subsequent quorum.

Quorum in Read/Write Operations

In a replicated system with N replicas:

  • Write quorum (W): Write must be acknowledged by at least W replicas before confirming success.
  • Read quorum (R): Read must consult at least R replicas and return the most recent value.
  • Strong consistency guarantee: W + R > N ensures that every read quorum overlaps with every write quorum by at least one node, so reads always see the latest write.

The Distributed Transaction Problem

A distributed transaction spans multiple independent resources (databases, services) and must either commit or roll back atomically across all of them. This is fundamentally harder than a local transaction because any participant can fail independently at any point — including after some participants have committed but before others have.

Two-Phase Commit (2PC)

Two-Phase Commit is a distributed protocol that coordinates atomic commits across multiple participants. A coordinator node orchestrates two phases to ensure all participants either commit or roll back.

Phase 1: Prepare

  1. Coordinator sends Prepare message to all participants (P1, P2, P3).
  2. Each participant writes the transaction to its log (durably), acquires all necessary locks, and verifies it can commit.
  3. Participants respond with Vote-Commit (if ready) or Vote-Abort (if they cannot commit).

Phase 2: Commit or Abort

  1. If all participants voted Commit: coordinator writes "commit" to its log, then sends Commit to all participants.
  2. If any participant voted Abort: coordinator sends Abort to all participants.
  3. Participants apply the decision and release their locks.
  4. Participants acknowledge the commit/abort.

Problems with 2PC

  • Blocking protocol: If the coordinator crashes after Phase 1 but before Phase 2, participants are stuck holding locks indefinitely — they cannot proceed without the coordinator's decision. This is the most severe limitation.
  • Single point of failure: The coordinator is essential. If it fails at the wrong moment, the system is blocked until recovery.
  • Latency: Two round-trips plus logging overhead add significant latency compared to a single-participant transaction. Locks held during both phases reduce concurrency.
  • No partition tolerance: If a network partition isolates some participants from the coordinator, those participants are blocked.

SAGA Pattern

The SAGA pattern is an alternative to 2PC for long-running, multi-step transactions in microservices. Instead of a single atomic transaction, a SAGA decomposes a business process into a sequence of local transactions. Each local transaction updates a single service and publishes an event or message to trigger the next step. If any step fails, compensating transactions are executed in reverse order to undo the completed steps.

Key Concepts

  • Local transaction: Each step is an ACID transaction within a single service's database.
  • Compensating transaction: A transaction that semantically undoes a previously completed step. Note: compensation is not always a technical rollback — it may create new records (e.g., a refund record rather than deleting the payment record) to preserve audit trail.
  • Idempotency: Steps and compensations must be idempotent — they may be retried on failure.

Choreography-Based SAGA

Services react to events from other services without a central coordinator. Each service publishes events when a step completes; other services subscribe and react.

  • No central orchestrator — each service is autonomous
  • Loosely coupled — services only know about events

  • Business logic is centralized and visible in one place
  • Easier to understand, test, and monitor the transaction flow
  • Orchestrator becomes a dependency of all participant services
  • Technology examples: AWS Step Functions, Temporal, Conductor

The Outbox Pattern

The outbox pattern solves the dual-write problem: how to atomically update a database record AND publish an event to a message broker, when these are two separate systems with no shared transaction.

The Dual-Write Problem

# Naive approach — NOT atomic:
db.update("UPDATE orders SET status='paid' WHERE id=123")
# Process crashes here — order is paid but event not published
kafka.publish("payment.completed", { order_id: 123 })
# OR:
kafka.publish(...)
# Process crashes here — event published but DB not updated
db.update(...)

Outbox Solution

  1. In the same database transaction that updates business data, also insert a row into an "outbox" table describing the event to be published.
  2. A separate message relay process (or Debezium CDC) reads the outbox table and publishes messages to the broker.
  3. After publishing, the relay marks the outbox row as processed (or deletes it).
# Atomic: both happen in one database transaction
BEGIN;
  UPDATE orders SET status = 'paid' WHERE id = 123;
  INSERT INTO outbox (event_type, payload, created_at)
  VALUES ('payment.completed', '{"order_id":123}', NOW());
COMMIT;

# Separate relay process (eventually)
SELECT * FROM outbox WHERE processed = false ORDER BY created_at;
FOR row IN unprocessed_rows:
    kafka.publish(row.event_type, row.payload)
    UPDATE outbox SET processed = true WHERE id = row.id

Guarantees

  • The business state update and the event intent are always consistent — they commit together or roll back together.
  • At-least-once delivery: if the relay crashes after publishing but before marking processed, the message will be republished on retry. Consumers must be idempotent.
  • Ordering: events in the outbox are ordered by insertion time, which preserves causal ordering within a service.

Geohash

Geohash is a geocoding system that encodes a geographic location (latitude/longitude pair) into a short string of alphanumeric characters. The encoding subdivides the world into a grid of rectangular cells. Adjacent cells share common prefixes, enabling proximity queries using simple string prefix matching.

Encoding Process

  1. Interleave latitude and longitude bits to produce a single binary sequence.
  2. Encode the binary sequence using Base32 (characters: 0-9 and b-z excluding a,i,l,o).
  3. Each additional character doubles the precision (halves the cell size).

Quad Trees

A quad tree is a tree data structure where each internal node has exactly four children, partitioning a 2D space into four quadrants (NW, NE, SW, SE). Quad trees are used to efficiently index spatial data and support range queries and proximity searches.

How It Works

  • Start with a root node representing the entire area.
  • Each node tracks points within its region.
  • When a node's point count exceeds a threshold (e.g., 4 points), subdivide into four equal quadrants and distribute points.
  • Recurse until all regions have acceptable density or minimum cell size is reached.

Query

def range_query(node, search_rect):
    results = []
    if not node.rect.intersects(search_rect):
        return results  # Prune: no overlap

    for point in node.points:
        if search_rect.contains(point):
            results.append(point)

    if node.is_divided:
        for child in node.children:  # NW, NE, SW, SE
            results.extend(range_query(child, search_rect))

    return results

Advantages and Limitations

  • Queries skip entire quadrants that do not intersect the search region — O(log N) average
  • Good for point data that is roughly uniformly distributed
  • Poor for clustered data: dense areas create very deep trees; sparse areas waste space
  • Not well-suited for non-point objects (polygons, line segments) — use R-trees

R-Trees

An R-tree is a height-balanced tree data structure designed for indexing multi-dimensional information, particularly geometric objects such as points, rectangles, and polygons. Unlike quad trees (which partition space uniformly), R-trees group nearby objects together using minimum bounding rectangles (MBRs) regardless of spatial uniformity.

Structure

  • Each leaf node contains references to spatial objects (up to M objects per leaf)
  • Each internal node contains entries of the form (MBR, child_pointer) where MBR is the minimum bounding rectangle that encloses all objects in the subtree
  • MBRs can overlap between sibling nodes — a query may need to search multiple subtrees

Query

def search_rtree(node, query_rect):
    results = []
    for entry in node.entries:
        if entry.mbr.intersects(query_rect):
            if node.is_leaf:
                results.append(entry.object)
            else:
                results.extend(search_rtree(entry.child, query_rect))
    return results

Used by: PostGIS (PostgreSQL spatial extension), SQLite R-Tree module, most GIS databases. Used to efficiently answer spatial queries: "find all restaurants within 500m," "find all polygons that overlap this region."

Skip Lists

A skip list is a probabilistic data structure providing O(log N) average time complexity for search, insert, and delete operations — comparable to balanced trees but with simpler implementation. It is a layered linked list where higher layers contain fewer nodes, allowing efficient search by skipping over large sections of the base list.

Structure

  • Level 0: Contains all elements in sorted order (standard linked list).
  • Level 1: Contains approximately half of level 0's elements (randomly promoted).
  • Level k: Contains approximately half of level (k-1)'s elements.
  • Maximum height: O(log N) levels.

Search Algorithm

def search(target):
    current = head
    level = max_level

    while level >= 0:
        # Advance forward while next value < target
        while current.forward[level] and current.forward[level].value < target:
            current = current.forward[level]
        level -= 1  # Drop down one level

    current = current.forward[0]
    if current and current.value == target:
        return current
    return None

Insert: Probabilistic Promotion

When inserting a new node, the node is always added to level 0. With probability 0.5, it is also added to level 1. With probability 0.25, to level 2. And so on. This random promotion maintains the logarithmic height property on average without requiring rotations.

Redis Sorted Sets (ZSET): Redis implements sorted sets using a skip list combined with a hash table. Skip lists enable O(log N) ZRANGEBYSCORE and ZRANK operations. Redis chose skip lists over balanced trees because: simpler code, easier range queries, better cache locality for range scans.

HyperLogLog

HyperLogLog (HLL) is a probabilistic algorithm for estimating the cardinality (number of distinct elements) of a multiset using a fixed, small amount of memory, regardless of how many elements are in the set.

How It Works

The key insight: if you hash each element and count the maximum number of leading zeros in any hash, the cardinality can be estimated as 2^(max_leading_zeros). More precisely, HyperLogLog uses multiple hash functions and combines their estimates to reduce variance.

Count-Min Sketch

Count-Min Sketch (CMS) is a probabilistic data structure for frequency estimation of elements in a data stream. It provides approximate frequency counts using a two-dimensional array of counters, with a tunable tradeoff between accuracy, memory, and computation.

Structure and Update

  • Maintain a d×w matrix of integer counters, initialized to zero.
  • Use d independent hash functions h1, h2, …, hd each mapping elements to [0, w).
  • Update(element): For each hash function hi, increment matrix[i][hi(element)].
  • Query(element): For each hash function hi, read matrix[i][hi(element)]. Return the minimum of all d values (overestimates due to hash collisions, but minimum is least overestimated).
# Twitter trending topics approximation
cms = CountMinSketch(width=1000, depth=5)

for tweet in tweet_stream:
    for hashtag in tweet.hashtags:
        cms.update(hashtag)

# Query frequency of #AI
estimated_count = cms.query("#AI")
# Accurate within a bound: actual_count <= estimated <= actual + epsilon * N

Merkle Trees

A Merkle tree is a hash tree where every leaf node is labeled with the cryptographic hash of its data, and every non-leaf node is labeled with the hash of its children's labels. The root hash represents all data in the tree — any change to any leaf changes the root hash, and the specific changed leaf can be identified efficiently without examining all leaves.

Structure

          Root = H(H(H1,H2), H(H3,H4))
         /                            \
    H(H1,H2)                    H(H3,H4)
    /      \                    /      \
   H1       H2                H3       H4
(data 1)  (data 2)          (data 3)  (data 4)

Efficient Synchronization

Given two replicas with different root hashes:

  1. Compare root hashes — if equal, all data is identical.
  2. If different, recursively compare left subtree hashes, then right subtree hashes.
  3. Differences are localized to subtrees with mismatching hashes.
  4. Only data blocks under differing leaf nodes need to be transferred.

This finds differences in O(changes log N) time rather than O(N) by scanning all data.

Cassandra Anti-Entropy Repair

Cassandra builds a Merkle tree for each table on each replica during repair operations. Nodes compare Merkle tree roots to detect inconsistencies. Only the data blocks corresponding to differing leaf nodes are transferred, making repair efficient even for tables with billions of rows where only a handful of rows have diverged.

Bloom Filters

A Bloom filter is a space-efficient probabilistic data structure used to test whether an element is a member of a set. It can return False Positives (maybe in set) but never False Negatives (definitely not in set).

How it works

Uses a bit array of $m$ bits and $k$ different hash functions. When adding an element, set bits at all $k$ hash positions to 1. When querying, if any of the $k$ bits are 0, the element is definitely NOT in the set.

Use Cases: Reducing expensive disk lookups for non-existent keys (BigTable, Cassandra), Malicious URL filtering (Chrome).

Batch vs Stream Processing

Batch Processing

  • Process bounded data sets (finite input)
  • High latency — runs periodically (hourly, nightly)
  • High throughput — processes massive data efficiently
  • Can re-read input data (idempotent, correctable)
  • Examples: daily sales report, ML model training, ETL pipelines
  • Technologies: Apache Spark (batch), Hadoop MapReduce

Stream Processing

  • Process unbounded data as it arrives (infinite input)
  • Low latency — milliseconds to seconds
  • Lower throughput per unit time than batch
  • State management more complex (windowing, watermarks)
  • Examples: fraud detection, real-time dashboards, alerting
  • Technologies: Apache Flink, Kafka Streams, Apache Spark Streaming

MapReduce

MapReduce is a programming model for processing large datasets in parallel across a distributed cluster. Introduced by Google in 2004, it abstracts data parallelism into two phases: Map and Reduce.

Phases

  • Map phase: Input data is split into chunks. Each chunk is processed by a Map function independently and in parallel. The Map function outputs zero or more key-value pairs. Workers do not communicate — fully parallel.
  • Shuffle and Sort: All key-value pairs with the same key are grouped together and sent to the same Reduce worker. This is the most network-intensive phase.
  • Reduce phase: Each Reduce function receives a key and all values associated with it. It computes an aggregate and emits the result.
Word count across 1 TB of text files
# Map function (runs on each text chunk, independently)
def map(document_id, document_text):
    for word in document_text.split():
        emit(word.lower(), 1)

# → Output: ("the", 1), ("quick", 1), ("the", 1), ("fox", 1), ...

# Shuffle: Groups all ("the", ...) together, routes to same reducer

# Reduce function (runs once per unique word)
def reduce(word, counts):
    emit(word, sum(counts))

# → Output: ("the", 14523), ("quick", 421), ("fox", 207), ...

ETL Pipelines

ETL (Extract, Transform, Load) is a data integration pattern that extracts data from source systems, transforms it (cleans, enriches, aggregates, restructures), and loads it into a target system (data warehouse, data lake, or operational database).

Extract

Pull data from heterogeneous sources: relational databases (full extract or incremental via CDC), REST APIs, flat files (CSV, JSON), event streams, SaaS platforms (Salesforce, HubSpot). Frequency: nightly batch, hourly micro-batch, or continuous streaming.

Transform

Operations performed during transformation:

  • Data cleaning: Handle nulls, duplicates, malformed records, encoding issues.
  • Type casting: Convert strings to dates, normalize numeric precision.
  • Deduplication: Identify and merge duplicate records across sources.
  • Enrichment: Join with reference data (geocode IP addresses, translate product codes to names).
  • Aggregation: Compute sums, counts, averages per dimension.
  • Business rule application: Apply domain-specific categorization and filtering.

Load

Write transformed data to the target store. Strategies:

  • Full load: Truncate and reload target. Simple, consistent, but expensive for large data.
  • Incremental load: Only load new or changed records (using a watermark timestamp or CDC). Efficient but requires careful handling of late-arriving data.
  • Upsert (merge): Update existing records, insert new ones. Maintains target as current state.

Modern ELT: Modern cloud data warehouses (Snowflake, BigQuery) are so powerful that it is often more efficient to load raw data first and transform it within the warehouse. This "ELT" approach (Extract, Load, Transform) allows flexible re-transformation without re-ingestion.

Data Lakes

A data lake is a centralized repository that stores data in its raw, native format at any scale. Unlike a data warehouse (which stores data in a structured, processed form), a data lake accepts any data — structured, semi-structured, and unstructured — without requiring a schema to be defined at write time.

Schema on Read vs Schema on Write

  • Schema on Write (Data Warehouse): Data is transformed to match a defined schema before being written. Queries are fast; schema is enforced. Inflexible — schema changes are expensive.
  • Schema on Read (Data Lake): Raw data is written without transformation. The schema is applied when data is read. Flexible — raw data can be reprocessed with new schemas. Risk of data quality issues if not governed.

Data Swamp

A data lake without governance, documentation, and data quality processes quickly becomes a "data swamp" — a repository of poorly documented, duplicated, inconsistent data that nobody trusts or can effectively use. Prevention requires: data cataloging (Apache Atlas, AWS Glue Data Catalog), data quality checks, clear ownership, and access control.

Data Warehousing

A data warehouse is a relational database optimized for analytical queries. It integrates data from multiple source systems, enforces consistent schemas, and provides a query interface optimized for aggregations and scans rather than transactional workloads.

OLTP vs OLAP

OLTP (Online Transaction Processing)

  • Optimized for short, simple transactions
  • High write throughput (thousands of writes/second)
  • Row-oriented storage
  • Normalized schema (3NF)
  • Current data only (no history)
  • Examples: PostgreSQL, MySQL for production apps

OLAP (Online Analytical Processing)

  • Optimized for complex queries scanning large data
  • High read throughput (aggregate millions of rows)
  • Column-oriented storage (excellent for analytical queries)
  • Denormalized schema (star/snowflake schema)
  • Historical data with time dimension
  • Examples: Snowflake, BigQuery, Redshift, ClickHouse

Star Schema

The star schema organizes a data warehouse into a central fact table (containing quantitative measurements and foreign keys) surrounded by dimension tables (containing descriptive attributes). Queries join the fact table to one or more dimension tables.

-- Fact table: sales transactions
fact_sales (
    sale_id INT,
    date_key INT    → dim_date,
    product_key INT → dim_product,
    store_key INT   → dim_store,
    customer_key INT → dim_customer,
    quantity INT,
    revenue DECIMAL
)

-- Dimension tables: descriptive context
dim_date    (date_key, date, day_of_week, month, quarter, year)
dim_product (product_key, name, category, brand, price_tier)
dim_store   (store_key, name, city, state, region)

-- Analytical query
SELECT d.quarter, p.category, SUM(f.revenue)
FROM fact_sales f
JOIN dim_date d    ON f.date_key = d.date_key
JOIN dim_product p ON f.product_key = p.product_key
WHERE d.year = 2024
GROUP BY d.quarter, p.category;

Data Lakehouse

The Lakehouse architecture combines the flexibility and low cost of a data lake with the reliability, ACID transactions, and performance of a data warehouse. It uses open table formats (Delta Lake, Apache Iceberg, Apache Hudi) to add structure, schema enforcement, and transaction support on top of object storage.

Key Capabilities

  • ACID transactions: Multiple concurrent writers can commit atomically. Failed jobs do not leave partial data.
  • Schema evolution: Add, rename, and reorder columns without rewriting data. Schema is stored in metadata, not baked into files.
  • Time travel: Query historical versions of tables. Roll back bad writes. Audit who changed what.
  • Upserts and deletes: Efficiently update specific rows (necessary for GDPR right-to-erasure compliance).
  • Unified storage: Both BI/analytics tools and ML workloads read from the same lakehouse.

Lambda Architecture

Lambda architecture processes data using two parallel paths — a batch layer that provides accurate, comprehensive views of historical data, and a speed layer that provides real-time approximations of recent data — served together through a query layer.

Layers

  • Batch layer: Processes the complete historical dataset periodically (nightly). Produces accurate batch views. Uses Hadoop, Spark. High latency, high accuracy.
  • Speed layer: Processes only recent data (last hour) in real time. Produces real-time views. Uses Spark Streaming, Flink. Low latency, approximate accuracy.
  • Serving layer: Merges batch and speed views to answer queries. The batch view covers all time up to the last batch run; the speed view covers the gap since then.

Limitations

  • Two codebases to maintain — batch logic and stream logic for the same computation
  • Increased operational complexity
  • Introduced when mature stream processing did not exist — largely superseded by Kappa architecture

Kappa Architecture

Kappa architecture simplifies Lambda by removing the batch layer. Instead, it treats "batch" as a special case of streaming — replaying historical events from a log (like Kafka) through the same streaming engine.

Benefits

  • Single codebase for all data processing.
  • Simpler operations.
  • Easier consistency guarantees.

  • Two codebases to maintain
  • More complex operationally

  • One codebase
  • Simpler operationally
  • Requires log retention long enough for reprocessing
  • Preferred when stream processing can handle all use cases

Stream Processing Engines

Apache Flink

Flink is a stateful stream processing engine with true streaming semantics (not micro-batching). It processes each event individually with sub-second latency, supports event time processing with watermarks for out-of-order data, provides exactly-once processing guarantees via distributed snapshots, and manages large amounts of operator state efficiently in RocksDB.

Apache Kafka Streams

Kafka Streams is a library (not a cluster) for building streaming applications on top of Kafka. It runs as threads within your application process — no separate cluster needed. Supports stateful operations (aggregations, joins) backed by local RocksDB stores synchronized to Kafka topics for durability. Excellent for Kafka-centric microservice architectures.

Apache Spark Streaming

Spark Streaming (and Structured Streaming in newer Spark versions) processes streams as micro-batches — small batches of data collected over a short interval (500ms–several seconds). Provides a unified API for batch and streaming; the same Spark code runs on both. Structured Streaming provides exactly-once semantics through checkpointing.

Stream Processing Concepts

  • Event time vs processing time: Event time is when the event occurred; processing time is when it reaches the processor. Late-arriving data can cause incorrect results if processing time is used for windowing.
  • Watermarks: The stream processor's estimate of the current event time, accounting for expected delay. Events with timestamps earlier than the watermark are considered late and may be dropped or handled specially.
  • Windows: Group events into time-bounded sets for aggregation. Tumbling windows (non-overlapping, e.g., each 5 minutes), sliding windows (overlapping, e.g., every 1 minute with 5-minute length), session windows (grouped by activity gaps).
  • State backends: Stateful operations (counts, aggregations, joins) require durable state storage. Flink supports in-memory, RocksDB (local disk), and cloud object storage backends.

The Inverted Index: Core Data Structure for Search

A regular database index maps row → content. An inverted index maps term → [documents containing it]. This enables O(1) term lookup regardless of total document count.

flowchart LR subgraph Documents D1["Doc 1: 'distributed systems scale'"] D2["Doc 2: 'scale horizontally with sharding'"] D3["Doc 3: 'distributed database internals'"] end subgraph Inverted Index T1["'distributed' → [Doc1, Doc3]"] T2["'scale' → [Doc1, Doc2]"] T3["'sharding' → [Doc2]"] T4["'systems' → [Doc1]"] end
What's stored per posting (beyond just doc ID)
Full-featured inverted indexes store: document ID, term frequency (how many times the term appears), field (title vs. body), and optionally term positions (for phrase queries like "distributed systems" — both words must appear in order). Position storage triples index size but enables exact phrase matching.
Tokenization & Normalization Pipeline
Before indexing: "Running Dogs Quickly!" → tokenize → ["Running", "Dogs", "Quickly"] → lowercase → ["running", "dogs", "quickly"] → stop word removal → ["running", "dogs", "quickly"] → stemming → ["run", "dog", "quick"]. A search for "ran" now matches "running" via the stem "run".

TF-IDF and BM25: Relevance Scoring

TF-IDF (Term Frequency × Inverse Document Frequency)
TF: Documents mentioning "database" 20 times are more about databases than documents mentioning it once. IDF: "the" appears in every document — not useful. "NoSQL" appears in 1% of documents — very signal. IDF penalizes common terms. Combined: terms that appear often in a document but rarely globally = high relevance.
BM25 (Best Match 25)
The de facto standard relevance model (used by Elasticsearch, Solr, Lucene as default since 2015). BM25 improves TF by applying diminishing returns — going from 1 to 2 mentions of a term matters more than going from 100 to 101. Also accounts for document length (shorter documents with the term score higher). Most search engines start with BM25 then layer on ML re-ranking.
Learning to Rank (FAANG Practice)
Google, Bing, and LinkedIn use ML models (LambdaMART, neural re-rankers) on top of BM25 initial retrieval. The BM25 score is one feature among hundreds: click-through rate, freshness, authority, personalization signals. In interviews: "BM25 for initial retrieval, then a lightweight ML model for re-ranking the top-K results."

Elasticsearch Architecture

Shards and Segments
An Elasticsearch index = multiple shards (each shard is a full Lucene instance). Within a shard, data is stored in immutable segments. New documents create new segments; deleted documents are marked in a deletion bitset. Periodic segment merging compacts them. Never over-shard: each shard has overhead (~10MB+ heap). Rule: aim for 10–50GB per shard.
The Near-Real-Time (NRT) Refresh
New documents are available for search after a "refresh" (default: 1 second). Documents written to the in-memory buffer become visible by writing a new segment and opening it. This is why Elasticsearch search lags are ~1 second, not milliseconds. You can control this with refresh_interval — set to -1 for bulk indexing (max throughput), 1s for live search.
Twitter/X: Real-time tweet search
Twitter indexes ~500M tweets/day for search. They use a custom Lucene setup with ~1 second indexing lag. Key insight: new tweets (recency) are prioritized in ranking — most users want the latest tweets, not the most BM25-relevant. Their ranking is: engagement signals (retweets, likes) × time-decay function × personalization × BM25 text score.

Search System Design: A Framework

FAANG Interview: Design a Search System
  1. Indexing pipeline: Source data → Kafka → indexing workers → Elasticsearch/Solr. Use change data capture (CDC) from the DB to keep index in sync.
  2. Query pipeline: Client → query parser (tokenize, detect intent) → BM25 retrieval → re-ranking (ML model) → response.
  3. Freshness vs. throughput: Batch re-indexing for historical data; incremental updates via CDC for new/changed content.
  4. Relevance tuning: A/B test ranking models on click-through rate and conversion metrics.
  5. Scaling reads: Multiple replica shards; route queries to replicas. Coordinating node scatter-gathers results from all shards and merges sorted results.
Elasticsearch vs. Algolia vs. OpenSearch vs. Typesense
Elasticsearch/OpenSearch: Self-hosted, highly configurable, steep learning curve. Best for log analytics (ELK stack) and complex search requirements.
Algolia: Managed SaaS, optimized for sub-10ms search UX (typo-tolerance built-in). Simple to integrate. Expensive at scale. No self-host option.
Typesense: Open-source Algolia alternative. Fast, simple, good for product search.
PostgreSQL FTS: GIN index + tsvector/tsquery. Good enough for small catalogs (<1M docs). Free. No dedicated search infrastructure.

What is Disaster Recovery?

Disaster Recovery (DR) is a set of policies, tools, and procedures to enable the recovery or continuation of vital technology infrastructure and systems following a natural or human-induced disaster.

Disasters include:

  • Infrastructure failures: Data center fire, power outage, hardware failure
  • Natural disasters: Earthquakes, floods, hurricanes
  • Cyberattacks: Ransomware, DDoS, data breach
  • Human error: Accidental deletion, misconfiguration
  • Software bugs: Deployment gone wrong, database corruption

Core Concepts: RTO and RPO

Two critical metrics define your DR strategy:

RTO - Recovery Time Objective

Definition: Maximum acceptable time to restore service after a disaster

Question: "How long can we afford to be down?"

Examples:

  • Banking: RTO = 1 hour
  • E-commerce: RTO = 15 minutes
  • Social media: RTO = 5 minutes
  • Internal tools: RTO = 4 hours
  • Batch processing: RTO = 24 hours

Impact: Lower RTO = Higher cost

RPO - Recovery Point Objective

Definition: Maximum acceptable amount of data loss measured in time

Question: "How much data can we afford to lose?"

Examples:

  • Financial transactions: RPO = 0 (no data loss)
  • E-commerce orders: RPO = 1 minute
  • User posts: RPO = 5 minutes
  • Analytics data: RPO = 1 hour
  • Logs: RPO = 24 hours

Impact: Lower RPO = Higher cost

Understanding RTO and RPO
Timeline of a Disaster:

10:00 AM - Last successful backup
02:00 PM - Disaster strikes (database corrupted)
04:00 PM - Service restored

RPO = 4 hours (data between 10AM-2PM is lost)
RTO = 2 hours (system was down from 2PM-4PM)

Impact:
• Lost 4 hours of transactions (RPO)
• Website down for 2 hours (RTO)
• Revenue loss: $100K/hour × 2 = $200K
• Data loss: 500 orders need manual recovery

The Four Disaster Recovery Strategies

1. Backup & Restore (Cheapest, Slowest)

How it works:

  • Regular backups stored in cloud (S3, Azure Blob)
  • When disaster strikes, provision new infrastructure
  • Restore data from backups
  • Reconfigure and restart services

Metrics:

  • RTO: Hours to days
  • RPO: Hours (depends on backup frequency)
  • Cost: 💰 Low ($500-$2K/month)

Best for: Non-critical systems, internal tools, development environments

Example: Internal HR System
Daily Backup Schedule:
• 2AM: Full database backup → S3
• Cost: $50/month for storage

Disaster Scenario:
1. Database crashes at 10AM
2. Provision new RDS instance (30 min)
3. Download backup from S3 (1 hour)
4. Restore database (2 hours)
5. Update DNS and test (30 min)

Total RTO: 4 hours
RPO: 8 hours (lost data since 2AM backup)
Acceptable: Yes (internal system, not customer-facing)

2. Pilot Light (Moderate Cost, Fast)

How it works:

  • Core infrastructure always running in secondary region
  • Database replication active (real-time or near-real-time)
  • Application servers off or minimal (scaled to zero)
  • When disaster strikes, scale up application tier quickly

Metrics:

  • RTO: ~1 hour
  • RPO: Minutes (based on replication lag)
  • Cost: 💰💰 Medium ($5K-$20K/month)

Best for: Business-critical applications that can tolerate short downtime

Example: E-Commerce Site
Primary Region (US-EAST):
• Application: 50 servers running
• Database: PostgreSQL with 2 replicas
• Load balancer: Active

Secondary Region (US-WEST) - Pilot Light:

• Load balancer: Configured but idle

• Storage: $200
• Networking: $300
Total: $1,000/month

Disaster Scenario:

2. Promote secondary database to primary (5 min)
3. Launch application servers (auto-scale) (10 min)
4. Update DNS to secondary region (30 min)
5. Test and verify (15 min)

Total RTO: 1 hour
RPO: 5 minutes (replication lag)
Revenue loss: $100K × 1 = $100K
Acceptable: Yes (1 hour outage reasonable)

3. Warm Standby (High Cost, Very Fast)

How it works:

  • Scaled-down version of full environment always running
  • Application servers running at minimal capacity
  • Database replication active (synchronous or near-sync)
  • When disaster strikes, scale up to full capacity

Metrics:

  • RTO: ~15 minutes
  • RPO: Seconds to minutes
  • Cost: 💰💰💰 High ($20K-$50K/month)

Best for: Mission-critical applications where 15-min downtime is acceptable

Example: Banking Application
Primary Region:
• Application: 100 servers
• Database: 5 replicas
• Users: 1M active

Secondary Region - Warm Standby:
• Application: 20 servers (20% capacity)
• Database: Replica with sync replication
• Users: Can handle 200K (20%)

Monthly Cost:
• 20 servers: $5,000
• Database replica: $1,000
• Load balancer: $500
Total: $6,500/month

Disaster Scenario:
1. Primary region fails
2. Auto-scale secondary from 20→100 servers (10 min)
3. Update DNS (cached, takes time to propagate)
4. Gradually shift traffic as DNS updates

Total RTO: 15 minutes
RPO: 1 minute (sync replication lag)
Revenue loss: $100K × 0.25 = $25K
Acceptable: Yes (banking can handle brief outage)

4. Hot Standby / Active-Active (Highest Cost, Instant)

How it works:

  • Full production environment in multiple regions
  • Both regions actively serving traffic (active-active)
  • Database replication synchronous or conflict-free (CRDT)
  • When disaster strikes, traffic automatically reroutes

Metrics:

  • RTO: Seconds (automatic failover)
  • RPO: Near zero (synchronous replication)
  • Cost: 💰💰💰💰 Very High ($50K-$200K+/month)

Best for: Ultra-critical applications (financial trading, healthcare, emergency services)

2. Global load balancer detects failure (5 seconds)

RPO: 0 (synchronous replication)
Revenue loss: $0 (seamless failover)
Acceptable: Perfect (trading can't stop)

What is Observability?

Observability is the ability to understand the internal state of a system by examining its external outputs. A system is observable if you can answer "why is this broken?" from data alone, without adding new instrumentation after the fact. Observability is built, not added — it requires designing systems to expose their behavior through structured telemetry.

Observability vs Monitoring

Monitoring asks "is this thing I already know about working?" — it checks known failure modes against predefined thresholds. Observability asks "what is happening and why?" — it allows investigation of unknown failure modes using arbitrary queries against detailed telemetry.

Three Pillars of Observability

1. Logs

Logs are discrete, time-stamped records of events that occurred within a system. Each log entry captures what happened, when it happened, and contextual information about the state at that moment.

2. Metrics

Metrics are numeric measurements collected at regular intervals over time. They are efficient to store and query (as time series) and are the primary tool for alerting and capacity planning.

Metric Types

  • Counter: Monotonically increasing value. Resets to 0 on restart. Rate of change is meaningful. Example: total HTTP requests, total errors.
  • Gauge: A value that can go up and down arbitrarily. Example: current active connections, memory usage, queue depth.
  • Histogram: Samples observations and counts them in configurable buckets, also tracking sum and count. Enables percentile calculation. Example: HTTP request duration in buckets [0.1s, 0.5s, 1s, 5s].
  • Summary: Calculates configurable quantiles client-side. Less flexible than histograms for aggregation across instances.

RED Method (for Services)

  • Rate: Requests per second the service is handling.
  • Errors: The number or rate of failed requests.
  • Duration: Distribution of request latencies (p50, p95, p99).

USE Method (for Resources)

  • Utilization: Average time the resource is busy (e.g., CPU %).
  • Saturation: Amount of work waiting to be served (e.g., CPU run queue length).
  • Errors: Error events (e.g., disk I/O errors, network packet drops).

3. Distributed Tracing

Correlation IDs (Request IDs)

A correlation ID (also called trace ID or request ID) is a unique identifier attached to a request at the entry point (API gateway or first service) and propagated to every downstream service call. All log entries related to a single user request share the same correlation ID, enabling reconstruction of the complete request trace from logs across all services.

# API Gateway — generate if not present
def handle_request(req):
    correlation_id = req.headers.get('X-Correlation-ID') or str(uuid4())

    # Propagate to all downstream calls
    downstream_headers = {
        'X-Correlation-ID': correlation_id,
        'X-Request-Source': 'api-gateway'
    }

    # Include in all log entries
    logger.info("Request received", extra={
        "correlation_id": correlation_id,
        "user_id": req.user.id,
        "path": req.path
    })

    result = call_service("order-service", headers=downstream_headers)

    # Return in response for client-side debugging
    return result, {'X-Correlation-ID': correlation_id}

Alerting

Alerting is the process of detecting when system behavior deviates from expected norms and notifying the appropriate team. Good alerting finds real problems early without generating noise that trains engineers to ignore alerts.

Alert Quality Criteria

  • Actionable: The recipient knows what to do. An alert that says "CPU is high" without context about what it means or how to fix it is poor. An alert that says "Checkout service CPU >90% for 10 minutes — possible infinite loop in payment retry logic, see runbook #42" is actionable.
  • Urgent: The alert fires before customers notice. Alert on 95th percentile latency crossing 1 second — do not wait for p50 to cross 5 seconds.
  • Signal-to-noise: False positives train engineers to ignore alerts. Every alert that pages someone and turns out to be nothing is a step toward alert fatigue.
  • On the right channel: Not all alerts require waking someone at 3am. Tier alerts: page (immediate, 24/7), ticket (business hours), dashboard (informational).

Dashboards

Dashboards are visual interfaces that display key metrics and system health at a glance. They serve different audiences and purposes: on-call dashboards for incident response, business dashboards for stakeholders, engineering dashboards for capacity planning.

Dashboard Design Principles

  • One job per dashboard: An on-call dashboard should show what is broken and where, not every metric. A capacity planning dashboard shows trends over months.
  • Hierarchical drill-down: Overview dashboard → service dashboard → specific endpoint or operation.
  • Consistent time ranges: All panels on a dashboard should share the same time window by default.
  • RED metrics first: For service dashboards, Rate, Errors, and Duration are the most important panels at the top.
  • Annotate deployments: Mark deployment events as vertical lines on time series graphs to correlate changes with metric shifts.

Runbooks

A runbook is a documented set of procedures for handling known operational scenarios — typically tied to specific alerts. When an alert fires at 3am, the on-call engineer should be able to follow the runbook without needing deep expertise in the system.

Runbook Structure

  • Alert name and trigger condition: What metric threshold caused this alert to fire.
  • Impact statement: What users or functionality is affected. Severity and urgency.
  • Immediate mitigation: Steps to stop the bleeding quickly (restart a service, enable feature flag, scale up).
  • Diagnostic steps: Ordered investigation procedure — where to look first, second, third. Include specific log queries, dashboard links, CLI commands.
  • Root cause patterns: Common causes and their specific indicators.
  • Resolution steps: How to fix each root cause.
  • Escalation path: Who to contact if you cannot resolve it within X minutes.
  • Post-incident: What to document, which team to notify, whether to file a bug or post-mortem.

Encryption: In Transit vs. At Rest vs. In Use

Type What It Protects How Tools
In Transit Data moving over network TLS 1.2/1.3 (mandatory), mTLS for service-to-service Let's Encrypt, AWS ACM, Istio mTLS
At Rest Data stored on disk, in DB, in S3 AES-256 server-side encryption (SSE), full-disk encryption AWS KMS, S3-SSE, db-level TDE (Transparent Data Encryption)
In Use Data while being computed (cutting edge) Homomorphic encryption, trusted execution environments (Intel SGX) AWS Nitro Enclaves, Azure Confidential Computing
End-to-End (E2E) Data from sender to recipient — not even servers can read Client-side encryption with user-controlled keys Signal Protocol, WhatsApp, iMessage
TLS 1.3 vs TLS 1.2
TLS 1.3 (2018) eliminates the round-trip in the handshake: 1-RTT instead of 2-RTT for new connections, and 0-RTT session resumption (at slight security cost). It also removes weak ciphers (RC4, SHA-1, RSA key exchange). Google found TLS 1.3 reduced connection setup latency by ~20ms on average. All new systems should require TLS 1.3 minimum.
Key Management: The Hard Part
Encrypting data is easy. Managing keys securely at scale is hard. Gold standard: use a Hardware Security Module (HSM) — a tamper-resistant chip that stores root keys and never exposes them. AWS CloudHSM and AWS KMS (backed by HSMs) handle this. Keys should be rotated regularly. Never store encryption keys in the same system as the encrypted data.

Authentication: Passwords → Tokens → Certificates

flowchart LR subgraph Modern Auth Flow U[User] -->|username+password| A[Auth Service] A -->|verify bcrypt hash| DB[(Users DB)] A -->|issue JWT\nAccess + Refresh| U U -->|JWT in Authorization header| API[API Server] API -->|verify signature\nno DB call| Allow[Allow Request] end
Password Hashing: bcrypt vs. Argon2
Never store plain-text passwords. Never use MD5 or SHA-256 alone (too fast — GPU can crack billions/sec). Use bcrypt (work factor 12–14), scrypt, or Argon2id (winner of Password Hashing Competition 2015). Argon2id is memory-hard — costs GB of RAM to compute, making GPU/ASIC attacks impractical. bcrypt at work_factor=12 takes ~250ms per hash on a server — slow enough to prevent dictionary attacks, fast enough for legitimate logins.
JWT (JSON Web Tokens) Trade-offs
JWTs are stateless — the server doesn't need a DB lookup to validate a request. The downside: you can't invalidate a JWT before expiry without a blocklist (which adds a DB lookup back). Mitigation: use short expiry (15 minutes) for access tokens + long-lived refresh tokens (stored in DB, revocable). This is the standard OAuth 2.0 pattern.
mTLS for Service-to-Service Auth
In microservices, services must authenticate each other, not just users. mTLS (mutual TLS) requires both client and server to present certificates. A service mesh (Istio) does this automatically via short-lived SPIFFE certificates (rotated every 24 hours). No API keys in config files. This is how Google's BeyondCorp zero-trust network works internally.

Authorization: RBAC vs. ABAC vs. ReBAC

Model Logic Pros Cons Used By
RBAC (Role-Based) User has Role → Role has Permissions Simple, auditable Role explosion at scale (1000s of roles) AWS IAM roles, most enterprise apps
ABAC (Attribute-Based) Access decided by user/resource/env attributes Fine-grained, context-aware Complex policies, hard to audit AWS IAM policies, XACML systems
ReBAC (Relationship-Based) Access based on graph of relationships Natural for social/sharing models Complex graph queries Google Zanzibar, GitHub, Notion
Google Zanzibar: The Authorization System Powering Gmail, Drive, Docs
Google's Zanzibar (published 2019) handles 10 million authorization checks per second globally, with <10ms p95 latency. It stores relationships as tuples: (object, relation, user) — e.g., (doc:42, viewer, user:alice). Arbitrary graph traversal lets you answer: "Can Alice view Doc 42?" by following relationship chains. Open-source implementations: OpenFGA, SpiceDB, Permify, Cerbos.

Zero Trust Architecture

Traditional security: "Trust everything inside the network perimeter." Zero Trust: "Never trust; always verify." The network perimeter is dead — endpoints are mobile, services run in shared clouds, insiders can be attackers.

Google BeyondCorp
Google implemented zero trust internally after the Aurora attacks (2010). All employee access is granted based on device certificate (is this a managed Google laptop?) + user identity (is this the right person?) + policy (does this person's role allow this resource?). No VPN required — engineers access internal tools directly from any network. The model is now the basis for Google Cloud's BeyondCorp Enterprise product.
OWASP Top 10 and System Design
When asked about security in a system design interview, cover: (1) Injection: parameterized queries, not string concatenation; (2) Broken Auth: short-lived tokens, MFA, rate limit login attempts; (3) Sensitive Data Exposure: encrypt at rest and in transit, no PII in logs; (4) SSRF: validate and whitelist outbound URLs in services that fetch URLs; (5) Rate limiting + DDoS: CDN-level (Cloudflare) + application-level (token bucket per IP/user).

This is a two-sided marketplace with a real-time reservation engine — the same class as Airbnb, Ticketmaster, and OpenSea. The FAANG interviewer is looking for: (1) strong consistency for bookings, (2) eventual consistency for search, (3) how you prevent double booking at scale, and (4) your ability to reason about hot-partition problems.

4. Core Design: Availability Engine (The Hardest Part)

This is where the interviewer will spend most time

The Availability Engine must ensure no double booking while handling concurrent requests. This is a classic distributed concurrency problem. Walk through at least two approaches and explain the tradeoffs.

Precomputed Time Slot Model (Recommended)

Divide each restaurant's day into 15-minute slots. Maintain a row per slot tracking available capacity. All reservation writes update this table atomically.

flowchart LR User --> GW[API Gateway] GW --> R[Reservation Service] R --> H{1. Create HOLD\n2-min TTL} H --> T{2. BEGIN TRANSACTION\nSELECT ... FOR UPDATE\nCheck capacity > 0\nDecrement capacity\nINSERT reservation} T -->|Commit| C[Reservation Confirmed] T -->|Rollback| F[409 Conflict\nNo slot available] C --> K[Emit Kafka event\nreservation.created] K --> N[Notification Service]

Double Booking Prevention: Three Approaches

❌ Compute on the fly (naive)

Query all reservations, calculate availability per request.

  • Correct but slow — O(N) table scans
  • Doesn't prevent race condition
  • Won't scale to 120 QPS peak writes

✅ Pessimistic locking (recommended)

SELECT * FROM availability
WHERE restaurant_id = $1
  AND time_slot = $2
FOR UPDATE;
-- If capacity > 0: decrement + insert
-- COMMIT atomically
  • Guarantees no double booking
  • Row-level lock, not table lock
  • Excellent for moderate write QPS

⚠️ Optimistic locking (alternative)

UPDATE availability
SET capacity = capacity - 1,
    version = version + 1
WHERE restaurant_id = $1
  AND time_slot = $2
  AND version = $version_read
  AND capacity > 0;
  • No locks held — better throughput under low contention
  • Retry on version conflict — adds latency under high contention
  • Use for less popular restaurants
The 2-minute HOLD pattern
When a diner clicks "Reserve" but hasn't confirmed yet: create a soft hold stored in Redis with a 2-minute TTL. This temporarily decrements shown availability. On confirm, run the actual DB transaction. On timeout, the hold expires automatically and the slot returns to available. This prevents the "phantom slot" problem where many users see the same slot and all try to book simultaneously.
Hot restaurant problem
Nobu Saturday 7pm gets 10,000 concurrent requests. With pessimistic locking, all threads line up for the same row lock — creating a thundering herd. Solutions: (1) a reservation queue per restaurant (serialize writes via Kafka partition keyed by restaurant_id); (2) slot-level partitioning; (3) rate limit per restaurant slot.

6. Caching Strategy

Redis (TTL: 30–60s on availability, 5min on search)
Cache restaurant search results and approximate availability. Short TTL bounds staleness. Invalidate immediately on any booking. The final confirmation step always re-validates against the authoritative DB — the cache is only used to show "approximately available" in the search UI, never to approve a booking.
CDN (TTL: 24h on restaurant metadata)
Restaurant name, photos, cuisine, hours — highly cacheable, changes rarely. Purge on restaurant profile update. This offloads ~90% of read traffic for restaurant detail pages.

7. Sharding Strategy

Shard by restaurant_id
All data for a given restaurant lives in the same shard: availability, reservations, waitlist. This makes reservation transactions local to a shard (no cross-shard distributed transactions). Trade-off: Cross-restaurant analytics (e.g., "top cuisines in NYC") requires scatter-gather or a separate analytics replica. Popular restaurants become hot shards — mitigated by reserving multiple shards per restaurant or using a secondary hash.

Critical: booking writes must route to restaurant's primary region

A restaurant in New York has its authoritative DB in us-east-1. A European user booking that restaurant must have their reservation write routed to us-east-1 — even though reads can come from an EU read replica. Never allow a booking to commit on an async replica.

12. Advanced Topics (Staff-Level Signals)

Waitlist Auto-Promotion
When a reservation is cancelled, Kafka event fires → Waitlist Service picks next eligible user → creates soft hold → sends "you have 10 minutes to confirm" push notification. Race condition: two waitlist users promoted simultaneously → only first HOLD that converts to a confirmed booking wins (same DB transaction pattern).
Overbooking Model (like airlines)
Use historical no-show data per restaurant to compute an overbooking coefficient. If a restaurant has 15% no-show rate, allow 115% capacity bookings. Requires ML model per restaurant per time-of-day, day-of-week. Add this to the conversation if the interviewer probes for ML integration.
Rate limiting and bot protection
Reservation bots are a real problem (scalpers for trendy restaurants). Token bucket rate limit per user_id and per IP. Require CAPTCHA after N failed booking attempts. Flag suspicious patterns: same user booking 20 restaurants within 1 minute.
