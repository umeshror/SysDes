1. Executive Summary
This document describes the production architecture for a globally scalable URL shortening service (analogous to Bit.ly or TinyURL). The system converts long URLs into compact, opaque short codes and performs low-latency HTTP redirects at internet scale.

Core Value Proposition
Input:   https://www.amazon.com/products/path/item/123456
Output:  https://short.ly/aZ3x9K

The architectural thesis is straightforward: URL shorteners are overwhelmingly read-heavy. For every URL created, hundreds or thousands of redirect lookups occur. Every design decision — caching layers, replication topology, region distribution, analytics pipeline — flows directly from optimizing the read path.

2. Problem Definition & Scope
Functional Requirements
Generate a short URL code for any valid long URL.
Redirect users from a short URL to its original URL (< 100 ms).
Support optional custom aliases (e.g., short.ly/my-campaign).
Support URL expiration — links automatically deactivate after a set date.
Track redirect analytics (click counts, geographic data, referrer).
Allow authenticated users to manage their links (list, disable, delete).

Non-Functional Requirements
High availability: the redirect path must survive any single component failure.
Low latency: redirects must be served from geographically proximate infrastructure.
Horizontal scalability: stateless services that scale linearly with traffic.
Security: abuse prevention, phishing link detection, enumeration resistance.
Observability: full tracing, metrics, and alerting across all services.

Out of Scope (v1)
Explicitly Excluded from This Design
Enterprise billing and tiered plans
Deep analytics dashboards (BI tooling, funnels, A/B attribution)
ML-based spam and phishing detection
Content classification and safe-browsing integration
White-label custom domain management
QR code generation and management

The query pattern is simple and highly cacheable:

6. Write Path — URL Creation
API Contract
POST /v1/urls
{
  "long_url": "https://example.com/very/long/path",
  "custom_alias": "my-campaign",
  "expires_at": "2025-12-31T00:00:00Z"
}
Response: HTTP 201 Created
{
  "short_url": "https://short.ly/aZ3x9K",
  "short_code": "aZ3x9K",
  "expires_at": "2025-12-31T00:00:00Z"
}

Write Flow — Step by Step
Client sends POST /v1/urls with long_url and optional metadata.
API Gateway validates the Bearer token and applies rate limiting (e.g., 100 creates/min for free tier).
Write Service validates the long_url (must be syntactically valid, not on blacklist).
If custom_alias provided: check uniqueness in DB. If taken, return HTTP 409 Conflict.
Otherwise: Write Service requests the next ID from the ID Generator.
ID Generator issues an ID from its pre-fetched batch (from Redis INCR).
Write Service encodes the ID as Base62 to produce the short_code.
Write Service inserts the row into Postgres Primary. Unique constraint on short_code prevents duplicates.
Write Service returns the complete short URL to the client.

Why the write path does NOT warm the cache
Newly created URLs receive minimal traffic initially. Warming the cache on every write wastes Redis memory on links that may never be clicked. Instead, cache entries are populated lazily on first redirect (cache-aside pattern). Frequently accessed URLs will naturally self-populate.

Counter + Base62 — Implementation
Base62 uses the alphabet [a-zA-Z0-9] (62 characters). A 6-character code provides:
62^6 = 56,800,235,584 ≈ 56 billion unique codes
At 10M new URLs/day, this provides 15+ years of capacity before needing 7-character codes.

ID Allocation via Redis Batching
Each Write Service instance pre-fetches a batch of IDs from Redis using INCRBY:
INCRBY global_url_counter 1000  →  returns 501000
The server now owns IDs 500001–501000 and allocates them locally, making only 1 Redis call per 1,000 URLs created. This reduces Redis load by 1,000× while maintaining uniqueness.

Multi-Region ID Partitioning
To eliminate cross-region Redis coordination, each region is pre-assigned a non-overlapping ID range:

Trade-off: Sequential IDs are Enumerable
Sequential Base62 codes allow attackers to scrape all created URLs by incrementing the code. This is an acceptable known trade-off for v1.
8. Read Path — Redirect
The redirect path handles the majority of system traffic and is the primary latency-critical code path. It must be optimized for minimal hops and maximum cache utilization.

Redirect Flow — Step by Step
User browser requests GET https://short.ly/aZ3x9K.
GeoDNS resolves to the nearest regional CDN edge node.
CDN checks its edge cache. On hit (rare for dynamic redirects), returns immediately.
CDN forwards to the regional API Gateway, which routes to a Redirect Service pod.
Redirect Service looks up short_code in Redis. On cache hit (>95% of requests): returns HTTP 302 Location header immediately.
On cache miss: Redirect Service queries the nearest Postgres Read Replica.
DB returns long_url, status, expires_at. Service validates status and expiry.
Redirect Service writes the entry to Redis (TTL = min(expires_at, 24h)).
Returns HTTP 302 Location: <long_url> to client.
Asynchronously: Redirect Service publishes a click event to Kafka for analytics.

HTTP 301 vs. HTTP 302 — Critical Decision

The performance cost of 302 vs. 301 is negligible given our caching layer. The analytics and control benefits far outweigh the marginal extra server round-trip.

Cache Strategy — Cache-Aside (Lazy Population)
Cache key: short_code
Cache value: { long_url, status, expires_at } — everything needed to serve a redirect
TTL: min(url.expires_at, 24 hours) — expired URLs automatically evict
Cache miss: query Read Replica, populate cache, serve redirect
Cache invalidation: on URL disable/delete, explicitly DEL the Redis key

Cache Hit Rate Impact
Why >95% Cache Hit Rate is Achievable
URL access patterns follow a heavy power-law distribution: the top 1% of URLs receive ~80% of all traffic (Zipf's Law). With Redis holding 10M hot URLs (~5 GB), the vast majority of traffic is served from memory. The DB only sees cache-miss traffic — roughly 2,500 RPS at 95% hit rate vs. 50,000 total RPS.

Replication Topology
Postgres streaming replication provides a simple, proven high-availability topology:
Primary (writes) ──→ Read Replica 1 (US) ──→ redirect reads
                ──→ Read Replica 2 (EU) ──→ redirect reads
                ──→ Read Replica 3 (APAC) → redirect reads

All writes go to Primary. Redirect Service reads from the replica in its region.
Replication lag is typically < 1 second — acceptable for redirect use (eventual consistency).
If Primary fails, a replica is promoted using Patroni or pg_auto_failover (RTO ~30 seconds).

Future: Sharding Strategy
At extreme scale (>100B URLs, >10,000 writes/sec), horizontal sharding becomes necessary. The recommended approach:
Shard by short_code prefix (first character): 62 shards, each handling ~1/62 of the keyspace.
Alternatively, use CitusDB (Postgres-native sharding) to avoid application-layer routing logic.
DynamoDB or Cassandra become viable at this scale — but this threshold is unlikely for 5+ years.

Traffic Routing
GeoDNS (e.g., AWS Route 53 Latency Routing or Cloudflare) routes users to their nearest regional cluster.
Each region runs a full stack: API Gateway → Redirect Service → Redis → Read Replica.
Write traffic can be handled locally (eventual consistency) or forwarded to a global primary (strong consistency).

Cross-Region Consistency Model
Consistency Trade-off for Redirects
Newly created URLs may take 1–5 seconds to replicate to all regions. During this window, a user in EU who just created a URL via US servers may get a 404 on redirect if they immediately click the link from the EU region. Mitigation: (1) create URLs in the user's local region, (2) use a short "write-through" period where the creating region's cache is authoritative, or (3) accept this as an edge case too rare to optimize in v1.
11. Analytics Pipeline
The Challenge: 1B Events Per Day
Every redirect generates a click event containing: short_code, timestamp, user-agent, IP address (geolocation), and referrer. Writing these directly to Postgres at 11,600 RPS would saturate the DB and add latency to the critical redirect path.

Event Streaming Architecture
The solution decouples the analytics write path from the redirect critical path using Kafka:
Redirect Service → Kafka Topic (clicks) → Flink/Spark → ClickHouse/BigQuery → Dashboard

Why Fire-and-Forget is Acceptable
Click events are published to Kafka asynchronously after the 302 redirect is returned. If Kafka is temporarily unavailable, click events are dropped rather than blocking the redirect. Analytics accuracy is a "best effort" SLA — users tolerate approximate counts far more than they tolerate slow redirects.

The Redirect Service implements circuit breakers on both the Redis and DB connections:

15. Operational Concerns
URL Expiration Cleanup
Expired URLs must be removed to avoid wasting storage and to ensure redirect returns 410 Gone (not 302 to a stale URL). Two-phase approach:
Redirect Service checks expires_at on every cache-miss DB lookup. Returns 410 if expired.
Background cron job runs hourly: DELETE FROM url_mappings WHERE expires_at < NOW() AND status = 'active'. Uses the partial index on expires_at for efficiency.

Cache Invalidation on URL Disable
When a user disables or deletes a URL, the cache entry must be evicted to prevent stale 302 redirects:
Write Service → Redis DEL short_code → DB UPDATE status = disabled
This is a "write-through invalidation" pattern. The window for stale redirects is bounded by the time between the DB write and the Redis DEL completing — typically < 10 ms on the same network.

Blue-Green Deployment
Redirect Services are deployed using blue-green strategy. Because the service is stateless, traffic can be shifted instantly with zero downtime. Rollback is a single load balancer reconfiguration.

18. Interview Prep — Staff-Level Follow-Up Questions
FAANG Staff-level interviewers will probe these areas after the initial design. Being prepared for these demonstrates depth.

Q: How would you handle a viral URL getting 1M clicks in 1 minute?
This is a "hot key" problem. A single Redis key can handle ~100K ops/sec per node, so 1M/min (~16K RPS) is fine on a single node. However, if traffic exceeds that:
Redis Cluster: distribute the key across multiple nodes using local replication (client-side read splitting).
CDN caching: for truly viral links, push the mapping to CDN edge caches to absorb the spike without hitting origin.
In-process LRU: Redirect Service pods maintain a small in-memory LRU cache (e.g., 1,000 entries). A viral URL will cache in-process across all pods, effectively distributing the load.

Q: How do you generate IDs without a central coordinator?
Twitter Snowflake approach: encode region ID (5 bits) + machine ID (10 bits) + timestamp (41 bits) + sequence (12 bits) = 64-bit integer. No coordination required. Each machine generates globally unique IDs autonomously. Trade-off: IDs depend on clock synchronization; NTP drift can cause ID collisions (mitigated by rejecting IDs from the past).

Q: How do you ensure the system can handle 10× traffic overnight?
Auto-scaling: Kubernetes HPA scales Redirect Service pods based on CPU and custom metrics (requests per pod). Redis scales vertically first; if a single node exceeds 80% capacity, switch to Redis Cluster. Postgres read replicas are pre-provisioned — adding a replica takes ~30 min for WAL catch-up, so this must be proactive, not reactive. CDN absorbs the first wave of traffic increases with zero infrastructure changes.

Q: How do you prevent a single bad deploy from taking down all redirects globally?
(1) Blue-green deployment: new version receives 0% traffic until health checks pass. (2) Canary releases: route 1% of traffic to new version for 15 minutes; auto-rollback if error rate or latency increases. (3) Feature flags: new behavior hidden behind flags; enables instant rollback without redeploy. (4) Regional rollout: deploy to one region first (e.g., APAC smallest), monitor for 1 hour, then proceed.
