0. Introduction

Code review is one of the most powerful, yet most misunderstood, practices in software engineering. Done well, it accelerates the team, spreads knowledge, and catches critical bugs. Done poorly, it creates resentment, stalls velocity, and fosters a toxic culture.

This guide is a compilation of best practices from the world's most effective engineering organizations—including Google, Microsoft, and Netflix—combined with academic research. It provides actionable tactics for both reviewers and authors to make the review process a collaborative engine for growth rather than a bureaucratic hurdle.

1. Philosophy: Why Code Review Exists

Before tactics, you need to understand the purpose. Most developers think code review is about catching bugs. That's too narrow. The resources on the Awesome Code Review list converge on a richer picture:

The Four Real Purposes

  1. Codebase health over time — The primary goal isn't perfection in any single PR. It's that the codebase improves on a trajectory. A CL that makes things 10% better should be approved, even if it isn't perfect.
  2. Knowledge sharing — Reviews spread understanding of the codebase across the whole team. Microsoft's research shows that developers cite knowledge transfer as the #1 value of code review — ahead of bug detection.
  3. Mentorship — Reviews are an opportunity to pass along best practices, architectural instincts, and domain knowledge to newer developers.
  4. Social bonding — A well-run code review builds trust between teammates. It signals "I care about your success and the quality of what we ship together."
"Code reviews are as much a social exercise as a technical one. They're an opportunity for teammates to share knowledge and bond through collaboration."
⚠️ The Anti-Pattern: Gatekeeping

If your reviews feel like a toll booth — where developers grudgingly pay their way through — you've lost. Reviews should feel like collaboration, not inspection. The difference shows up in language, speed, and tone. All of that is in your control as a reviewer.

2. What to Actually Look For

Google's engineering practices document gives the most complete checklist:

🧭 Design

Does the change fit the architecture? Are pieces interacting well?

❌ Bad Design Signal

A developer adds a feature by storing user preferences in the HTTP session object. Works now — but preferences are lost on logout, can't be shared across devices, and can't be queried from admin tools.

✅ Right Comment

"Storing prefs in the session means they can't survive a logout or be accessed server-side. Would you be open to persisting this to the UserProfile table instead? Happy to discuss the migration path."

⚙️ Functionality

Does the code do what the author intended? Does it do what users need?

  • Think about edge cases: empty lists, null values, concurrent modification, very large inputs
  • Think about race conditions in async/parallel code
// What would a reviewer catch here? function calculateAverage(numbers) { return numbers.reduce((sum, n) => sum + n, 0) / numbers.length; // BUG: if numbers = [], returns NaN (0 / 0) } // After the review: function calculateAverage(numbers) { if (numbers.length === 0) return 0; return numbers.reduce((sum, n) => sum + n, 0) / numbers.length; }

🧠 Complexity

"Reviewers should be especially vigilant about over-engineering. Encourage developers to solve the problem they know needs to be solved now, not the problem the developer speculates might need to be solved in the future."
🚫 YAGNI — You Aren't Gonna Need It

A developer building a NotificationService might add plugin hooks, strategy patterns, and event buses "for future extensibility." But if the current feature just needs to send one email — all of that is waste. Build what you know you need, today.

🧪 Tests

Tests are code too. Ask: Will this test actually fail if the code breaks? Does it test behavior or is it a ceremony that always passes?

// Weak test — tests nothing meaningful: it('should return a user', () => { const result = getUser(1); expect(result).toBeDefined(); // Always true if no exception thrown }); // Strong test — tests actual behavior: it('should return the correct user name and email', () => { const result = getUser(1); expect(result.name).toBe('Alice'); expect(result.email).toBe('alice@example.com'); }); it('should throw NotFoundError for a non-existent ID', () => { expect(() => getUser(999)).toThrow(NotFoundError); });

📛 Naming

Names are the primary documentation of code. Bad names force every future reader to reverse-engineer intent.

❌ Confusing const d = new Date();
let x = users.filter(u => u.a);
function proc(inp) { ... }
✅ Clear const createdAt = new Date();
let activeUsers = users.filter(u => u.isActive);
function processPayment(order) { ... }

💬 Comments in Code

Code comments should explain why, not what. If the "what" isn't obvious from the code, fix the code — don't add a comment to explain confusing code.

📐 Style

Style debates with no canonical reference are a waste of time. The style guide is law. If there is no style guide, accept the author's style — and then create a style guide after.

3. How to Navigate a PR / CL

A PR with 30 changed files is overwhelming if you start at the top and work down. Google's engineering practices give a structured way to navigate:

  1. Read the description first. Does this change make sense? Is it solving the right problem? If the description is missing or vague, ask for one before reviewing.
  2. Find the "main" file. Usually one file has the largest number of logical changes. Start there.
  3. Read the tests. Tests tell you what the author intended to do. They're the executable specification. Read them before the implementation.
  4. Check for major design problems immediately. If there are architectural issues, flag them right away — even if you haven't finished reviewing.
  5. Review the rest in logical order. After major files, go through remaining files systematically.
💡 When to Reject Before Starting

Sometimes a PR shouldn't exist at all. Reject early and politely: "Looks like you put good work into this! However, we're moving away from the FooWidget system you're modifying. Would you be open to discussing an alternative approach before we proceed?"

4. Speed: The Most Underrated Factor

Most complaints developers have about code review are actually complaints about speed. Slow reviews cause cascading damage:

  • Team velocity drops — other developers are blocked waiting for their dependencies to land
  • Context is lost — the author has moved on mentally; revisiting old code is now expensive
  • Quality pressure builds — developers start accepting subpar code just to get things moving
  • Cleanups stop happening — nobody refactors if they know it'll sit in review for a week
"One business day is the maximum time it should take to respond to a code review request."
— Google Engineering Practices

The Right Tradeoff: Personal vs. Team Velocity

Don't interrupt deep work. Wait for a natural break (after lunch, end of a task), then review promptly.

When to Give LGTM With Outstanding Comments

You can approve a PR while still leaving comments if you're confident the developer will address the remaining notes and the comments are minor. This avoids an unnecessary round-trip for low-stakes nits.

5. Writing Great Review Comments

The Core Rule: Code, Not Person

Every comment should be about a line of code, a design decision — never about the developer as a person.

❌ Personal "You wrote this in the worst possible way."

"Did you even test this?"
✅ About the Code "This function will throw if the array is empty. What would you think about adding a guard clause?"

"There doesn't appear to be a test for the null input case — would a test here help document this behavior?"

The "Never Say You" Technique (mtlynch)

Never using the word "you" in a review comment forces you to phrase feedback about the code, not the person who wrote it.

❌ With "you" "You need to handle the error here."

"Why did you use a loop instead of a map?"
✅ Without "you" "This error case isn't handled — would it make sense to return an empty array here?"

"Curious about the loop vs. map choice here — is there a performance reason?"

Ask Questions, Don't Issue Commands

❌ Commands "Rename this variable."

"Move this to a separate function."
✅ Questions & Suggestions "What would you think about a name like activeUsers to make the intent clearer?"

".map() might communicate the intent more clearly here — curious if you considered it?"

Praise Good Work

✅ Examples of Good Praise

"This error handling is really clean — I'll remember this pattern."

"Great test coverage on the edge cases. Exactly what this function needed."

Signal Why Something Matters

💡 Example with Context

"This query runs inside the loop, so for 1,000 users we're making 1,000 DB calls. Moving it outside and batching the results will make this page load 50× faster under real traffic."

6. Conventional Comments

Conventional Comments is a standard format for writing review comments that immediately communicates the reviewer's intent by prefixing every comment with a typed label.

The Format

<label> [(decorations)]: subject Optional discussion — explain the "why", provide context, suggest a path to resolution, or cite relevant documentation.

The Labels

blocker issue suggestion question nitpick praise thought todo
Label Meaning Action Required?
blocker Must be fixed before merge. A real defect, security issue, or correctness failure. Yes — cannot merge
issue A problem that needs to be addressed. Yes — should fix
suggestion A proposed improvement. Pair with (blocking) or (non-blocking). Depends on decoration
question A genuine question seeking understanding, not implying a problem. Answer, not necessarily change
nitpick A trivial preference. Almost always non-blocking. Usually no
praise Genuine positive recognition. No action needed. No
thought An idea that might spark discussion. Not actionable right now. No — food for thought
todo A small, clear action item. Usually blocking. Yes — before merge

Real Examples

blocker: This endpoint has no authentication check. Any unauthenticated user can access all customer data. Please add the @RequireAuth decorator before merging. suggestion (non-blocking): The .filter().map() chain could be a single .reduce() call, which avoids a full second pass. Only worth changing if performance is a concern here. nitpick (non-blocking): "isUserAuthenticated" could just be "isAuthenticated" since the context already implies a user. Up to you! praise: This retry logic with exponential backoff is elegant. I'll borrow this pattern for the jobs queue.
🏆 Why This System is Powerful

Labels remove the guesswork. The author knows exactly what they're dealing with: is this a crisis or a nitpick? Can they merge after answering a question, or do they need to redesign something?

7. Netlify's Feedback Ladder

Netlify's feedback ladder lets teams communicate the spectrum of review comments explicitly.

Rung Label Meaning
🔴 6 Blocker Cannot merge. Correctness, security, or a fundamental design failure.
🟠 5 Should Fix Strong recommendation. Would significantly improve code health.
🟡 4 Consider A suggestion worth thinking about. Won't block the PR.
🟢 3 Nit A trivial stylistic preference. Take it or leave it.
🔵 2 Praise Calling out something good. No action needed.
⚪ 1 FYI Sharing information. No action requested.
"Roundtrips — from teammate to reviewer back to teammate — are expensive, costing up to two working days of a sprint each time."

Self-Review as a Pre-emptive Tool

Netlify also recommends that authors review their own code before submitting and annotate it with comments meant for the reviewer, proactively answering questions and saving an entire roundtrip.

8. Toxic Behaviors to Unlearn

🧨 Toxic Behavior #1: Opinion Passed Off as Fact

❌ Toxic"This is wrong. Use a hashmap."
✅ Backed by Evidence"For this size of input (>1000 items), a Map lookup is O(1) vs O(n) for the array search. If performance matters here, the Map would be worth the added complexity."

🧨 Toxic Behavior #2: The Comment Avalanche

Dumping 50 comments in a first review pass is overwhelming and demoralizing. The goal is incremental improvement over time, not perfection in one pass.

🧨 Toxic Behavior #3: Scope Creep Used as Power

Blocking a PR because of pre-existing problems the author didn't cause is a form of hostage-taking. If it was broken before this PR, track it in a separate ticket.

🧨 Toxic Behavior #4: Sarcasm and Condescension

❌ Corrosive"Another O(n²) loop. Classic."

"This is... interesting design."
✅ Constructive"This nested loop is O(n²) — for large data sets that's a concern. A Map-based approach would bring it to O(n)."

🧨 Toxic Behavior #5: Judgmental "Why" Questions

❌ Accusatory"Why didn't you just use the existing utility function?"
✅ Curious"There's an existing utility function formatDate() that does something similar — would that work here, or is there a reason this needs a custom implementation?"
🚨 Why This Matters Beyond Feelings

Toxic behaviors in code reviews can be more harmful than no code review at all, because they actively stifle creativity, confidence, and the willingness to ask questions.

9. Code Reviews Like a Human (mtlynch.io)

High-Level Before Low-Level

Don't review style nits in round one if there are architectural problems to discuss. Sequence your rounds:

  1. Round 1: Architecture, design, approach. Is this the right solution?
  2. Round 2: Logic, correctness, edge cases. Does it work correctly?
  3. Round 3: Style, naming, readability. Is it easy to maintain?

Frame Feedback as Collaboration

❌ Gatekeeper Frame"I'm not approving this until X is fixed."

"This needs to be completely rewritten."
✅ Collaborator Frame"This is close — just need to sort out X before we land it."

"The approach here is making this complex. What if we tried Y instead?"

When to Meet Synchronously

If a thread has gone 4+ messages and no consensus is emerging, stop the async discussion and schedule a 10-minute call. After the meeting, post a comment summarizing the decision made.

10. Being a Great PR Author

Write a Great Description

A good PR description has three parts: What (what does this change do?), Why (what problem does it solve?), and How to test (how can the reviewer verify this works?).

❌ Bad PR Description

Title: "fix stuff"
Body: (empty)

✅ Good PR Description

Title: "Fix order total calculation when discount codes are stacked"

Root cause: The discounts were applied sequentially to the original price rather than cumulatively on the remaining balance.
Fix: Caps the combined discount percentage at 100% before applying.
Testing: Added unit tests for single discount, stacked discounts, and the edge case of >100% combined.

Review Your Own Code First

Before requesting review, open the diff as if you were the reviewer. You'll catch embarrassing issues and the act of explaining your own code often reveals design problems.

Acknowledge Every Comment

For every comment, either make the change and mark it resolved, or reply with your reasoning. Never silently ignore a comment.

11. Ship Small Diffs

📊 The Data

Teams that keep PRs under 200 lines ship approximately 40% more code than teams doing 200+ line PRs.

"Ask a programmer to review 10 lines of code, he'll find 10 issues. Ask him to review 500 lines, he'll say it looks good."

How to Split Large Work

  • Separate refactoring from feature work. Rename a function in one PR; add the new behavior in the next.
  • Use feature flags. Merge incomplete code to main behind a flag that's off in production.
  • Plan your PRs before you code. List the steps the feature requires. Most of those steps can be separate PRs.
  • Database migrations first. Add columns in one PR; write the code that uses them in the next.

What "Small" Actually Means

Small doesn't just mean few lines — it means one logical change. A PR that touches 50 files across three different concerns is hard to review even if it's only 200 lines.

12. Stacked Pull Requests

Stacked PRs are the advanced technique for keeping diffs small when building a large feature with natural sequential dependencies.

The Stacked PR Workflow

  1. Create branch fb-schema from main. Add the DB migration. Open PR #1 targeting main.
  2. While PR #1 is in review, create branch fb-model from fb-schema. Open PR #2 targeting fb-schema. The diff only shows the model changes.
  3. Continue stacking: fb-service from fb-model, fb-api from fb-service, etc.
  4. Merge in order: PR #1 first, retarget PR #2 to main, merge, and so on.
⚠️ The Trade-Off

Stacked PRs create rebasing complexity. If PR #1 is changed based on review feedback, all downstream branches need to be rebased. Tools like ghstack automate this.

13. Handling Pushback & Disagreements

When the Author Pushes Back

First: actually consider that they might be right. They're closer to the code. If their argument makes sense from a code health perspective, drop the issue and acknowledge they were right.

💡 Good Disagreement Example

Reviewer: "This should use our standard RetryPolicy class rather than manual retry logic."

Author: "The RetryPolicy class doesn't support this timeout behavior I need."

Reviewer: "That's a fair point. Two options: (1) extend RetryPolicy with a timeout parameter, or (2) use the custom logic now and file a ticket to generalize it. Which do you prefer?"

Escalation Path

  1. Switch to a synchronous conversation — text is terrible for conflict resolution
  2. Bring in a third technical opinion: a tech lead, architect, or domain expert
  3. Reference the team's documented standards — having written ADRs removes personality from technical disputes

14. Building an Inclusive Review Culture

The Confidence Gap

Experienced developers often have confidence to push back on comments they disagree with. Newer developers don't. Label your feedback clearly and explain your reasoning more, not less, for developers who are still learning.

Don't Pile On

When multiple reviewers are assigned, coordinate — pick a primary reviewer and have others only add what the primary missed.

Psychological Safety

The ultimate measure of your review culture is: do people want to send you their code?

Onboarding New Members

For new developers especially, the first few reviews set expectations that last. Be generous with context, explicit about what's blocking vs. optional, and sparing with feedback volume.

15. What Research Says

Microsoft's Study (Bosu, Greiler, Bird — 2015)

  • Comments were most valued when they pointed to relevant expertise the author lacked
  • Vague, subjective comments ("this could be cleaner") were consistently rated as unhelpful
  • Knowledge transfer was cited as the #1 value of code review — ahead of defect detection
  • Early, frequent reviews were significantly more useful than large, infrequent ones

The SmartBear/Cisco Study

  • Reviewers catch significantly fewer defects after 60–90 minutes of review time
  • Reviews of more than 200–400 lines produce significantly fewer bug findings per line
  • The sweet spot is reviewing less than 400 lines over no more than 60 minutes

What Good Comments Look Like (in Data)

  • Specific — pointed to a concrete problem, not a vague pattern
  • Actionable — suggested a clear path to resolution
  • Educational — explained the "why" not just the "what"
  • Delivered quickly — value drops dramatically with time

16. Automation: Let Computers Do Their Job

What to Automate

  • Formatting — Prettier, gofmt, rustfmt. No human should ever leave a comment about indentation.
  • Linting — ESLint, Pylint, Rubocop. Catch undefined variables, unused imports, deprecated APIs.
  • Type checking — TypeScript, mypy. Catch type errors before humans read the code.
  • Test execution — CI runs tests automatically. No PR should be reviewable if tests are failing.
  • Security scanning — Tools like Snyk, Dependabot, and Semgrep catch common vulnerability patterns.
✅ The Right Division of Labor

Automation handles: style, formatting, linting, test execution, type checking, coverage, known security patterns
Humans handle: design, logic correctness, edge cases, readability, mentorship, architectural fitness

17. The 10 Principles to Live By

01
Automate the mechanical stuff
Linters, formatters, CI. Free reviewers to think about design and logic.
02
Approve when it improves things
Don't hold out for perfection. A CL that makes the codebase better deserves to land.
03
Keep PRs small — always
One logical change per PR. If it's large, break it up. This is a skill; practice it.
04
Label your feedback clearly
Use Conventional Comments or a feedback ladder. Eliminate ambiguity about what's blocking.
05
Back opinions with evidence
Style guide, docs, benchmarks, or concrete reasoning. "I prefer" is never enough.
06
Comment on code, not the person
"This function" not "you wrote". Every single time. No exceptions.
07
Ask questions, don't issue commands
"What would you think about..." opens collaboration. "Do this." closes it.
08
Praise good work genuinely
It motivates, builds psychological safety, and models the behaviors you want to see.
09
When stuck, talk
Async threads spiral. A 10-minute call resolves what 30 comment replies couldn't.
10
Respond within one business day
Most complaints about code review are really complaints about speed. Be fast.
"The best code reviewers are great not because they find the most bugs, but because they create an environment where people want their code reviewed."
