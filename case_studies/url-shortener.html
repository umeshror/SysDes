Global URL Shortening Platform

Staff / Principal Engineer Level Case Study — Version 4.0

📝 Architectural Thesis

URL shorteners are overwhelmingly read-heavy. For every URL created, thousands of redirect lookups occur. Every design decision — from replication topology and caching layers to the analytics pipeline — flows directly from optimizing the read path for sub-100ms latency.

1. Executive Summary

This design describes a production-scale architecture for a globally scalable URL shortening service (analogous to Bit.ly). The system performs low-latency HTTP redirects at internet scale while ensuring 11 nines of data durability for permanent user assets.

Platform Targets

Requirement Target Rationale
Redirect Latency (p99) < 100 ms globally Beyond 200 ms, user conversion drops sharply.
Availability 99.99% Outage means millions of broken links worldwide.
Redirect Throughput 50,000 RPS Peak Based on 1B redirects/day with 10x peak factor.
Read : Write Ratio ~1,000 : 1 Heavy read-write asymmetry.
Data Durability 11 Nines URLs are permanent user assets.

2. Problem Definition & Scope

Functional Requirements

  • Short code generation for long URLs.
  • Ultra-low latency redirects (< 100 ms).
  • Custom aliases & URL expiration (TTL).
  • Real-time redirect analytics.
  • User link management (list, disable).

Non-Functional Requirements

  • HA: No single point of failure.
  • Scale: Stateless linear scaling.
  • Security: Phishing & Abuse prevention.
  • Obs: Tracing, metrics, and alerting.

3. Capacity Planning

Scaling challenges are derived from read-write asymmetry. 1.8 TB/year of storage is trivial; serving 50,000 RPS globally is the core architectural hurdle.

Metric Calculation Result
Daily Redirects 100M DAU × 10 clicks 1 Billion
Peak Redirect RPS Avg 11.6K × 10x ~50,000 RPS
Write Throughput 10M creates / 86,400s ~115 writes/sec
Redis Hot Cache 10M URLs × 500 bytes ~5 GB (Fits one node)

4. Data Model

Query pattern is simple: SELECT long_url FROM url_mappings WHERE short_code = ?. We use indexing on short_code (PK) and expires_at (partial index) for efficient cleanup.

Column Type Description
short_code VARCHAR(10) PK - Base62 encoded unique ID.
long_url TEXT Original destination (Indexed for dup-check).
expires_at TIMESTAMPTZ Indexed for hourly cleanup cron.
user_id BIGINT FK to Users; supports pagination.

6. Write Path — URL Creation

The Write Service prioritizes integrity over latency. It requests batches of IDs from the ID Generator and persists mappings to the primary database.

sequenceDiagram participant User participant WS as Write Service participant IDG as ID Generator participant DB as Postgres Primary User->>WS: POST /v1/urls (long_url) WS->>WS: Validate URL & Blacklist check WS->>IDG: Request next ID (from batch) IDG-->>WS: Issue ID (e.g. 10001) WS->>WS: Base62 Encode ID (-> aZ3x9K) WS->>DB: INSERT Mapping DB-->>WS: Row Persisted WS-->>User: HTTP 201 Created (short_url)
Write Path Execution Flow
💡 Why not warm the cache?

Newly created URLs often have zero initial traffic. Warming the cache on every write wastes memory. We use Cache-Aside (lazy population) so only "hot" links eventually reside in Redis.

7. Short Code Generation

We chose Counter + Base62 Encoding. This guarantees zero collisions and allows for the shortest possible codes.

Approach Mechanism Pros Cons
Hash (MD5) Truncated Hash Deterministic Collision probability ❌
Random String Base62 Random Decentralized Birthday Paradox ❌
Counter Base62(Counter) Zero collisions, Shortest Coordination needed ✅

ID Allocation via Redis Batching

To eliminate contention, each Write Service pre-fetches IDs using INCRBY global_counter 1000. It now owns a block (e.g., 500k-501k) and allocates locally, reducing Redis calls by 1000x.

8. Read Path — Redirects

The Redirect Service is the most critical path. It achieves sub-100ms latency by performing a memory-first lookup and serving an HTTP 302.

sequenceDiagram participant User participant CDN as Edge CDN participant RS as Redirect Service participant Cache as Redis Cluster participant DB as Postgres Replica User->>CDN: GET short.ly/aZ3x9K CDN->>RS: Forward Request RS->>Cache: GET aZ3x9K alt Cache Hit Cache-->>RS: { long_url, status, expires_at } else Cache Miss RS->>DB: SELECT mapping WHERE code=aZ3x9K DB-->>RS: Return long_url RS->>Cache: SET aZ3x9K (Lazy Population) end RS-->>User: HTTP 302 Location: long_url RS-)+Kafka: Fire-and-Forget Analytics Event
Redirect Path Execution Flow (Latency Optimized)

HTTP 301 Permanent

Browsers cache indefinitely. We lose all visibility into repeat clicks.

HTTP 302 Temporary

Browsers check our server every time. Enables full analytics and link deactivation. ✅

9. Database Selection: PostgreSQL

Relational SQL is chosen for its maturity and ACID guarantees. At 115 writes/sec, Postgres is vastly over-capable and operationally simpler than NoSQL.

Factor PostgreSQL NoSQL (Cassandra/Dynamo)
Uniqueness Enforced via PK/Unique Const Must implement at App Layer
Consistency Strong ACID Tunable / Eventual
Ops Extremely well understood Complex replication/tuning

10. Multi-Region Deployment

Multi-region is mandatory for latency. A Singapore user hitting a US East server faces >200ms RTT, failing our SLA before processing even begins.

Regional Traffic Partitioning

Each region runs a full stack. To avoid cross-continent ID coordination, each region is pre-assigned a unique ID range (e.g., US: 0-10B, EU: 10-20B, Asia: 20-30B).

11. Analytics Pipeline

Clicks are non-blocking. The Redirect Service publishes events to Kafka partition by short_code. Flink enriches the data (GeoIP) and performs 1-minute window aggregations before storing in ClickHouse.

12. Abuse Prevention

  • Google Safe Browsing: Scan long URLs at creation time.
  • Randomized ID Bits: Mitigate scraping of sequential IDs.
  • Token Bucket: Enforce 10 req/ID per minute for free tier at Gateway.

13. Staff-Level Failure Handling

Failure Detection Response
Redis Cluster Fails Health Check (~10s) Redirect Svc falls back to DB Read Replicas.
DB Primary Fails Patroni (~15s) Failover to Replica; 30s write-block window.
Entire Region Fails Global DNS Health Traffic shifts to next-nearest region via GeoDNS.

14. Observability

We monitor core SLAs: Redirect p99 latency, Cache Hit Rate (Alert < 90%), and Kafka consumer lag. 11 nines of durability is verified through regular automated WAL integrity checks.

15. Operational Concerns

  • Hourly Cleanup: Chron job deletes entries where expires_at < NOW().
  • Blue-Green Deployment: Stateless Redirect pods shift via load balancer.

16. Future Evolution

  • CDA Redirects: Edge Compute (Cloudflare Workers) for high-traffic links.
  • Serverless: Shift to Lambda@Edge for rare links to save infrastructure costs.

17. Summary of Key Decisions

Decision Chosen Approach Key Reason
ID Gen Batch Redis INCR Zero collisions, shortest code.
Redirect HTTP 302 Preserves Analytics & Control.
Database Postgres ACID safety, operational simplicity.

18. Staff-Level Prep: Viral URLs

The "Hot Key" Problem

If a URL gets 1M clicks in 1 minute, a single Redis node may saturate. Mitigation: Redirect service pods maintain a small in-process LRU cache (1k entries). Viral links cache across all pods, protecting Redis entirely.
