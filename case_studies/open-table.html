Design OpenTable

Case Study  |  Global Restaurant Reservation System — Two-sided Marketplace

🎯 Interview Signal

This is a two-sided marketplace with a real-time reservation engine — the same class as Airbnb, Ticketmaster, and OpenSea. The FAANG interviewer is looking for: (1) strong consistency for bookings, (2) eventual consistency for search, (3) how you prevent double booking at scale, and (4) your ability to reason about hot-partition problems.

1. Clarify Requirements

For Diners (Demand Side)

  • Search by location, date, time, party size, cuisine, price
  • View real-time available time slots
  • Make / modify / cancel reservations
  • Join waitlist when fully booked
  • Receive confirmation + reminders (email/SMS/push)
  • View booking history, leave reviews

For Restaurants (Supply Side)

  • Manage floor layout and table inventory
  • Define hours, reservation slots, party-size limits
  • Block time slots for private events
  • Real-time dashboard of upcoming bookings
  • Manage waitlist manually or automatically
Non-functional requirements (state these explicitly in the interview)
Zero double bookings — strong consistency required for reservation writes.
99.99% availability — no more than ~52 minutes downtime/year.
Search <200ms p99 — read latency SLA for restaurant/slot search.
Eventually consistent search OK — stale availability in search results is fine; final confirmation always validates against authoritative DB.
Multi-region, horizontally scalable.

2. Capacity Estimation

Metric Assumption QPS (avg) QPS (peak 10×)
Daily Active Users 10M — —
Restaurant searches 10M/day ~115 QPS ~1,150 QPS
Reservations created 1M/day ~12 QPS ~120 QPS
Restaurants 100K — —
Tables per restaurant 20 avg — —
Availability rows (15-min slots, 14h/day) 100K × 56 slots × 365 ~2B rows/year —
Interview insight: search is 10× heavier than writes

This shapes your entire architecture: read path and write path must be separated. Don't use the same DB for Elasticsearch-style search and for transactional reservation writes. The read path can be eventually consistent (cache + Elasticsearch). The write path must be strongly consistent (RDBMS with locking).

4. Core Design: Availability Engine (The Hardest Part)

This is where the interviewer will spend most time

The Availability Engine must ensure no double booking while handling concurrent requests. This is a classic distributed concurrency problem. Walk through at least two approaches and explain the tradeoffs.

Precomputed Time Slot Model (Recommended)

Divide each restaurant's day into 15-minute slots. Maintain a row per slot tracking available capacity. All reservation writes update this table atomically.

flowchart LR User --> GW[API Gateway] GW --> R[Reservation Service] R --> H{1. Create HOLD\n2-min TTL} H --> T{2. BEGIN TRANSACTION\nSELECT ... FOR UPDATE\nCheck capacity > 0\nDecrement capacity\nINSERT reservation} T -->|Commit| C[Reservation Confirmed] T -->|Rollback| F[409 Conflict\nNo slot available] C --> K[Emit Kafka event\nreservation.created] K --> N[Notification Service]

Double Booking Prevention: Three Approaches

❌ Compute on the fly (naive)

Query all reservations, calculate availability per request.

  • Correct but slow — O(N) table scans
  • Doesn't prevent race condition
  • Won't scale to 120 QPS peak writes

✅ Pessimistic locking (recommended)

SELECT * FROM availability
WHERE restaurant_id = $1
  AND time_slot = $2
FOR UPDATE;
-- If capacity > 0: decrement + insert
-- COMMIT atomically
  • Guarantees no double booking
  • Row-level lock, not table lock
  • Excellent for moderate write QPS

⚠️ Optimistic locking (alternative)

UPDATE availability
SET capacity = capacity - 1,
    version = version + 1
WHERE restaurant_id = $1
  AND time_slot = $2
  AND version = $version_read
  AND capacity > 0;
  • No locks held — better throughput under low contention
  • Retry on version conflict — adds latency under high contention
  • Use for less popular restaurants
The 2-minute HOLD pattern
When a diner clicks "Reserve" but hasn't confirmed yet: create a soft hold stored in Redis with a 2-minute TTL. This temporarily decrements shown availability. On confirm, run the actual DB transaction. On timeout, the hold expires automatically and the slot returns to available. This prevents the "phantom slot" problem where many users see the same slot and all try to book simultaneously.
Hot restaurant problem
Nobu Saturday 7pm gets 10,000 concurrent requests. With pessimistic locking, all threads line up for the same row lock — creating a thundering herd. Solutions: (1) a reservation queue per restaurant (serialize writes via Kafka partition keyed by restaurant_id); (2) slot-level partitioning; (3) rate limit per restaurant slot.

5. Data Model

Table Key Fields Notes
restaurants restaurant_id (PK), name, location (PostGIS), timezone, operating_hours Geo-indexed for proximity search
tables table_id, restaurant_id, capacity, floor_section Physical inventory
availability restaurant_id, time_slot, available_capacity, version Hot table — sharded by restaurant_id
reservations reservation_id, restaurant_id, user_id, time_slot, party_size, status, created_at Append-mostly; index on (restaurant_id, time_slot)
waitlist waitlist_id, restaurant_id, time_slot, user_id, priority, created_at Ordered by priority + created_at

6. Caching Strategy

Redis (TTL: 30–60s on availability, 5min on search)
Cache restaurant search results and approximate availability. Short TTL bounds staleness. Invalidate immediately on any booking. The final confirmation step always re-validates against the authoritative DB — the cache is only used to show "approximately available" in the search UI, never to approve a booking.
CDN (TTL: 24h on restaurant metadata)
Restaurant name, photos, cuisine, hours — highly cacheable, changes rarely. Purge on restaurant profile update. This offloads ~90% of read traffic for restaurant detail pages.

7. Sharding Strategy

Shard by restaurant_id
All data for a given restaurant lives in the same shard: availability, reservations, waitlist. This makes reservation transactions local to a shard (no cross-shard distributed transactions). Trade-off: Cross-restaurant analytics (e.g., "top cuisines in NYC") requires scatter-gather or a separate analytics replica. Popular restaurants become hot shards — mitigated by reserving multiple shards per restaurant or using a secondary hash.

8. Multi-Region Architecture

flowchart LR subgraph US-East UE[API + Services] --> PG_US[(PostgreSQL\nPrimary)] PG_US --> RR_US[(Read\nReplica)] end subgraph EU-West EU[API + Services] --> RR_EU[(Read\nReplica)] RR_EU -.->|async replication| PG_US end U_US([US Diner]) --> UE U_EU([EU Diner]) --> EU EU -->|booking write| UE
Critical: booking writes must route to restaurant's primary region

A restaurant in New York has its authoritative DB in us-east-1. A European user booking that restaurant must have their reservation write routed to us-east-1 — even though reads can come from an EU read replica. Never allow a booking to commit on an async replica.

9. Event-Driven Notification Flow

Kafka topics
reservation.created, reservation.modified, reservation.cancelled, reservation.reminded (triggered by a scheduler 24h + 2h before slot).
Notification Service consumes and fans out to: Email (SES/SendGrid), SMS (Twilio), Push (FCM/APNS). Retry on failure, DLQ for repeated failures. Notifications are async and eventually consistent — a 5-second delay in sending a confirmation email is fine; a 5-second delay in confirming a booking is not.

10. Failure Scenarios

Failure Impact Mitigation
Primary DB crashes Writes fail Automatic failover to standby (RDS Multi-AZ, <30s); recent writes from WAL replayed
Redis crashes Cache miss, higher DB load Fall through to DB; system is slower but correct; Redis rebuilt from DB on recovery
Notification failure User doesn't get confirmation email Kafka DLQ with exponential backoff retry; separate from booking path (doesn't block reservation)
Popular restaurant slot contention Lock waits, high latency Per-restaurant write queue (Kafka partition); request serialization; slot partitioning
Elasticsearch down Search fails Fallback to directly querying read replica with degraded ranking; search is not on critical path

11. Tradeoffs Summary

Decision Choice Why Cost
Consistency for booking Strong (pessimistic lock) Zero double bookings is a hard requirement Lower write throughput, lock contention at peak
Consistency for search Eventual (Elasticsearch) Search performance >> search freshness User may briefly see stale availability
Slot precomputation Precomputed availability table O(1) availability lookup — critical for read SLA Extra storage, sync complexity with table changes
Notification delivery Async via Kafka Decoupled, retry-safe, not in booking critical path Eventual delivery — user may wait seconds for email
Sharding key restaurant_id Transactions stay local to shard, no distributed txns Hot shards for popular restaurants; analytics is harder
Multi-region writes Route to restaurant's primary region Avoid split-brain, ensure authoritative availability Higher write latency for cross-region users

12. Advanced Topics (Staff-Level Signals)

Waitlist Auto-Promotion
When a reservation is cancelled, Kafka event fires → Waitlist Service picks next eligible user → creates soft hold → sends "you have 10 minutes to confirm" push notification. Race condition: two waitlist users promoted simultaneously → only first HOLD that converts to a confirmed booking wins (same DB transaction pattern).
Overbooking Model (like airlines)
Use historical no-show data per restaurant to compute an overbooking coefficient. If a restaurant has 15% no-show rate, allow 115% capacity bookings. Requires ML model per restaurant per time-of-day, day-of-week. Add this to the conversation if the interviewer probes for ML integration.
Rate limiting and bot protection
Reservation bots are a real problem (scalpers for trendy restaurants). Token bucket rate limit per user_id and per IP. Require CAPTCHA after N failed booking attempts. Flag suspicious patterns: same user booking 20 restaurants within 1 minute.
