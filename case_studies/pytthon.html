Section 01

The Execution Pipeline

When you type python script.py, it's tempting to imagine Python reading each line and executing it like a shell script. That's not what happens. Python runs your code through a multi-stage compilation and interpretation pipeline before a single instruction executes.

Here's the full picture:

CPython Execution Pipeline

Stage 1 — Lexing and Parsing

Python first reads the raw text of your file and breaks it into tokens — the smallest meaningful units of the language. Keywords like for, def, operators like +, identifiers, and literals are all tokens.

These tokens are then fed into a parser, which checks that they form valid grammar according to Python's language specification. If your code is syntactically wrong (mismatched parentheses, wrong indentation), this stage raises a SyntaxError. No actual execution has happened yet.

Stage 2 — AST Generation

A valid token stream is then transformed into an Abstract Syntax Tree. This is a tree of nodes that captures the meaning of your code, not just its text. Each node represents a construct: an assignment, a function call, a loop. The tree is "abstract" because it drops irrelevant details like whitespace and parentheses.

Stage 3 — Compilation to Bytecode

The AST is compiled into bytecode — a low-level sequence of instructions designed for the Python Virtual Machine, not your CPU. This step also produces a code object, a self-contained package that includes the bytecode plus everything it needs to run: constants, variable names, and nested code objects for inner functions.

Stage 4 — PVM Execution

The Python Virtual Machine takes the code object and runs it, instruction by instruction, on its internal stack. This is where your code actually does something.

Key Insight

Python is not purely interpreted. It compiles to bytecode first (like Java compiles to JVM bytecode), then interprets that bytecode. The difference from Java: CPython has no Just-In-Time compiler, so bytecode never gets further compiled to machine code.

Section 02

The Abstract Syntax Tree

The AST is the heart of Python's tooling ecosystem. Understanding it explains why linters, formatters, and type checkers work the way they do.

Take this expression:

x = (2 + 3) * 4

Python internally represents this as a tree of nodes. The assignment has two children: the target (x) and the value (a multiplication). The multiplication has its own children: the addition, and the literal 4. The addition has children 2 and 3.

AST for: x = (2 + 3) * 4

What the AST enables

Constant folding. The compiler can look at the Add(2, 3) node, see that both children are constants, and replace the whole subtree with Num(5) before any bytecode is emitted. This means (2 + 3) * 4 is compiled as if you wrote 20.

Tooling. Every linter, formatter, type checker, and security scanner in the Python ecosystem works by parsing your code into an AST and then walking or transforming that tree. pylint detects unused variables by checking if a Name node is ever read. black reconstructs source code by visiting the AST and emitting its own formatting. mypy infers types by annotating tree nodes.

Metaprogramming. Python exposes the ast module, letting you parse, inspect, and modify the tree at runtime. Frameworks use this for decorators, code generation, and DSLs.

Practical Takeaway

If you ever build a linter, a code transformer, or a DSL in Python — you'll be working directly with the AST. Learning it once pays forever.

Section 03

Bytecode — Python's Instruction Set

Bytecode is a compact, platform-independent sequence of instructions that the PVM understands. It's much simpler than machine code — there's no need to deal with registers, memory addresses, or CPU architectures. But it's also more abstract, which means the PVM has to do more interpretation work.

For a simple expression x = (2 + 3) * 4, after constant folding the bytecode looks like this:

## Bytecode for: x = 20
  2           0 LOAD_CONST               0 (20)     # push 20 onto stack
              2 STORE_NAME               0 (x)      # pop stack, store in 'x'
              4 LOAD_CONST               1 (None)   # implicit return value
              6 RETURN_VALUE                        # exit the frame

Each line is one instruction. The number on the left is the offset in bytes. You can inspect bytecode yourself:

import dis
def add(a, b):
    return a + b

dis.dis(add)

The Code Object

Bytecode doesn't exist in isolation. It's wrapped in a code object — a Python object (types.CodeType) that carries everything needed to execute a function or module:

Version Warning

Bytecode is not stable across Python versions. CPython's bytecode changes between releases — new instructions are added, old ones are renamed. The .pyc cache files include a version magic number precisely because they're invalid across versions.

Section 04

The Python Virtual Machine

The PVM is a stack-based virtual machine. Every computation it performs uses a simple stack: instructions push values onto the stack, operate on the top of the stack, and push results back. There are no general-purpose registers like in a real CPU.

Stack execution of: (2 + 3) * 4

Every time you call a function, a separate stack (called an evaluation stack) is created for that invocation inside its own frame. Values are pushed and popped as instructions execute. When the function returns, the frame is discarded.

Why Stack-Based
  • Simple to implement
  • Smaller instruction set
  • Easy portability across CPUs
  • No register allocation needed
The Cost
  • More instructions per operation
  • Slower than register-based VMs
  • No JIT compilation in CPython
  • Each step = interpreted overhead
Key Insight

A single Python line like a + b maps to multiple VM steps: load a, load b, dispatch the + operator (which calls __add__ on the type), push the result. The interpreter loop processes every one of these. This overhead — multiplied across millions of lines — is a core reason Python is slow relative to compiled languages.

Section 05

PyObject — Everything Is an Object

In CPython, every value — integers, strings, lists, functions, classes, even None and True — is a PyObject. This is a C struct at the heart of Python's dynamic type system.

PyObject memory layout

The ob_refcnt field is a counter of how many Python variables point to this object. When it reaches zero, the object is deallocated. The ob_type pointer points to the object's type, which is itself a PyObject — this is how Python knows which __add__ or __len__ method to call. The data section varies by type.

Why this is powerful — and costly

Because everything is a PyObject, Python can treat all values uniformly. A function that accepts "any object" works because every object exposes the same interface through its type pointer. Dynamic typing works because the type isn't tracked at compile time — it's stored in the object itself.

The cost is real though. A Python integer takes 28 bytes of memory. A C integer takes 4 bytes. That's a 7× overhead just for storage, before you factor in the indirection and pointer chasing that hurt CPU cache performance.

Key Insight

Python trades memory and speed for flexibility. The same code can operate on integers, floats, custom objects — no generics or templates required. The PyObject model is what makes Python's dynamism feel effortless to write, and expensive to run.

Section 06

Memory Management

Python uses a two-layer garbage collection strategy: reference counting handles most allocations instantly, while a cyclic garbage collector handles the edge cases that reference counting can't.

Reference Counting

Every PyObject maintains an ob_refcnt. When you assign a variable, the count goes up. When a variable goes out of scope or is reassigned, it goes down. When the count hits zero, the memory is freed immediately, without waiting for a GC cycle.

# refcount demonstration
import sys

a = []           # refcount = 1
b = a            # refcount = 2
print(sys.getrefcount(a))  # 3 (getrefcount itself adds 1)
del b            # refcount = 2 (back to a + getrefcount)

This determinism is why with blocks and context managers work reliably: file handles and database connections are released the moment the last reference disappears, not at some future GC pause.

Cyclic Garbage Collector

Reference counting has one fatal flaw: it can't handle cycles. If two objects reference each other, their counts never reach zero even when nothing else refers to them.

# Reference cycle — neither object can be freed by refcounting
a = []
b = [a]
a.append(b)
del a, b  # counts don't reach 0 — memory leak without cyclic GC

Python's cyclic GC periodically scans objects it knows can form cycles (containers like lists, dicts, and custom objects). It uses a reachability analysis: starting from roots (global variables, stack frames), any object it can't reach is garbage.

Generational Garbage Collection

The generational hypothesis — that most objects die young — is borne out by real programs. Python's GC optimizes for this by checking the youngest generation most frequently and promoting survivors upward.

Production Note

You can tune GC thresholds with gc.set_threshold(). In long-running servers with many short-lived objects, you can disable Gen 0 collection and trigger it manually between requests to avoid latency spikes.

Section 07

The GIL — Python's Most Misunderstood Feature

The Global Interpreter Lock is a mutex that protects CPython's internal state. At any point in time, only one thread can be executing Python bytecode. This is the single most controversial design decision in Python's history.

GIL behaviour: CPU-bound vs I/O-bound threads

Why does the GIL exist?

Without the GIL, every object mutation would need its own lock. Incrementing a reference count — something that happens millions of times per second — would require a lock acquisition and release. The GIL is a single coarse-grained lock that is far cheaper than thousands of fine-grained locks, and it makes CPython's C API dramatically simpler to use correctly.

Workarounds that actually work

Key Insight

The GIL is a design tradeoff, not a bug. It makes single-threaded CPython faster and safer, at the cost of CPU-bound multithreading. Python 3.12+ introduced per-interpreter GILs as a first step toward removing it. PEP 703 proposes making the GIL optional in a future release.

Section 08

Dictionary Internals

Python's dict is one of the most heavily optimized data structures in the language. Attribute lookup, module globals, keyword arguments — all of them internally use dictionaries. Getting this right matters enormously.

A Python dict is a hash table with open addressing. Each key is hashed to produce an index into a sparse array of slots. If the slot is empty, the key is inserted there. If it's occupied by a different key, Python probes nearby slots until an empty one is found.

Dict lookup flow

Why Python dicts are fast

Rather than a linked-list chain for collisions (chaining), Python uses open addressing — all entries live in the same flat array. This is cache-friendly because nearby slots are likely in the same cache line. The probing sequence uses a perturbation trick (involving the full hash value, not just the low bits) to reduce clustering.

Section 09

Function Calls and Frames

Every function call in Python creates a frame object — a PyObject that contains the complete execution state for that call. Frames are allocated on the heap (not the C stack), which is what enables Python's introspection capabilities.

Frame stack during nested calls

What a frame contains

Each frame holds: the local variables as a fixed-size array (faster than a dict), the evaluation stack for the current computation, the instruction pointer (which bytecode offset is currently running), and a back-pointer to the calling frame. That chain of back-pointers is exactly what Python uses to produce tracebacks.

Why this matters for performance

Frame objects are heap-allocated PyObjects. Creating one involves memory allocation, initialisation, and reference counting. In tight inner loops, calling a small function millions of times carries this cost each iteration. A common optimisation is to inline small helpers or use built-ins (which are implemented in C and bypass frame creation for simple operations).

Key Insight

The frame chain is Python's call stack. Unlike C, it lives on the heap and can be inspected at runtime with inspect.currentframe(). This is what makes debuggers, profilers, and traceback work — but it also means function calls are significantly more expensive than in compiled languages.

Section 10

Name Resolution — LEGB

When Python encounters a name like len or x, it searches through four scopes in order:

LEGB lookup order

Local lookups are fastest because CPython stores locals in a fixed-size array and accesses them by index — no dict lookup needed. Global and built-in lookups require a dict search, which is still O(1) but involves hashing and pointer indirection.

A real-world optimization trick

# In a hot loop, rebind a global as a local for speed
def process_items(items):
    _len = len           # bind built-in to local variable
    _append = items.append
    result = []
    for item in items:
        if _len(result) < 100:   # local lookup, not built-in lookup
            _append(item * 2)

This is a micro-optimisation that matters most in loops called millions of times. The speedup comes from skipping one dict lookup (global → built-in) on every iteration.

Section 11

The Import System

When you write import math, far more happens than "load a file":

Import resolution flow

The first time you import a module, Python runs its entire body. All top-level assignments execute, functions are defined, and classes are created. The resulting module object is stored in sys.modules. Every subsequent import of the same module simply returns the cached object — no re-execution.

This is why import-time side effects are dangerous: they run once and only once, regardless of how many files import the module.

Practical Tip

If you have expensive setup (loading a model, connecting to a database), putting it at module level is a valid pattern — it runs once per process. But it means startup time is paid upfront. Use lazy imports (importing inside functions) when startup time matters more than first-use latency.

Let's be honest about the costs:

Why Python still wins

Python's strategy is not to compete with C, Go, or Java at raw computation. It's to act as a control plane over high-performance native engines:

Python as a control plane

A NumPy operation like a * b on two arrays of one million floats runs a tight C loop at near-SIMD speeds, with no Python overhead for each element. Python writes the instruction; C executes it in bulk. The slowness of the PyObject model simply doesn't apply because Python is not in the hot path.

Key Insight

Python is a control plane, not a compute plane. Write your loops in Python; let NumPy, PyTorch, or Cython handle the iteration. The entire ML ecosystem is built on this exact boundary.

Interview-Grade Summary

CPython compiles source code through a lexer, parser, AST builder, and bytecode compiler into code objects, which are then executed by a stack-based virtual machine. Every value is a PyObject — a uniform object model that enables dynamic typing at the cost of memory overhead and pointer indirection. Memory is managed by reference counting for the common case, with a generational cyclic GC for object cycles. The Global Interpreter Lock ensures thread safety without fine-grained locks, at the cost of CPU-bound concurrency. Core structures like dicts are highly optimized open-addressing hash tables. Python's performance strategy is delegation: offload computation to native extensions (NumPy, PyTorch) while keeping Python in the orchestration layer.
