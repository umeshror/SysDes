System Design Trade-offs

Module 3  |  25 Comparisons — FAANG Interview Depth

How Interviewers Evaluate Trade-off Discussions

At L5+/Staff level, you are expected to name the trade-off before being asked, quantify the impact, cite a real-world precedent, and explain when you'd pick each side. The formula: "We could use X which gives us ____. The cost is ____. Given our constraint of ____, we choose X because ____."

1. Strong vs. Eventual Consistency

The single most tested trade-off in distributed systems interviews. Consistency defines what a reader sees after a write completes. In a distributed system, getting every node to agree instantly requires coordination overhead — latency, availability loss, or both.

Strong Consistency

  • Every read reflects the latest committed write
  • Implemented via: 2PC, Paxos, Raft, synchronous replication
  • Linearizability = strongest form (operations appear instantaneous)

Cost: Latency ↑, availability ↓ during partitions (CAP: choose CP)

Number: Spanner's global strong-consistent read adds ~5–15ms due to TrueTime wait

Eventual Consistency

  • Writes propagate asynchronously — nodes converge "eventually"
  • Reads may return stale data for a window (replication lag: ms to seconds)
  • Conflict resolution required: LWW, CRDTs, vector clocks

Gain: Low latency, high availability, horizontal scale (CAP: choose AP)

Number: Cassandra replication lag is typically 1–5ms in same DC, <100ms cross-region

flowchart TD A[Write arrives] --> B{Need all nodes to agree?} B -->|Yes| C[Synchronous replication\nRaft / 2PC / Paxos] B -->|No| D[Async replication\nGossip / Kafka / Bin-log] C --> E[Strong Consistency\n+Linearizable reads\n-Higher latency\n-Unavailable on partition] D --> F[Eventual Consistency\n+Low latency writes\n+Always available\n-Stale reads possible] E --> G{Your workload?} F --> G G -->|Money, auth, inventory| E G -->|Likes, views, feeds| F
Real-world: Amazon Shopping Cart
Amazon chose eventual consistency for the shopping cart (Dynamo paper, 2007). Showing a user a slightly stale cart is acceptable; being unavailable during checkout is not. Conflicts are resolved by merging carts on next read.
Real-world: Google Spanner
Spanner achieves external consistency (stronger than linearizability across datacenters) using TrueTime — atomic clocks + GPS receivers in every datacenter. Every commit waits for the uncertainty interval (typically 1–7ms) to pass before returning, ensuring global order.
Real-world: Meta TAO
Facebook's TAO graph cache replicates reads to followers with eventual consistency. Read-after-write for the same user is solved by reading from the master for a short window after a write — not full strong consistency, but a practical "consistency for the author" pattern.

2. Latency vs. Throughput

Two distinct performance metrics that are often optimized at each other's expense. Low latency = fast individual requests. High throughput = many requests completed per second.

System Latency p99 Throughput Technique
Redis GET <1ms ~1M ops/sec (single node) In-memory, single-threaded event loop
Kafka produce 2–10ms 1M+ msgs/sec per broker Sequential disk writes, batching, zero-copy sendfile()
DynamoDB single-digit ms Unlimited (partition scaling) SSD + consistent hashing + eventual consistency
PostgreSQL complex query 50–500ms Low under write contention MVCC + B-Tree, random I/O
Little's Law in interviews

L = λ × W — concurrency = arrival rate × avg latency. If your avg latency doubles, you need 2× more threads/connections to maintain the same throughput. This is why p99 latency spikes cause thread pool exhaustion and cascading failures.

3. ACID vs. BASE

Not just a database choice — a statement about what guarantees your system provides to application developers and downstream consumers.

ACID

  • Atomicity: Commit or rollback — never partial writes
  • Consistency: DB constraints always satisfied post-txn
  • Isolation: Concurrent txns don't see each other's dirty state
  • Durability: Committed data survives crashes (WAL / fsync)

Isolation levels: READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ → SERIALIZABLE (each adds cost)

BASE

  • Basically Available: System responds even during partial failures
  • Soft State: Data may expire or be overwritten without explicit action
  • Eventual Consistency: All replicas converge, given no new writes

Practical implication: Application must handle "read your own write" anomalies and conflicts

War story: Knight Capital (August 2012)
Knight Capital lost $440M in 45 minutes partly because their trading system lacked atomic rollback. A bad deployment activated obsolete code on 7 of 8 servers. Non-atomic deploy + no isolation between old and new logic = disaster. ACID transactionality in deployment (atomic switch) would have helped contain it.
Interview framing:
When asked "SQL vs NoSQL?", redirect to ACID vs BASE: "The real question is what consistency guarantees does this read/write path need? If two concurrent writers can conflict, we need ACID isolation. If we can accept stale reads and merge conflicts offline, BASE gives us more scale."

4. Caching Strategies

Strategy Read Path Write Path Stale Risk Data Loss Risk Use
Cache-Aside App checks cache → miss → load from DB → populate cache App writes DB; invalidates or TTLs cache entry Medium (TTL window) None General purpose, most common
Read-Through Cache fetches from DB on miss automatically App writes DB only Medium None Read-heavy, consistent read path
Write-Through Normal cache lookup Write to cache + DB synchronously None (always fresh) None When reads must always be fresh after write
Write-Back Normal cache lookup Write to cache only; async flush to DB None for reads High (unflushed data on crash) Write-heavy where durability is secondary (leaderboards, counters)
Cache Invalidation: The Hardest Problem

Phil Karlton: "There are only two hard things in Computer Science: cache invalidation and naming things." Stale cache entries cause subtle, hard-to-reproduce bugs. Prefer: short TTLs for mutable objects, event-driven invalidation with message queues (write to DB → publish event → subscriber invalidates cache), or versioned cache keys (user:42:v7 → write new version, old entries expire naturally).

5. Batch vs. Stream Processing

flowchart TD Event[New data event] --> Q{Acceptable latency?} Q -->|Hours / Days| B[Batch Processing\nHadoop / Spark Batch\nSimple retry on failure\nHigh throughput] Q -->|Seconds / ms| S[Stream Processing\nFlink / Kafka Streams\nExactly-once semantics\nStateful operators] B --> L[Lambda Architecture\nBatch layer accuracy\n+ Speed layer recency\n= Serving layer merge] S --> L
Meta's Scuba — Real-time analytics powered by streams
Meta processes 1TB+ of log data per second into Scuba, a real-time in-memory database. Engineers can query millions of rows within 1 second of them being logged — impossible with batch.
Netflix Keystone Pipeline
Netflix routes 2+ trillion events/day through a streaming pipeline built on Kafka and Flink. Used for: real-time A/B test result collection, encoding quality monitoring, CDN health, and personalization signals.
When batch wins
ML training, monthly billing, compliance reports, nightly ETL. The simplicity of "just re-run it" on failure is extremely valuable — no exactly-once semantics needed.

Polyglot Persistence — The FAANG Answer

Don't choose one. Use each database for what it does best: PostgreSQL for transactional user data, Cassandra for time-series / write-heavy, Redis for caching and leaderboards, Elasticsearch for full-text search, Neo4j / Neptune for graph traversal, ClickHouse / BigQuery for analytics. Uber runs 50+ Postgres clusters, 100s of Cassandra clusters, Elasticsearch, and Redis — simultaneously.

GitHub's dual API reality
GitHub REST v3 has been running since 2010. They launched GraphQL v4 in 2016 because the REST API required 300+ round trips for some IDE integrations. GraphQL reduced that to 1. Both still exist — REST for simple scripting and CI tools, GraphQL for rich client integrations.
Netflix internal gRPC
Netflix migrated internal service calls to gRPC (from REST+JSON) and achieved 67% reduction in payload bytes and ~10ms latency improvement per hop — meaningful at their scale of billions of internal calls/day.

8. Load Balancer vs. API Gateway

flowchart LR Client --> LB[Load Balancer\nL4/L7 traffic split\nHealth checks\nTLS termination] LB --> GW[API Gateway\nAuth / JWT validation\nRate limiting\nRequest routing\nTransformation] GW --> S1[Service A] GW --> S2[Service B] GW --> S3[Service C]

These are complementary, not alternatives. The LB is an infrastructure concern (where does traffic go?); the API Gateway is a business concern (is this caller allowed, and what should they see?).

When to skip the API Gateway
Internal service-to-service calls behind a service mesh (Istio / Linkerd). mTLS, retries, circuit breakers, and telemetry are all handled by the mesh sidecar. Adding an API Gateway on top would just add a latency hop with no benefit.
Kong at scale
Kong (open-source API Gateway) processes 1 trillion+ API calls/month for some enterprises. It runs as a cluster of Nginx+LuaJIT processes — a proxy, not a monolith. Each plugin (auth, rate limiting) is a micro-module executed per request in ~0.1ms.

10. Polling vs. WebSockets vs. SSE

sequenceDiagram participant Client participant Server Note over Client,Server: Short Polling Client->>Server: GET /status (every 5s) Server-->>Client: 200 (empty if no change) Note over Client,Server: Long Polling Client->>Server: GET /events (hold connection) Server-->>Client: 200 (only when event ready) Note over Client,Server: WebSocket Client->>Server: HTTP Upgrade Server-->>Client: 101 Switching Protocols Server-->>Client: push event (async, anytime) Client->>Server: send message (async, anytime) Note over Client,Server: SSE Client->>Server: GET /stream Server-->>Client: data: event1 Server-->>Client: data: event2
Slack's WebSocket fleet
Slack maintains millions of persistent WebSocket connections. They run a dedicated "connection server" layer (written in Java) whose sole job is to hold sockets and fan-out messages. It's completely stateless in terms of business logic — it just knows "user X is connected to server Y." Business logic lives in separate services.
Twitter's SSE for timelines
Twitter's "live" timeline uses SSE (not WebSockets) because the feed is server→client only. SSE uses plain HTTP — works through proxies, firewalls, and CDNs without special handling. Auto-reconnect is built into the browser spec.

11. Stateful vs. Stateless Architecture

Stateless (preferred for scale)

  • Request carries all context: JWT, API key, request ID
  • Any instance handles any request — true horizontal scale
  • Blue/green deploy, rolling restart, auto-scale: all trivial
  • Health check = simple HTTP ping, no state to drain

Stateful (when you need it)

  • WebSocket connections — session lives on specific server
  • In-memory game state — microsecond access to mutable data
  • Streaming processors — maintain aggregation windows
  • Must drain connections on shutdown, sticky LB routing
The Twelve-Factor App Rule #6

"Processes are stateless and share-nothing." Any data that needs to persist must be stored in a backing service (DB, cache, object store). This is why Lambda functions and containerized microservices scale so cleanly — there's nothing to coordinate between instances.

Modular Monolith Microservices

Observability One log stream, one trace Distributed tracing required (Jaeger, Tempo)
Data Shared schema — easy joins Separate DBs — eventual consistency between services
Latency In-process method calls: nanoseconds Network RPC: 0.5–5ms per hop

Amazon's "two pizza teams" origin
Amazon's famous move from monolith to microservices in the early 2000s wasn't primarily technical — it was organizational. Jeff Bezos mandated that teams communicate only via service APIs. This forced clean boundaries and enabled independent deployment. The monolith-to-microservices transition took 4 years.
The Distributed Monolith anti-pattern
If your microservices deploy together, share a database, or require synchronous calls through a long chain to complete one user request — you have a distributed monolith. You get all the operational complexity of microservices with none of the scaling benefits. Signs: services can't be deployed independently, one service change requires updates to 5 others.

13. Token Bucket vs. Leaky Bucket (Rate Limiting)

flowchart LR subgraph Token Bucket T1[Tokens added at\nrate N/sec] --> T2[Bucket capacity = B\nAllows burst up to B] T2 -->|Token available| T3[Request passes] T2 -->|Empty| T4[Request rejected / queued] end subgraph Leaky Bucket L1[Requests enter\nqueue - FIFO] --> L2[Drains at constant\nrate R/sec] L2 --> L3[Request processed\nSteady smooth output] L1 -->|Queue full| L4[Request dropped\noverflow] end
Stripe's rate limiting architecture
Stripe uses a sliding window algorithm in Redis, storing a sorted set of request timestamps per API key. On each request: ZADD (add now), ZREMRANGEBYSCORE (remove old), ZCARD (count). If > limit → reject. The Redis sorted set operation is O(log N) and completes in <1ms. Stripe also uses tiered limits: per-endpoint, per-key, per-IP, and per-account simultaneously.
Cloudflare's distributed rate limiting
Cloudflare uses approximate sliding window counters synchronized across PoPs. Each PoP maintains a local counter and syncs periodically. This allows 100Gbps+ of traffic to be rate-limited at the edge without a central coordinator — consistency is sacrificed for availability and scale.

14. Primary-Replica vs. Multi-Primary Replication

flowchart TD subgraph Primary-Replica W1[Write] --> P[Primary\nAccepts all writes] P --> R1[Replica 1\nRead only] P --> R2[Replica 2\nRead only] end subgraph Multi-Primary W2[Write] --> M1[Primary 1\nAny writes] W3[Write] --> M2[Primary 2\nAny writes] M1 <-->|Conflict resolution\nLWW / CRDT| M2 end
MySQL at GitHub scale
GitHub runs thousands of MySQL instances in primary-replica topology. Each write goes to one primary; replicas serve reads. Replication lag is monitored continuously — if replica lag exceeds ~30 seconds, read traffic is redirected to the primary. Failover is automated via Orchestrator, taking ~30–45 seconds.
CockroachDB's multi-primary approach
CockroachDB implements multi-primary replication using Raft consensus per key range (16MB chunks called "ranges"). Each range has a Raft leader that coordinates writes. Conflict resolution is guaranteed by the consensus protocol — no LWW ambiguity. Enables active-active multi-region writes.

15. Horizontal vs. Vertical Scaling

Vertical Scaling (Scale Up)

  • Add more CPU, RAM, faster disk to the same machine
  • Simpler — no distributed systems coordination
  • Hard limit: largest available instance (e.g., AWS x2iedn.32xlarge: 4TB RAM)
  • Single point of failure remains
  • Good first step — often cheapest solution

Horizontal Scaling (Scale Out)

  • Add more machines; distribute load across them
  • No theoretical upper limit on capacity
  • Enables geographic distribution, fault isolation
  • Requires: load balancing, distributed state management, consensus
  • More complex operationally — worth it at true scale
Instagram's 2012 peak: vertical first
Instagram ran on a handful of EC2 instances for their first year (vertical scaling). Only after hitting the wall did they introduce sharding and horizontal scale. Lesson: Don't over-engineer. Scale vertically until it's no longer cost-effective, then scale horizontally. "Premature optimization is the root of all evil."

16. Push vs. Pull Architecture

Prometheus (Pull) vs. StatsD (Push)
Prometheus scrapes (pulls) metrics from each service's /metrics endpoint every 15s. Services don't need to know about Prometheus. Easy to discover new services, replay historical scrapes. Downside: what if a service dies between scrapes?

StatsD pushes UDP packets from within the application to a StatsD daemon. Low-overhead fire-and-forget. Downside: UDP is lossy, service must know StatsD address.

Prometheus dominates at FAANG scale (Kubernetes-native). StatsD is common in legacy or non-containerized systems.
Kafka's pull model for consumers
Kafka consumers pull at their own pace — this is intentional. Consumers control their offset. A consumer can slow down, go offline, and resume without losing messages (up to retention period). This "backpressure by design" is why Kafka consumers don't get overwhelmed — they simply slow their polling rate when processing is behind.

17. Orchestration vs. Choreography

flowchart TD subgraph Orchestration O[Order Service\nOrchestrator] -->|1. Reserve inventory| I[Inventory] O -->|2. Charge payment| P[Payment] O -->|3. Schedule shipping| S[Shipping] O -->|4. Send confirmation| N[Notification] end subgraph Choreography E1[order.placed event] --> I2[Inventory\nlistens & reserves] I2 --> E2[inventory.reserved event] E2 --> P2[Payment\nlistens & charges] P2 --> E3[payment.completed event] E3 --> S2[Shipping\nlistens & schedules] end
AWS Step Functions (Orchestration)
Step Functions provides a visual workflow editor and execution history for every state machine run. You can see exactly which step failed, with input/output logged. This makes debugging trivial compared to tracing choreographed events across Kafka topics. Used by Amazon's own order processing pipeline.
Choreography failure modes
In choreography, if the Payment service publishes "payment.completed" but the Shipping service's consumer group is down, the event sits in Kafka. When Shipping comes back up, it processes the backlog. This is resilient — but "zombie" or duplicate events require idempotent consumers. Every consumer must handle receiving the same event multiple times without double-processing.

Hot Shard Problem

If a celebrity (Justin Bieber, Taylor Swift) posts on a social network, all writes/reads for that entity go to one shard. Solutions: (1) add a random suffix to the shard key for hot entities, (2) pre-shard hot keys across multiple shards and aggregate reads, (3) use a separate cache tier for hot entities. Twitter specifically had to redesign their fan-out mechanism for celebrities with 100M+ followers.

19. Stateless Rate Limiting vs. Distributed Rate Limiting

Per-instance rate limiting (stateless)
Each server tracks its own counters in local memory. Fast (no network call) but approximate — 10 servers with 100 RPS limit each = 1000 RPS effectively passes. Acceptable for protecting individual servers from overload, not for API quota enforcement.
Centralized distributed rate limiting (Redis)
All servers increment a shared Redis counter. Accurate across the entire fleet. Redis INCR + EXPIRE is atomic — no race conditions. Latency cost: ~0.5ms per request for the Redis round trip. Used by: Stripe, GitHub, Shopify. Redis Cluster scales this to millions of keys/sec.
Gossip-based (approximate, edge-native)
Cloudflare's edge rate limiting syncs counters between PoPs via gossip. Each PoP's counter may be slightly stale (by milliseconds). Allows up to ~10% over-limit in exchange for no centralized bottleneck. Tradeoff: accuracy vs. availability and latency.

Master Framework: The 5 Trade-off Questions

Use this in every system design interview
  1. "What breaks first?" — Identify the bottleneck: DB writes? Network bandwidth? CPU? Memory? Design for the constraint, not the happy path.
  2. "What's the blast radius?" — If this component fails, what is the worst-case user impact? Design to minimize and isolate blast radius.
  3. "What do we give up?" — Name the specific CAP/PACELC tradeoff. Saying "we use Cassandra for availability" must come with "we give up immediate consistency."
  4. "Does this match the scale?" — A 10-user system doesn't need Kafka. A 10M-user system can't run on a single MySQL. Tailor complexity to actual requirements.
  5. "Can we change this later?" — Data model and public API contracts are expensive to change. Deployment architecture is cheaper. Be conservative where reversibility is low.
